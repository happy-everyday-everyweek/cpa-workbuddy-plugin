# Coze 上游失败被当「成功但 0 输出」返回 — 根因诊断

> 记录时间：2026-10-19 02:00
> 影响版本：coze-provider 0.4.0 ~ 0.4.3
> 修复版本：0.4.4

## 1. 现象

用户在 new-api 与 CPA 面板观察到：

- new-api 通用日志：该模型 `Tokens` 恒为 `-`、费用 `$0`。
- CPA 面板：连续 6 条请求 `输入 20702 / 输出 0 / 生成 6~12ms`，
  **全部标记为「成功」**。
- 客户端侧：请求"通了"，但拿不到任何回答。

关键点：这些请求**不是超时或报错**，而是被上游与本插件共同表达成了
"快速、成功、无内容"。这比直接报错更难排查。

## 2. 取证过程

### 2.1 先排除 usage 输出问题

0.4.1 已修复「插件不输出 usage」：直连插件测试得到 `9/2/11` 的真实估算值，
说明 usage 通道本身正常。面板里 `output=0` 不是估算逻辑的问题，
而是**正文真的是空的**——空正文自然算出 0 输出。

### 2.2 连测复现

连续 15 次对话请求，第 11~15 次出现连续空正文（WS 仅 3 个事件）。

### 2.3 诊断日志定位

0.4.2 / 0.4.3 两轮诊断版发布后，捕获到决定性日志：

```
[2026-10-19 01:32:00] [warn ] 对话执行失败
model=coze/doubao-seed-2-0-lite-260215
error=提交消息失败：该用户积分已耗尽（code=1000521）
```

同时查询账号积分接口确认：

```json
{"credits":{"expiring_remain":0,"remain":0,"total":3000}}
```

**上游根因**：扣子账号 3000 积分已全部用尽，`message/chat` 直接拒收消息。

## 3. 插件侧真实缺陷

上游拒绝是外部状态，本身不是插件缺陷。真正的缺陷是**插件把失败表达成了成功**：

### 3.1 抢发首帧使宿主提前判定流成功

`pumpClawStream` 在进入对话链路之前就先发了 assistant 角色帧：

```go
// 修复前
if first, errFirst := buildFirstChunk(id, model); errFirst == nil {
    if errEmit := streamEmit(streamID, first); errEmit != nil {
        return
    }
}
reply, errRun := exec.runStream(ctx, prompt, emit)
```

宿主 `sdk/api/handlers/handlers_stream.go:478` 的逻辑是
**"收到第一个 dataChunk 就提交流式响应头"**。角色帧一发，
宿主即认为本轮已成功开始，此后任何错误都只能退化为流内事件，
HTTP 状态码已无法回退。

### 3.2 失败仍补正常终止帧

```go
// 修复前
finishReason := openAIFinishStop
if errRun != nil {
    finishReason = openAIFinishLength
}
terminal, _ := buildChunk(id, model, "", &finishReason, buildUsage(prompt, reply))
_ = streamEmit(streamID, terminal)
```

即便 `sendChat` 直接失败，插件仍发出 `finish_reason=length` 的空正文终止帧。
对宿主和 new-api 而言，这就是一次**结构完整、正常结束的响应**：

- 没有 `error` 字段 → 不计失败；
- 有 `finish_reason` → 不判截断异常；
- `usage.completion_tokens=0` → 计费为 0。

三者叠加 = 「成功、0 输出、$0」。

### 3.3 同步路径同样问题

`collectStreamChunks` 复制了同一套逻辑，且同样在开头先 append 角色帧、
失败时返回 `chunks, nil`，宿主因此同样判成功。

## 4. 宿主的正确错误通道

查阅宿主源码确认两条事实：

1. `internal/pluginhost/stream_bridge.go:46` 的 `rpcStreamEmitRequest`
   带有 `Error string` 字段；`host.callHostStreamEmit` 会把它转成
   `pluginapi.ExecutorStreamChunk{Err: ...}`。
2. `sdk/api/handlers/handlers_stream.go:148` 对 `chunk.Err != nil`
   走 `executionErrorMessage` + `errChan` 失败分支，
   最终由 `ForwardStream` 的 `WriteTerminalError` 写出错误帧。

因此**错误必须走 `stream.emit` 的 `error` 字段，不能写成 payload**。

## 5. 修复方案（0.4.4）

### 5.1 首帧延迟到有内容时

角色声明帧不再抢跑，改为在首个**真正的 payload** 之前补发：

```go
emitted := false
emitContent := func(payload []byte) error {
    if !emitted {
        first, _ := buildFirstChunk(id, model)
        if errEmit := streamEmit(streamID, first); errEmit != nil {
            return errEmit
        }
        emitted = true
    }
    return streamEmit(streamID, payload)
}
```

这样"是否已有内容送出"成为可用于收尾判定的真实状态。

### 5.2 收尾决策按"是否已产出"分流

```go
func streamTerminal(errRun error, emitted bool) (string, error) {
    if errRun == nil {
        return openAIFinishStop, nil
    }
    if !emitted {
        return "", errRun   // 走错误通道
    }
    return openAIFinishLength, nil  // 保留已渲染内容
}
```

- 未产出 → `emitStreamError` 发 `{"stream_id":..., "error":"..."}`，
  下游收到明确失败与上游错误文案。
- 已产出 → 维持 `length` 收尾，不因后段失败作废已渲染内容。

### 5.3 空正文不再算成功

`waitForReply` 在两处补了失败返回：

- `event_final` 已到、兜底轮询也失败，且**正文与图片都为空** → 返回错误；
- 首字超时降级轮询后仍为空 → 返回错误。

判定同时看图片：生图回复的正文可能只是占位文本，不能仅凭正文为空判失败。

### 5.4 同步路径对齐

`collectStreamChunks` 同样延迟角色帧；未产出任何 chunk 时返回 `nil, err`，
由宿主按失败处理，不再伪造终止帧。

## 6. 验证

### 6.1 单元测试

新增 5 个用例：

| 用例 | 锁定契约 |
|---|---|
| `TestStreamTerminalReportsFailureBeforeFirstPayload` | 首帧前失败必须报错；已产出后用 length；正常结束用 stop |
| `TestMarshalStreamErrorEnvelope` | 错误信封走 `error` 字段，绝不带 `payload` |
| `TestRunStreamFailsWhenChatRejected` | 上游 `code=1000521` 时 `runStream` 必须返回错误 |
| `TestWaitForReplyFailsOnEmptyFinished` | 收尾但无内容必须返回错误 |
| `TestPumpClawStreamEmitsErrorBeforeFirstPayload` | 首帧前失败不得发出任何 payload |
| `TestPumpClawStreamKeepsContentAfterPartialFailure` | 已产出后失败用 length 收尾且带 usage |

`python scripts/cgo-shim-build.py coze`：build / vet / test 全绿。

### 6.2 变异反证

将 `pumpClawStream` 的收尾逻辑改回旧实现（失败一律给 `length`、
不走错误通道），`TestPumpClawStreamEmitsErrorBeforeFirstPayload`
精确失败并打印出被发出的角色帧 payload；还原后恢复全绿。

同时验证另两处：移除 `waitForReply` 的空正文报错后
`TestWaitForReplyFailsOnEmptyFinished` 失败；移除轮询后的空正文判定同样失败。

## 7. 残余事项

- **账号积分耗尽属外部状态**：`remain=0 / total=3000`，需充值或换账号后才能
  验证真实对话。本修复只保证"失败会被正确表达为失败"。
- 0.4.2 / 0.4.3 的诊断日志保留为常驻可观测性：空正文与执行失败
  在生产排障中仍是高价值信号。
