# Qoder 模型发现接口 COSY 签名失效（Signature invalid）根因诊断

- 编号：BUG-QODER-MODELS-SIGNATURE-INVALID-20261012
- 发现时间：2026-10-12 01:45（北京时间，用户要求对生产日志中 `Signature invalid` 取证）
- 判定时间：2026-10-12 01:55（北京时间）
- 状态：**已定位根因并于 2026-10-19 实施修复（qoder-ai / qoderwork 带体 GET + 五插件失败负缓存），本地单测与变异验证全绿，未发布生产**
- 关联：`doc/4-bugs/2026-10-12_001641_Qoder上游200排队帧未被识别致new-api调用qwen3.8挂死根因诊断.md`（同插件的另一独立缺陷）

## 1. 现象

生产 CPA 容器 `cli-proxy-api` 日志持续输出：

```
[qoder-ai] callModelsAPI: upstream status 403, body: {"code":"101","message":"Signature invalid"}
[qoder-ai] authModelsForIndex: dynamic discovery failed (models API status 403), falling back to static list
```

即 **模型动态发现（`GET /algo/api/v2/model/list`）的 COSY 签名被上游拒绝**，插件回落硬编码静态列表。

## 2. 规模与时间线

| 项 | 实测 |
| --- | --- |
| 累计条数（容器 8h 日志窗口） | **5449 条**（qoder-ai 5208 / qoderwork 241） |
| 首次出现 | 2026-10-11 14:23:14（容器 `StartedAt=2026-10-11T09:26:24Z`，即启动后约 5h） |
| 最新出现 | 持续至今（2026-10-12 01:48 仍有） |
| **models API 成功次数** | **0**（`dynamic discovery ok` 对 qoder 两插件全量搜索均为 0） |

**关键事实：该接口从未成功过**，不是"最近坏掉"，而是自 qoder-ai 0.1.0/0.1.1（2026-10-10 提交）落地起即失效——静态兜底一直在掩盖它。

## 3. 影响面（重要：不影响推理）

`grep 'Signature invalid' | grep -v callModelsAPI` = **0 条**，`grep 'upstream status 403' | grep -v callModelsAPI` = **0 条**：

- **403 只出现在 `callModelsAPI` 一条路径**，推理路径零命中。
- **同账号对照**（决定性）：账号 `qoderai-01a126de`、`qoderai-01a003c5` 在同一时段 **`active ping success ... with model auto`**（推理探活成功），同时其 models 发现失败——证明账号凭据、COSY 会话构建、签名算法主体均正常。
- 推理真实用量对照（最近 2h）：`failed=false` 19 条 / `failed=true` 14 条（后者为排队帧 60s 挂死，属另一 Bug），**无一条因签名失败**。

⇒ 实际影响限于：**模型列表退化为 10 个硬编码静态模型**（`qmodel_preview` / `auto` 等），而非上游实时列表。主用模型名仍在静态列表内，故用户侧感知弱，但动态发现这一设计功能**从未生效**。

## 4. 根因

**签名所声明的 body 与实际 HTTP 请求发送的 body 不一致。**

`qoder-ai/models.go:306-320`：

```go
encodedBody := qoderEncode([]byte("{}"))                       // 签名用这个
rawURL := endpointModels                                        // /algo/api/v2/model/list?Encode=1
req, err := http.NewRequestWithContext(ctx, http.MethodGet, rawURL, nil)  // 实际 body = nil
if err := applyCosyHeaders(req, sa, encodedBody, rawURL, "", false); err != nil {
```

`applyCosyHeaders` → `buildBearer(body, rawURL)`（`sign.go:166-188`）把 `body` 拼进签名：

```
sig = md5_hex(payloadB64 + "\n" + cosyKey + "\n" + date + "\n" + body + "\n" + pathSig)
```

即签名里写的是 `qoderEncode("{}")`，而 GET 请求**根本不发送 body**。

**与成功路径的逐项对照**：

| 路径 | 方法 | 实际发送 body | 签名 body | 结果 |
| --- | --- | --- | --- | --- |
| 推理（`endpointChat`） | POST | `strings.NewReader(encodedBody)` | `encodedBody` | **一致 → 成功** |
| 模型发现（`endpointModels`） | GET | `nil`（无 body） | `qoderEncode("{}")` | **不一致 → 403** |

两条路径共用同一 `buildBearer`，`payloadB64` / `cosyKey` / `date` / `pathSig` 的计算逻辑完全相同且推理已验证可用，**body 是二者唯一的差异变量**。

**代码注释即错误来源**：`models.go:309-310` 写着「An empty JSON object works (verified in reference_impl.py)」——该参考实现文件在当前仓库已不存在（`find` 无结果），注释描述的构造与实际 GET 无 body 的实现相矛盾，属历史遗留误植。

## 5. 证据

- **规模**：`docker logs cli-proxy-api | grep -c 'Signature invalid'` = 5449（qoder-ai 5208 / qoderwork 241）。
- **路径唯一性**：`grep 'Signature invalid' | grep -vc callModelsAPI` = 0。
- **从未成功**：`grep -cE '\[qoder-(ai|work)\].*dynamic discovery ok'` = 0（全量日志）。
- **同账号反证**：同一 `auth_file` 推理探活 `active ping success` 与 models 403 并存（2026-10-12 01:48 样本）。
- **代码事实**：`models.go:311` `qoderEncode([]byte("{}"))` 与 `:313` `http.MethodGet, rawURL, nil` 并存；`sign.go:184` 签名含 `body` 项。
- **双插件同构**：`qoderwork/models.go:309-322` 与 `qoder-ai/models.go:306-320` 结构逐行相同，两插件同时失效（5208 / 241 条）。
- **上游响应语义**：`{"code":"101","message":"Signature invalid"}` 为签名校验失败业务码，非端点不存在（后者会是 404 或其它码）。

## 6. 待验证点（本轮未直测）

1. ~~**服务端对无 body 的 GET 用哪个值校验签名**~~ **已裁定（2026-10-19）**：参照可正常工作的外部实现 qoder2api-hub（`shuishuipingan/qoder2api-hub`，commit `fd7a3740`，`qoder_proxy.py::read_dynamic_models`）——`sign_body = qoder_encode(b"{}")` 同时作为签名值与 GET 请求体发出（`Request(url, data=sign_body.encode(), method="GET")`），其注释明确裸 GET 会被服务端判 403。即服务端按「签名声明的 body == 实际收到的 body」校验，修复方向定为 §7-1（签名与请求都带 body）。
2. **国际版端点契约**：`KNOWLEDGE.md` §7 表格中 intl（qoder.com）的「模型清单」标注为 `?`（未验证），仅 CN 版记录 `GET /algo/api/v2/model/list` 实测成功（`models_list.json` 39898 bytes）。当前 qoder-ai 走 `openapi.qoder.sh`（国际），需确认该端点在国际版是否同样支持 COSY 签名——但 **qoderwork（CN，`gateway.qoder.com.cn`）同样 100% 失败（241 条）**，说明主因是代码实现而非区域端点差异。
3. 受本地连接红线约束（不得用生产凭据直连上游补证据），本结论基于代码 + 生产日志，未做服务端行为直测。

## 7. 修复方向（2026-10-19 已按方向 1 实施，见 §9）

根因单一、修复点唯一：**让 `callModelsAPI` 的签名 body 与实际发送 body 一致**，两条候选（择一，按待验证点 1 的结论）：

1. **签名与请求都带 body**：`http.NewRequestWithContext(ctx, http.MethodGet, rawURL, strings.NewReader(encodedBody))`，保持签名用 `encodedBody`；
2. **签名与请求都为空**：签名 body 传 `""`，请求保持 `nil`。

同步修复 `qoderwork`（同构代码）。验证方式：新增单测断言「签名 body 与请求实际 body 严格相等」；修复后生产观测 `dynamic discovery ok: N models` 首次出现，且 `Signature invalid` 归零。

## 8. 未覆盖与后续风险

- **未覆盖**：`active ping` 出现 `upstream 200: 112: {"pricingUrl":...}`（3 条，探活侧业务码），与签名无关，需另立评估。
- **未覆盖**：模型发现失败长期被静态兜底掩盖，可能存在其它"从未生效但被兜底隐藏"的动态能力，建议排查同类回落路径的可观测性（当前仅在 debug 日志暴露，无面板告警）。
- **风险**：修复涉及 `models.go` + `sign.go` 调用契约，属模型目录路径改动，须走完整回归（cgo-shim build/vet/test + 6-review + 生产热重载验收）。

## 9. 实施结论（2026-10-19，会话 670f2eed，未发布生产）

按 §7 方向 1（签名与请求都带 body）+ 负缓存加固实施，范围与证据：

### 9.1 P0 签名一致性修复（qoder-ai / qoderwork）

- 两处 `callModelsAPI` 重构出 `newModelsAPIRequest`：GET 以 `strings.NewReader(encodedBody)` 真实携带与签名同一的 `qoderEncode("{}")` 请求体（此前签名带 body、实际 body=nil，恒 403 code 101）。
- qwenwork 不受本缺陷影响（其 `callModelsAPI` 走 Bearer + `/api/desktop/chat-modes`，无 COSY 签名）。
- 新增 `models_sign_body_test.go`：不依赖网络，从 `Bearer COSY.<payloadB64>.<sig>` 头反推 md5，穷举候选 body（`""` / `qoderEncode("{}")`）还原签名，断言「签名声明的 body == 请求实际 body」。
- 变异验证：把请求体改回 `nil` → 该用例 FAIL 且报错打印两者值（`签名 body="$kwm…" 与实际 body=""`），确认断言真能捕获旧缺陷。

### 9.2 P1 模型发现失败负缓存（qoder-ai / qoderwork / qwenwork / workbuddy / workbuddy-ai）

- `dynamicModelsCache` 增加 `failedAt` 字段与 `dynamicModelsFailCacheTTL = 5min`；新增 `inDynamicModelsFailWindow` / `markDynamicModelsFailed`；`storeDynamicModels` 成功即清除窗口。
- 所有逐账号扫描 / 单账号拉取入口（qoder 系 `fetchDynamicModels` + `fetchDynamicModelsFromStorage`；workbuddy 系 `fetchDynamicModelsFromStorage` + `fetchDynamicModelsFromAnyAuth` / `dynamicModelsFromCacheOrAuth`）在窗口内直接返回 nil，交给 resolveModels 静态兜底；全败路径写入 `failedAt`。
- 这直接切断「auth 重写 → model.for_auth → N 账号 × 每事件全扫」的 N+1 风暴（生产 8409 条 403 的放大器），即使 P0 未生效或上游再次变更也不会重演。
- 每插件 `callModelsAPIFn` 注入缝（沿 `sendActivePingQoderFn` 既有惯例）支撑真实行为断言：`models_negative_cache_test.go` 三用例——窗口拦截（第二次事件 calls 保持 1）、窗口过期恢复（calls=2）、成功清窗口 + 二次失败重开窗口。
- 变异验证：删除窗口检查 → 拦截用例 FAIL（calls=2, want 1），三个插件形态各自复验。
- **9.2.1 复核追加修复（同日晚间）**：首版 `fetchDynamicModelsFromStorage` 在「本账号被拒」分支先 `markDynamicModelsFailed()` 再 `return fetchDynamicModels()`，而后者入口的窗口检查会立即拦住 → 自身声明的「回退到已注册凭据扫描」成为死路径（本账号凭据损坏时另一账号本可成功的扫描永远走不到）。改为「先回退、无果再开窗」，并抽出 `fetchDynamicModelsFallbackFn` 接缝支撑顺序断言；新增 `TestNegativeCache_StorageFallbackRunsBeforeWindow`，变异（恢复先开窗）→ `回退结果应被采用，got []` 精确 FAIL。

### 9.3 P2 换号退避与错误体上限（qoder-ai / qoderwork / qwenwork）

- `pickNextAuth` 在选定候选后统一 `time.Sleep(failoverBackoff)`（50ms）：所有换号路径（执行器循环 / 流式循环 / 前置冷却拦截）都经此唯一 chokepoint，单点收口；默认预算 10 次时最坏增加 500ms。
- `readAllUpstreamErr` 改为 `io.LimitReader(r, 1<<20)`，对齐仓库既有惯例（zcode / copilot / cursor / doubao 同 1MiB）。
- `read_all_upstream_err_limit_test.go`：3MiB 输入断言恰好截断 1MiB + 短错误体原样保留 + 退避常量非零护栏；变异（去 LimitReader / 退避归零）均 FAIL。

### 9.4 验证与边界

- 五插件 `python scripts/cgo-shim-build.py <plugin>` build+vet+test 全绿（复核修复后重跑：qoder-ai 10.0s / qoderwork 10.1s / qwenwork 10.6s / workbuddy 25.9s / workbuddy-ai 2.5s）；本轮改动文件 gofmt 全绿；生产代码测试污染扫描 `POLLUTION: PASS`（注入缝仅测试替换，生产默认指向真实现）。
- P0 宿主转发链已对宿主源码取证：`internal/pluginhost/http_bridge.go:156` 用 `bytes.NewReader(bytes.Clone(req.Body))` 重建请求，GET 携带的 body 会真实发出（非插件侧假象）。
- **端到端「dynamic discovery ok 首现 / Signature invalid 归零」属生产观测项，本轮按用户约束不发布、不热重载，留待发布后验收**；P0 方向性结论以上游可工作实现（qoder2api-hub）+ 签名/实际 body 一致性不变量测试为据。
- workbuddy / workbuddy-ai 本轮只补 P1 负缓存（其签名链路无 P0 缺陷、换号风暴面 P2 未纳入本轮范围）；若后续要全插件对齐 P2，另立周期。
