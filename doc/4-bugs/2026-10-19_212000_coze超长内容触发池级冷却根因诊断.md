# coze 超长内容触发池级冷却根因诊断

- 日期：2026-10-19 21:20 (GMT+8)
- 插件：`coze-provider` 0.4.5（生产）
- 表现：`doubao-seed-2-0-lite` 连续返回
  `503 auth_unavailable: no auth available (providers=coze-provider, model=doubao-seed-2-0-lite; last upstream error: 提交消息失败：数据库错误（code=1000003）)`
- 结论：**上游 `message/chat` 的 content 有 65535 字节硬上限；越界返回 `1000003`，
  插件把它当账号级失败上抛，宿主因此冷却整个账号池。**

## 1. 现象取证

生产容器日志（2026-10-19 21:05）：

```
[21:05:07] warn 对话执行失败 model=coze/doubao-seed-2-0-lite-260215 error=提交消息失败：数据库错误（code=1000003）
[21:05:07] warn upstream execution failed ... auth_file=coze-1185dd02733b1278.json duration=3.571s
[21:05:09] warn 对话执行失败 ... error=提交消息失败：数据库错误（code=1000003）
[21:05:09] warn upstream execution failed ... auth_file=coze-d74585febdd673f3.json duration=1.817s
[21:05:09] error 500 | 5.419s | POST "/v1/responses"
[21:05:09] error 503 | 3ms   | POST "/v1/responses"   ← 此后全部 3–5ms 短路
```

关键判据：
- 两个**不同账号**各失败一次，错误码完全相同 → 不是单账号问题；
- 21:05:09 起 503 的耗时全部是 3–5ms → 宿主在候选选择阶段就拒绝，没有触达上游；
- 两个账号文件 `disabled:false`、无 `auth_invalid` → 不是 0.4.5 的失效标记误判。

## 2. 直连上游探测（绕过插件）

用生产账号直接请求 `www.coze.cn`，结果：

| 场景 | content 体积 | 结果 |
|---|---|---|
| 短消息 | 十余字节 | `code:0` |
| 5KB 文本 | 5109 字节 | `code:0` |
| 多角色折叠 | 54 字节 | `code:0` |
| 并发 3 条 | 各数十字节 | 全部 `code:0` |
| 中文长文 | 50013 字符（150KB） | `code:1000003` |
| ASCII 20KB | 20018 字节 | `code:0` |
| ASCII 48KB | 48002 字节 | `code:0` |
| ASCII 60KB | 60000 字节 | `code:0` |
| ASCII 65.5KB | 65500 字节 | `code:0` |
| **ASCII 64KB 边界** | **65535 字节** | **`code:0`** |
| **ASCII 64KB 边界** | **65536 字节** | **`code:1000003`** |

结论：**阈值精确等于 65536 字节（64KB），与内容语义、账号、并发均无关**。
这是上游消息落库字段的长度上限，越界时上游返回的是「数据库错误」而非参数校验错误。

## 3. 端到端复现（经生产 CPA）

```
1) 短请求           → 200
2) 70000 字节 prompt → 500 {"message":"提交消息失败：数据库错误（code=1000003）"}
3) 紧接着短请求 ×3   → 503 auth_unavailable（3 次全部）
```

第 3 步是故障放大器：**一次超长请求之后，正常的短请求也全部不可用**。

## 4. 根因链

```
用户请求 prompt ≥ 65536 字节
  → 插件握手成功、WS 建连、message/chat 被上游拒（code=1000003）
  → 插件 pumpClawStream 首帧前失败，经 stream.emit 的 error 字段上报纯文本
     （host_callbacks.go:246 把它转成 chunk.Err，不带任何 HTTP 状态码）
  → 宿主 resultErrorFromError 因无状态码，按 500 处理
  → MarkResult → applyAuthFailureState 的 default 分支
     走 recoverableFailureRetryAfter → auth.Unavailable = true、NextRetryAfter = now + 冷却
  → 两个账号各经历一次后全部不可用
  → availableAuthsForRouteModel 返回 auth_unavailable
  → 此后所有 coze 请求 3ms 内 503，直到冷却到期
```

两个放大器：
1. **上游错误码语义失真**：`1000003` 字面是「数据库错误」，实际由体积超限触发；
2. **错误通道丢失状态码**：插件不实现 `StatusCode()`，宿主的
   `IsRequestFault` 判据（400/409/413/422）永远不成立，只能当 5xx。

## 5. 修复

### 5.1 入口预检（主修复）

新增 `verifyChatContent`，按 **UTF-8 字节**校验，上限 `clawMaxContentBytes = 65535`。
在 `handleExecExecute` 与 `handleExecStream` 的**同步入口**、任何上游调用之前执行。

为什么必须放在同步入口：异步已返回后，`pumpClawStream` 在后台协程里失败只能
走 `stream.emit` 的纯文本 `error` 通道——那里没有状态码字段，宿主仍会冷却账号。
同步入口的失败会经 RPC 信封回传，才能携带 `http_status`。

### 5.2 错误信封补状态码

`envelopeError` 增加 `Retryable` 与 `HTTPStatus`；新增 `requestFaultEnvelope`。
`cliproxyPluginCall` 的错误回写改为 `writeExecutionError`：错误实现
`StatusCode()` 且落在 4xx 时用请求级信封，其余保持原样。

宿主侧对应链路：
- `internal/pluginhost/rpc_client.go:310` 读 `envelope.Error.HTTPStatus` → `rpcPluginError`；
- `internal/clienterror/client_error.go:101` 把 413 列入请求故障白名单；
- `sdk/cliproxy/auth/conductor_cooldown.go:1237` 把请求故障标记为 `request_scoped`；
- `shouldSkipCredentialCooldown` 据此跳过冷却。

### 5.3 边界判据

- 按字节而不是字符：一个汉字 UTF-8 占 3 字节，按 rune 计数会把
  20000 字的中文（约 60KB）判成安全；
- 上限取 65535（含）；65536 起拒绝；
- 错误文案同时给出实际字节与上限，让用户知道要删多少。
