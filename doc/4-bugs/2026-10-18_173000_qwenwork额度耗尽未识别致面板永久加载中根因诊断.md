# qwenwork 额度耗尽未被识别致面板永久「加载中」且耗尽账号继续路由根因诊断

- 日期：2026-10-18
- 状态：已修复（qwenwork-provider 0.2.7）
- 影响版本：qwenwork-provider 0.1.0 ~ 0.2.6（全生命周期）
- 发现渠道：用户提供生产面板截图，指出「qwenwork 插件没有 0 积分耗尽的功能，参考 workbuddy」

## 1. 现象

生产面板 `QwenWork 账号面板` 三个账号中，第一个账号 `u9c993791` 的「可用积分」区域**永久显示转圈 + 「加载中…」**，且该账号没有任何耗尽徽标；顶部「0积分」筛选计数为 `0`。

同时用户提出诉求：qwenwork 缺少 workbuddy 那样的「0 积分耗尽」能力。

## 2. 根因

### 2.1 直接原因：上游 `quota.exceeded` 未映射进额度快照

生产直连该账号上游实测：

```json
// GET /api/v1/adapter/user/account-context
{"code":"ok","data":{"plan":{"name":"个人免费版"},"quota":{"total":null,"used":null,"remaining":0,"exceeded":true}}}

// GET /api/v1/adapter/user/wallets
{"code":"ok","data":{"daily_credits":{"total_balance":0},"monthly_credits":{"total_balance":0},
 "longterm_credits":{"total_balance":0},"expiring_soon":{"count":0,"total_balance":0}}}
```

`fetchUserResource` 只把 `quota.remaining` 用于「钱包全为 0 时的回落」，`quota.exceeded` 仅被用来把 `TotalRemain` 归零，**没有写进快照**。结果快照三项数值全为 `0`、`packages` 为空。

`isCreditsExhausted` 的判据是「有消耗或额度池信号且剩余为 0」：

```go
if cr.TotalUsed > 0 || cr.TotalSize > 0 { return true }
return len(cr.Packages) > 0
```

免费版账号没有额度包，`total_used/total_size` 恒为 0 ⇒ **确定耗尽被降级成「数据未知」** ⇒ 面板 `exhausted=false` ⇒ 既不显示徽标，进度条也走「加载中…」分支。

### 2.2 更深一层：「0 积分仍可用免费模型」前提不成立

插件全链路按「免费模型不消耗积分」设计，共四处体现：

| 位置 | 原表述 |
|---|---|
| `lifecycle.go:2` | 0 积分不自动禁用：免费模型仍可用 |
| `active_auth.go:113` | 0 积分账号仍视为可路由 |
| `policy.go:132` | 0 积分不等于不可用：免费模型不消耗积分 |
| `panel.html:215` | 0 积分仍可用免费模型 |

生产用该 0 积分账号签发 MaaS 会话后实测：

| 模型 | 结果 |
|---|---|
| `qwen3.8-max-preview` | **429** `{"error":{"code":"balance_insufficient","type":"insufficient_quota"}}` |
| `qwen3.8-flash` | **429** 同上 |
| `qwen3.8-plus` | **429** 同上 |
| `glm-5.2` | **429** 同上 |

**QwenWork 没有免费模型**。0 积分账号只会稳定返回 429，继续参与路由只会浪费换号预算并污染 failover 计数。

## 3. 修复

### 3.1 信号层：快照携带 `exceeded`

`creditsSummary` 新增 `Exceeded` 字段；额度解析从 `fetchUserResource` 抽成纯函数 `buildCreditsSummary(ctxRaw, walRaw, ctxOK, walOK)`，把 `quota.exceeded` 写入快照。

`isCreditsExhausted` 调整判据顺序：先看 `TotalRemain > 0`（余额优先，防陈旧标记），再看 `Exceeded`，最后才用数值推断。

### 3.2 路由层：耗尽账号不承接流量

新增 `isCreditsLowOrExhausted`（= 耗尽 || 低于安全红线），四处统一改用：

- `scheduler.go` 调度候选过滤
- `scheduler.go` 的 `cachedCreditsScore` 返回值
- `active_auth.go` 的 `accountRoutable`
- `failover_retry.go` 换号候选过滤

### 3.3 生命周期：耗尽自动禁用（对齐 workbuddy）

新增 `disableAuth`：

- 启用态 + 耗尽 → 写 `disabled:true` + `exhausted_disable:true`（**可自动恢复**）
- 已有 `manual_disable` → 保留用户意图，不加 `exhausted_disable`
- 已有 `exhausted_disable` → 标记继续保留，恢复能力保持武装
- 无标记的禁用（宿主 UI 切换）→ 保持原状

`reconcileOneAccount`：启用态判定耗尽即调用 `disableAuth`；禁用态仅当 `isCreditsExhausted` 为 false 才重新启用。

`lifecycle_auto` 开关语义保留：**写 disabled 需要开启**；路由排除与面板展示无条件生效。

### 3.4 面板：耗尽不再转圈

新增 `isAccountExhausted(a)` 作为唯一判定入口（`a.exhausted` → `cr.exceeded` → 数值推断），`card()` / 筛选 / 计数 / 汇总卡全部改用它。

进度条新增耗尽分支：显示「已耗尽 · 余0」+ 红色满格 + 「充值或领取额度后自动恢复」，不再落到「加载中…」。

## 4. 验证

### 4.1 单测与变异反证

cgo-shim build/vet/test 全绿。变异反证三组：

| 变异 | 结果 |
|---|---|
| `isCreditsLowForRouting` 恢复旧「0 积分可路由」 | `TestExhaustedCreditsAreNotRoutable` + `TestExceededFlagMarksExhausted` FAIL |
| `accountRoutable` 跳过额度判定 | `TestPickSessionAuth_LowCreditAccountReassigns` + `TestPickSessionAuth_ExhaustedAccountReassigns` FAIL |
| `buildCreditsSummary` 不写 `Exceeded` | `TestBuildCreditsSummary_ExceededFlowsIntoSnapshot` FAIL |

第三组变异**首次执行时未被捕获**（当时测试只覆盖 `isCreditsExhausted` 纯函数），据此把解析逻辑抽成 `buildCreditsSummary` 并补 `billing_exceeded_test.go`，变异才命中——与 0.2.6 的 `mintPayload` 是同一类陷阱：只测纯函数不覆盖接线时，保护是假阳性的。

### 4.2 新增/调整用例

| 文件 | 用例 |
|---|---|

## 5. 教训

1. **「数值为 0」不等于「耗尽」**：免费档账号没有额度包时，`total_used/total_size` 恒为 0，与「取数失败」在数值层面完全一样。必须依赖上游的显式状态位（`quota.exceeded`），不能只靠数值推断。
2. **产品前提要实测**：四处代码 + 面板文案共同依赖「0 积分仍可用免费模型」，但这个前提从未被验证。一次 4 模型的实测就推翻了它。
3. **同一陷阱重复出现**：0.2.6 是「只测 `maasSessionID` 不测 `mintPayload`」，本次是「只测 `isCreditsExhausted` 不测 `buildCreditsSummary`」。凡是「纯函数 + 调用方」的结构，测试必须覆盖调用方实际组装的产物。
4. **面板「加载中」是危险占位**：它把「确定状态」和「未知状态」混在一个分支里，导致真实耗尽长期不可见。显式状态优先于占位。
