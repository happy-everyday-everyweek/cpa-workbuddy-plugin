# 发布构建体积过大根因诊断

- 日期：2026-10-18
- 类型：只读诊断（未改动任何构建配置、源码与发布产物）
- 触发：用户「检查一下我们发布构建太大的问题」
- 结论级别：根因已定位，并给出按收益/成本排序的优化选项

---

## 1. 结论摘要

**发布体积并不「过大」，它基本等于 Go 语言 `c-shared` 插件的体积地板。** 单插件单平台产物 7.5–8.1MB（cursor 10.3MB）中：

| 组成 | 占 `.so` 体积 | 说明 |
|---|---|---|
| Go 运行时 + 标准库 | **约 93%** | 与业务代码量几乎无关 |
| 插件自身业务代码 | 约 4%（324KB） | 12 插件中最大者也仅此量级 |
| 嵌入静态资源（panel.html 等） | 约 1%（90KB） | 已随 zip 二次压缩，实际增量近零 |
| 第三方库 | **约 0.03%**（2KB 符号） | SDK 与依赖几乎不产生可测体积 |

关键实测对照（同一份 `workbuddy` 源码，linux/amd64，均带 `-s -w`）：

| 构建内容 | 体积 | 相对增量 |
|---|---|---|
| 裸 c-shared（仅 `import "C"`） | **1,353,536** | 地板 |
| + `net/http` + `crypto/tls` | **3,900,064** | +2.55MB |
| + `encoding/json` | 3,912,480 | +12KB |
| + `gopkg.in/yaml.v3` | 4,156,192 | +256KB |
| + `github.com/tidwall/gjson` | 4,433,888 | +521KB |
| 真实 workbuddy 插件 | **8,087,200** | — |

**因此：任何「把二进制压到 3MB」的期望都不现实**——仅 HTTP+TLS 就已是 3.9MB。真正可压缩的空间集中在 yaml（256KB）与 gjson（521KB）两处，合计约 0.78MB / 插件，约占 9.6%。

同时确认：**`-s -w` 已正确生效**，未 strip 时 11.19MB，strip 后 8.10MB（省 3.08MB / 27.5%）。发布链路在 strip 这一环没有浪费。

- **12 插件 linux/amd64 zip 合计 37.75MB**；全平台 72 个 artifact 合计 **212.11MB**。
- 平台间差异主要由指针宽度与压缩率决定：darwin_arm64 最小（约 2.78–3.47MB），linux_amd64 最大。
- zip 压缩率稳定在 37–43%，说明产物熵分布高度一致（同一套 Go 运行时）。

### 2.2 异常项：cursor 比其他插件大 27%

cursor 0.1.6 的 `.so` 为 10.26MB，比中位数（约 8.0MB）多 **2.2MB**。归因明确：

- `google.golang.org/protobuf` 相关符号合计 **1,031,082 字节**；
- 其中 cursor 自有 `cursorproto` 包 **452,447 字节**（含 68,621 字节 `agent.desc` 与 44,969 字节 `management.html` 两个嵌入资源）；
- protobuf 运行时会连带引入 `reflect`（161KB）、`math/big`（104KB）等重包。

这是**功能必需**（Connect-RPC 协议需要 protobuf 编解码），不是配置失误。

## 3. 体积构成拆解

### 3.1 ELF 节区（workbuddy-provider 0.16.7，linux/amd64）

| 节区 | 字节 | 占文件 | 性质 |
|---|---:|---:|---|
| `.text` | 3,384,700 | 41.9% | 代码 |
| `.gopclntab` | 2,545,509 | 31.5% | Go 行号/函数表（`-w` 不剥离） |
| `.data.rel.ro` | 765,512 | 9.5% | 类型信息、itab、字符串指针表 |
| `.rela.dyn` | 747,744 | 9.3% | 重定位表 |
| `.noptrdata` | 380,609 | 4.7% | 只读数据 |
| `.rodata` | 169,104 | 2.1% | 只读常量 |
| `.data` | 69,618 | 0.9% | 可写数据 |
| `.bss` / `.noptrbss` | 143,104 / **33,684,992** | **0** | NOBITS，不占文件 |

`.text + .gopclntab` 两项即占 **73.4%**，这是 Go 二进制的典型结构。

> **关于 33MB `.noptrbss`**：来自 Go 1.26 的 `crypto/internal/fips140/drbg.memory`（`entropy.ScratchBuffer`，32MiB）。Go 官方注释明确说明它「应落在 `.noptrbss`，首次使用时才由物理页支撑，不使用 FIPS 140-3 模块的程序不承担内存或初始化开销」。实测 `dlopen` 后 RSS 仅增加 **1.7MB**，**该 33MB 不占文件、不占常驻内存**，不是体积问题。

### 3.2 符号级归因（workbuddy，重建保留符号版）

按包聚合（已剔除 BSS 与 `drbg.memory`）：

| 类别 | 字节 | 占比 |
|---|---:|---:|
| 标准库（other-std） | 1,994,485 | 43.8% |
| crypto（含 tls/x509/fips140） | 994,044 | 21.8% |
| runtime | 731,523 | 16.1% |
| net（http/url/netip） | 420,244 | 9.2% |
| internal | 152,087 | 3.3% |
| vendor/golang.org/x（net+text） | 269,810 + 100,436 | 8.1% |
| **嵌入资源（`main..gobytes.1`）** | **89,806** | **2.0%** |
| typeinfo/itab | 47,753 | 1.0% |
| **第三方库（3rd-party）** | **2,121** | **0.05%** |
| **CLIProxyAPI SDK** | **162** | **0.004%** |
| **插件业务代码（`main.*`）** | **324,057** | **7.1%** |

> 注：上表分母为符号总和（约 4.55MB），小于文件 8.76MB，差额即 `.gopclntab`/`.rela.dyn`/`.symtab` 等非符号结构。

**核心事实：插件业务代码只占 7%，第三方依赖占比不到 0.1%。体积由「用了 Go + HTTP/TLS」这一事实决定，不由「写了多少业务」决定。**

### 3.3 依赖的边际成本实测

以「裸 c-shared + net/http + crypto/tls」为基线（3,900,064）：

| 依赖 | 加入后 | 增量 | 备注 |
|---|---:|---:|---|
| `encoding/json` | 3,912,480 | +12KB | 已被 SDK 带入 |
| `regexp` | 3,904,192 | +4KB | 已被 net/http 带入 |
| `compress/gzip` | 3,900,064 | 0 | net/http 已含 |
| `net/http/cookiejar` | 3,908,256 | +8KB | |
| `gopkg.in/yaml.v3` | 4,156,192 | **+256KB** | 真实增量 |
| `github.com/tidwall/gjson` | 4,433,888 | **+521KB** | 真实增量（在已有 json 基础上 +521KB） |
| `go.etcd.io/bbolt` | 3,909,152 | +9KB | |
| `google.golang.org/protobuf/proto` | 3,987,808 | +88KB | 仅 proto 核心，不含 descriptor 反射 |

`gjson` 的 521KB 中，符号级新增仅 259KB，其余来自 `.gopclntab`（函数表）与 `.rela.dyn`（重定位）的配套增长。gjson 真正贵的不是它自己（`gjson.parseArray` 7.2KB、`gjson.Get` 4.2KB），而是它连带的 `encoding/json`（79.7KB 新符号）、`reflect`（26.8KB）、`time`（22.6KB）、`slices`（12.7KB）。

### 3.4 strip 与压缩实测

| 配置 | 体积 | 结论 |
|---|---:|---|
| 不 strip | 11,187,344 | |
| `-w`（去 DWARF） | 8,765,560 | 省 2.42MB |
| `-s -w`（去 DWARF + 符号表） | **8,099,584** | 再省 0.67MB，**CI 当前配置** |
| `-s -w` + `-gcflags=all=-l`（禁内联） | 7,592,224 | 省 0.51MB，但会损害性能，不建议 |
| zip level=1 | 3,493,730 | |
| zip level=6 | 3,190,092 | **CI 当前（Go 默认）** |
| zip level=9 | 3,173,494 | 仅省 16.6KB（0.5%） |

**zip 压缩级别从 6 提到 9 收益不足 1%，不值得改。**

### 3.5 嵌入资源压缩：无效优化（已实测证伪）

直觉上「panel.html 先 gzip 再 embed」能省 70%，但实测：

| 方式 | `.so` | zip |
|---|---:|---:|
| 原始 `panel.html`（83,870B） | 3,996,416 | 1,643,115 |
| 预压缩 `panel.html.gz`（25,370B） | 3,938,080 | 1,642,238 |

`.so` 省 58KB，但 **zip 只省 877 字节**——因为 zip 本身已对二进制做 Deflate，预压缩的数据是「已压缩数据再被压缩」，熵无法再降。**发布链路下这个优化无意义**，只在「直接分发裸 `.so`」时才有效。

## 4. 根因归纳

| # | 根因 | 性质 | 证据 |
|---|---|---|---|
| R1 | **Go `c-shared` 的固定运行时成本**：runtime + net/http + crypto/tls + 反射/类型系统 | 语言固有，不可消除 | 裸 c-shared 1.35MB；+HTTP/TLS 即 3.90MB；真实插件 93% 是运行时与标准库 |
| R2 | **`.gopclntab` 占 31.5%**，`-w` 与 `-s` 都不剥离它 | Go 设计，不可关闭（关了会失去 panic 栈与 profiling） | 2,545,509 字节；`-s -w` 后仍存在 |
| R3 | **cgo 引入 `.rela.dyn` 重定位表 9.3%** | `buildmode=c-shared` 固有 | 747,744 字节 |
| R4 | **yaml.v3 与 gjson 是可选重依赖**，合计约 0.78MB / 插件 | **可优化** | 边际成本实测 256KB / 521KB |
| R5 | **cursor 的 protobuf 栈额外 +1.03MB** | 功能必需 | protobuf 符号 1,031,082 字节 |
| R6 | 嵌入资源（panel.html 等） | **不是问题** | 仅 90KB，且 zip 后增量近零 |

**不存在「配置写错导致体积翻倍」这类缺陷**：`-trimpath`、`-s -w`、`buildmode=c-shared` 全部按预期生效；zip 只含单个二进制，没有误打包 `.h`、测试数据或调试文件；12 插件体积高度一致，反证没有单点膨胀。

## 5. 优化选项（按收益/成本排序）

### 选项 A：把 yaml.v3 换成轻量解析（收益 ~256KB/插件，中成本）

**现状**：workbuddy、qoderwork、traework、workbuddy-ai、cursor、qoder-ai、qwenwork 均**不使用** yaml；zcode、copilot、doubao、coze、token-usage-tracker 各用 1 处，且都只做 `yaml.Unmarshal(req.ConfigYAML, &decoded)`。

**可行路径**：宿主传入的 `ConfigYAML` 是简单键值结构，可改为 `encoding/json`（宿主 RPC 本身走 JSON）或手写 30 行键值解析器。**但需逐插件验证配置兼容性**（YAML 支持嵌套、多行字符串、锚点等，手写解析器有语义缺口风险）。

**收益**：5 个插件各 −256KB（约 −3.2%）。**风险**：中。建议作为独立小周期推进，先做 1 个插件验证。

### 选项 B：把 gjson 换成 encoding/json（收益 ~521KB/插件，中高成本）

**现状**：zcode（4 文件）、copilot（5 文件）、doubao（1 文件）、coze（1 文件）使用 gjson 做路径查询。

**可行路径**：gjson 的核心优势是「不定义 struct 直接取嵌套字段」。替换为 `encoding/json` + `map[string]any` 或定义 struct，代码量会上升，且 `map` 路径的性能通常更差。

**收益**：4 个插件各 −521KB（约 −6.4%）。**风险**：中高（涉及流式热路径解析，需逐处回归）。**除非有明确体积指标要求，否则不建议**——省 0.5MB 换解析逻辑重写不划算。

### 选项 C：接受现状，不做二进制优化（推荐）

**理由**：

1. **绝对体积不大**：单插件 zip 3.2MB，一次安装下载 3.2MB；全平台 212MB 托管在 GitHub Release（不占仓库）。
2. **可压缩空间有限**：A+B 全做完最多省 0.78MB/插件（约 9.6%），且只影响部分插件。
3. **风险收益比差**：省 9.6% 要动配置解析与流式解析两条核心链路。
4. **横向对比正常**：Go c-shared 插件普遍 5–10MB；本仓库 7.5–8.1MB 处于该区间中部。

**若确有「减小下载体积」的诉求，真正有效的方向是减少平台数**，而非压单文件：

| 方案 | 单次发布总量 | 相对现状 |
|---|---:|---:|
| 现状（6 平台） | 212.11MB | — |
| 去掉 windows_arm64 | 176.76MB | −16.7% |
| 只留 linux_amd64 + darwin_arm64 | 70.52MB | −66.7% |

### 选项 D：`-gcflags=all=-l` 禁内联（收益 0.51MB，不推荐）

省 6.3%，但会显著损害运行时性能（内联是 Go 最重要的优化之一），**不建议**。

## 6. 未验证与边界

- **生产容器内存**：SSH 探测被拒（`Connection closed`），未取得 9 插件同时加载的 RSS 实测值。按 1.7MB/插件估算，插件本身约 15–20MB，相对 CPA 整体可忽略。
- **跨平台体积归因**：仅对 linux/amd64 做了节区与符号级分析；darwin/windows 产物体积规律一致（同源、同参数），但未逐平台验证节区构成。
- **cursor 的 protobuf 可裁剪性**：未验证能否用 `protoc --go_opt=paths=source_relative` + 精简 descriptor 减小体积（Connect-RPC 通常需要完整 descriptor）。
- **yaml/gjson 替换的真实工作量**：未逐文件评估，选项 A/B 的成本为量级估计。

---

## 7. 建议

**默认建议：选项 C（接受现状）**。当前体积是 Go c-shared 的合理值，不存在需要紧急修复的缺陷。

若用户明确要求减小体积，建议优先级：

1. **先砍平台**（选项 C 后半）：收益最大、风险最低、零代码改动；
2. **再做选项 A（yaml）**：收益 256KB/插件，风险可控，可先单插件试点；
3. **选项 B（gjson）暂缓**：收益 521KB 但要重写流式解析，不划算。
