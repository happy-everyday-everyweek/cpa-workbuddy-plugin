# 生产 CPA 管理面板「404 未找到 v8 Management API」根因诊断

- 记录时间：2026-10-11 17:20 (GMT+8)
- 生产入口：`https://cpa.luode.vip`（服务器 45.207.222.65:18998）
- 容器：`cli-proxy-api`（镜像 `luode0320/cli-proxy-api:latest`，host 网络）
- 现象：管理面板登录报 `HTTP 404: 未找到 v8 Management API，请检查服务地址并将 CLIProxyAPI 升级至 v8 或更高版本；不再支持 v0 接口。`；重启容器后外网变为 `502 Bad Gateway`，面板彻底打不开。
- 定性：**配置数据损坏事故（非插件代码缺陷、非插件更新导致）**

---

## 一、根因（已实锤）

生产 CPA 的**生效配置文件内容被写成「转义格式」**：整个 YAML 文档塌缩成**单行**，全文 2412 个换行全部被替换成**字面两字符 `\n`**（反斜杠 + n），而不是真实换行符。

该内容在 MySQL 侧与本地 spool 文件侧完全一致：

- MySQL 表 `cli_proxy_api.config_store`，主键 `id='config'`
  - `char_length(content) = 70136`
  - 真实换行（LF）计数 = **1**
  - 字面 `\n` 转义对计数 = **2412**
  - `created_at = 2026-08-26 14:25:05`，**`updated_at = 2026-10-11 16:56:17`**
- 本地 spool 文件 `/CLIProxyAPI/mysqlstore/mysqlstore/config/config.yaml`（宿主机 `/usr/local/src/cli-proxy-api/mysqlstore/mysqlstore/config/config.yaml`）
  - 同样为单行转义内容，70136 字节

CPA 用 YAML 解析这段内容时，由于整份文档实际只有一行且以 `#` 开头，**整行被判为注释 → 解析结果为空配置**。

由此产生两个致命后果：

1. `remote-management.secret-key` 丢失 → 管理路由被禁用 → `/v0/management/*` 与 `/v8/management/*` **全部 404**
2. `port` 丢失 → 端口回退为 `0` → 启动时绑定随机端口

## 四、恢复方案

**关键利好**：MySQL 里的 content **内容本身是完整的 v8 配置**（含 `server.port: 8317`、`management.secret-key`、`plugins` 等），只是换行被转义。反转义即可恢复，无需重新手写配置。

### 方案 A（推荐）：反转义 DB 内容 + 重启

```sql
-- 1) 先备份（强烈建议）
CREATE TABLE cli_proxy_api.config_store_bak_20261011 AS
SELECT * FROM cli_proxy_api.config_store WHERE id='config';

-- 2) 把字面 \n 还原为真实换行
UPDATE cli_proxy_api.config_store
SET content = REPLACE(content, '\\n', '\n')
WHERE id = 'config';

-- 3) 校验：真实换行数应≈2412，转义对≈0
SELECT (char_length(content)-char_length(replace(content,char(10),''))) AS lf_count,
       (char_length(content)-char_length(replace(content,'\\n','')))     AS esc_n_pairs
FROM cli_proxy_api.config_store WHERE id='config';
```

```bash
# 4) 重启容器让 syncConfigFromDatabase 把修好的内容写回 spool 文件
docker restart cli-proxy-api

# 5) 验证：应打印 :8317，且管理接口返回 401/200 而非 404
docker logs --tail 30 cli-proxy-api | grep "started successfully"
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8317/v8/management/config
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8317/v0/management/config
```

### 方案 B（兜底）：用正确 v8 配置整体覆盖

若反转义后仍有字段异常，可基于容器内 `/CLIProxyAPI/config.example.yaml`（v8 布局模板）+ 现有凭据，生成一份正确配置整体覆盖 `config_store`，再重启。

- 确认 `/v1/responses` 等业务链路正常（本次故障期间业务流量未中断，仅管理面受损）。

## 五、后续建议

1. **定位 16:56:16 的写入源**：排查 16:51–16:56 之间其他会话/自动化脚本对生产服务器做了什么（尤其是否有人从 MySQL 导出 content 后又写回文件）。这是防复发的关键。
2. **配置写入防呆**：任何对 `config_store.content` 或 spool `config.yaml` 的写操作，都应走 CPA 管理 API（`PUT /v8/management/config`）而不是直接改文件/改库，避免再次引入转义或布局错误。
3. **端口显式固定**：`server.port` 建议保持显式 8317，避免一旦配置解析异常时端口静默漂移到随机值，导致 nginx 502 掩盖真实故障。
4. **管理面板自动更新**：如需固定前端版本，可设置 `management.disable-auto-update-panel: true`（本次前端升级到 v1.26.1 本身无害，但可减少变量）。
5. **配置备份**：给 `config_store` 加定期快照（本次若没有「内容本身完整」这一巧合，恢复代价会高得多）。
