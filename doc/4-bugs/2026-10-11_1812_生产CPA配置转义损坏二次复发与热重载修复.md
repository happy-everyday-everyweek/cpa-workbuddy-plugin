## 三、写入源确认手段（可复用）

1. `who` / `w` / `last -n 12`：本次看到 `root pts/0 183.239.175.194` **18:07 登录且仍在线**，正在 `docker logs -fn111 <容器>`（另一会话也在排查同一问题）；登录史中 16:57–17:26 一段横跨首次故障与修复。
2. `docker events --since/--until`：抓到 18:06:29 的 `exec: mysql ... select content from config_store`（非交互式 SSH 命令不留 `last` 记录，只能靠 events 抓）。
3. **指纹比对**：spool 与 DB `md5` 相同 → 证明 CPA 原样搬运；写入源不在容器内（events 无对应写操作），而在宿主机侧/外部会话。
4. **时间顺序**：文件先变（.390）、DB 后变（.654）→ 外部先写 spool，CPA watcher 重载后再同步回 DB。

## 四、修复（热重载法，业务零中断）

首次事故用了「改 DB + 重启容器」；本次端口未漂移，改用**热重载**，避免 60–80 秒重启中断：

1. 回滚点：`cp -a spool /root/config.yaml.broken.20261011_1812`；`CREATE TABLE config_store_bak_20261011_1812 AS SELECT * FROM config_store;`
2. 反转义：70196 字节 → **68990 字节 / 1207 换行**（较首次 68930 多 60 字节，即 zcode 0.1.3 新增配置），关键字段 `port: 8317`、`secret-key`、`plugins:`、`zcode-provider`、`allow-remote` 全在；preview md5 `6811a3768847e55745968510da4d9a56`。
3. **双写**：hex 写回 DB（`CONVERT(UNHEX('<hex>') USING utf8mb4)`）+ `cp preview → spool 文件`。
4. 等待 file watcher 热重载（约数秒）。
5. 验证：
   - 日志：`config successfully reloaded` → `remote-management.secret-key: created` → **`management routes enabled after secret key update`**
   - 本地与外网 `/management.html` **200**、`/v0|/v8/management/config` **401**
   - 端口仍 `*:8317`，容器 **未重启**（`Up` 时长连续）。

**回滚**：`UPDATE config_store SET content=(SELECT content FROM config_store_bak_20261011_1812 WHERE id='config') WHERE id='config';` 再写回 spool 或重启。

## 五、结论与防复发

- **这不是 CPA 的 bug，也不是插件代码问题**：CPA 只是「原样搬运 content 到 spool 再解析」；写坏的是外部会话的写入方式。
- **根因是行为层的**：外部会话反复用「读 content → 二次序列化 → 写回」改配置。**只要该写入方式不停止，故障会反复发生**（已连续两次）。
- **必须做**：
  1. 立即让该外部会话**停止直接读写生产 `config_store` / spool**；配置改动走管理 API `PUT /v8/management/config`。
  2. 改配置前先 `w` / `docker events` 确认无其他会话在操作同一份配置。
  3. 建议加**配置健康巡检**（检测 `content` 真实换行数是否为 1、`md5(content)` 是否等于 spool md5），异常即告警/自动反转义。
