# coze 请求体优先取原始体致 Responses 入口必然 503 根因诊断

- 时间：2026-10-18 22:00
- 版本：coze-provider 0.3.5 → 0.3.6
- 环境：生产（cpa.luode.vip，容器 `cli-proxy-api`）

## 1. 现象

用户在 CPA 管理台为 coze-provider 配置模型别名（`coze/doubao-seed-2-0-lite-260215`
→ `doubao-seed-2-0-lite`）后，经 new-api 转发调用持续失败。new-api 通用日志
每条记录都显示：

```
status_code=503, auth_unavailable: no auth available
(providers=coze-provider, model=doubao-seed-2-0-lite;
 last upstream error: 请求缺少 messages)
```

表现为「别名配置不生效」，但报错内容与别名无关。

## 2. 取证

### 2.1 三个对照实验（生产 CPA 直连）

| # | 入口 | 模型名 | 结果 |
|---|---|---|---|
| A | `/v1/chat/completions` | 别名 `doubao-seed-2-0-lite` | **200**，正文 `A` |
| B | `/v1/responses` | 别名 `doubao-seed-2-0-lite` | **500**，`请求缺少 messages` |
| C | `/v1/chat/completions` | 原名 `coze/doubao-seed-2-0-lite-260215` | **503**，`last upstream error: 请求缺少 messages` |

结论：**别名映射本身正常**（A 成功）。真正的分界是入口协议——凡经过
`/v1/responses` 的请求必然失败。C 的 503 是 B 的后果：宿主在模型执行失败后
把该账号标记为不可用，导致随后正常的 chat 请求也被拒。

### 2.2 源码定位

报错文案来自插件入口：`coze/convert.go:106`（`buildClawPrompt` 的
`len(messages)==0` 分支）。调用链：

```
handleExecStream / handleExecExecute
  → parseChatRequest(executorRequestBody(req.ExecutorRequest))
  → buildClawPrompt(chatReq.Messages)   ← 此处报错
```

`executorRequestBody` 旧实现（`coze/executor.go:659`）：

```go
if len(req.OriginalRequest) > 0 {
    return req.OriginalRequest
}
return req.Payload
```

而宿主侧（`internal/pluginhost/adapters_executors.go:835`）对两个字段的定义是：

- `OriginalRequest` = `opts.OriginalRequest`，**客户端原始请求体，未翻译**；
- `Payload` = `req.Payload`，**经协议翻译后的目标格式请求体**。

宿主只在 `prepareExecutorCall` 里翻译 `Payload`
（`adapters_executors.go:411`）。插件声明 `executor_input_formats=["openai"]`，
因此 `Payload` 恒为 OpenAI chat 形态；而 `/v1/responses` 的 `OriginalRequest`
里只有 `input` 字段，没有 `messages`。

**根因**：取值优先级与宿主语义相反。插件拿到了未翻译的原始体，在
Responses 入口解析必然得到空的 `messages`。

### 2.3 兄弟插件对照

`doubao/executor.go:64` 的策略是 `Payload` 优先、为空才回退 `OriginalRequest`，
与宿主契约一致。coze 的实现与之相反，属独立引入的偏差。

### 2.4 为什么错误会被放大成 503

插件返回的是普通 error（非结构化账号故障），宿主把它归入上游执行失败，
按账号级故障处理并把该账号标记为不可用；后续请求在选号阶段就直接
`auth_unavailable`，错误信息里带上了上一次的上游错误。因此一次协议层
解析失败会污染整个账号的可用性。

## 3. 修复

```go
func executorRequestBody(req pluginapi.ExecutorRequest) []byte {
    if len(req.Payload) > 0 {
        return req.Payload
    }
    return req.OriginalRequest
}
```

保留回退分支：宿主若未提供 `Payload`（极少数同步或中间件路径），仍可用原始体。

## 5. 遗留

- 本次修复解决的是 **CPA → coze** 段。new-api 侧仍需要在渠道 4「混合」的
  模型清单里登记 `doubao-seed-2-0-lite`（或对应别名），否则 new-api 不会
  把该模型的请求转发到 CPA。此前一次核查确认该渠道 `models` 字段无 coze 条目。
- `/v1/responses` 的流式响应由宿主做协议回译（插件只输出 OpenAI chat chunk），
  本次验收已覆盖流式场景。
