# 项目磁盘占用过大根因诊断

- 日期：2026-10-18
- 类型：只读诊断（未执行任何删除、gc、repack 或历史重写）
- 触发：用户「我们这个项目占用磁盘空间这么大的问题主要是什么」
- 结论级别：根因已定量确认

---

## 1. 结论摘要

**项目总占用约 7.24GB，其中 `.git` 占 6.8GB（94%），工作树只有 443MB。**

而 `.git` 的 6.8GB 里，**6.70GB（97%）是历史提交中的 `release-assets/` 二进制产物**——即历次发布把 `.so` / `.dylib` / `.dll` 压缩包直接提交进 Git 后留下的永久历史。

| 层级 | 体积 | 占项目总量 |
|---|---:|---:|
| `.git/objects/pack`（4 个 pack） | 4.20 GB | 58.0% |
| `.git/objects/??`（5018 个松散对象） | 2.64 GB | 36.5% |
| 工作树（不含 `.git`） | 443 MB | 6.1% |
| **合计** | **约 7.24 GB** | 100% |

工作树 443MB 中，`release-assets/` 本地缓存 282MB、`Python/` 136MB，真正的源码与文档不到 20MB。

**关键判断：这不是「代码变大了」，而是「二进制资产曾经入仓」造成的 Git 历史永久膨胀。** 该问题已于 2026-10-18 在「发布链路提速」中从**当前跟踪**里移除（`release-assets/` 已进 `.gitignore`），但**历史对象仍在**，所以磁盘占用不会自动下降。

---

## 2. 定量证据

### 2.1 历史 blob 构成（`git rev-list --objects --all` 全量枚举）

| 类别 | 体积 | 占历史 blob |
|---|---:|---:|
| `release-assets/` | **6.70 GB** | **97.0%** |
| 其他 >1MB 二进制 | 131.3 MB | 1.9% |
| 其余源码 / 文档 | 81.0 MB | 1.2% |
| **合计** | **6.91 GB**（7176 个 blob） | 100% |

> 6.91GB 是解压后 blob 的原始大小；pack 内 delta 压缩后实际占 4.20GB。

| 插件 | 历史 blob 体积 | 对象数 |
|---|---:|---:|
| traework-provider | 1636.5 MB | 657 |
| workbuddy-provider | 1432.3 MB | 569 |
| qoderwork-provider | 943.7 MB | 377 |
| zcode-provider | 628.3 MB | 249 |
| qoder-ai-provider | 509.8 MB | 201 |
| workbuddy-ai-provider | 362.9 MB | 145 |
| workbuddy-token-usage | 251.4 MB | 97 |

**成因**：每次发布 6 平台 × 约 3.2MB = 约 19MB，历史上共 338 个与 `release-assets/` 相关的提交。累计 12+ 插件、数百次版本迭代后，滚成 6.7GB。

### 2.3 pack 无法再压缩

| pack | 对象数 | delta 对象 | pack 体积 | 原始体积 | 压缩率 |
|---|---:|---:|---:|---:|---:|
| pack-b04b7db0… | 5326 | 2783 | 3.05 GB | 3.09 GB | 98.7% |
| pack-4e972722… | 1023 | 418 | 751 MB | 754 MB | 99.5% |
| pack-6b9ccdd6… | 865 | 316 | 330 MB | 332 MB | 99.1% |
| pack-3f29f2c8… | 3 | 0 | 21 KB | 66 KB | 31.6% |

**压缩率约 99%**：因为内容是已 Deflate 压缩的 zip，Git 的 zlib/delta 对它几乎无效。**再执行 `git gc` / `git repack -adf` 也不会明显变小**——这是二进制入仓的典型特征。

### 2.4 工作树 443MB 构成

| 目录 | 体积 | 说明 |
|---|---:|---|
| `release-assets/` | 282 MB | **本地缓存，可随时删除**（GitHub Release 才是权威源） |
| `Python/` | 136 MB | 便携 Python 运行时（`pythoncore-3.15-64`），非项目产物 |
| `doc/` | 3.0 MB | 文档 |
| 12 个插件源码目录 | 合计约 10 MB | 真正的业务代码 |
| `.codegraph/` | 9.2 MB | 代码索引缓存 |
| `assets/` | 1.1 MB | 图标资源 |
| 其余（skills/scripts/test 等） | 约 1 MB | |

### 2.5 本地磁盘现状

| 盘 | 已用 | 可用 |
|---|---:|---:|
| C | 188.7 GB | 17.4 GB |
| D | 41.8 GB | 36.6 GB |
| **F** | **20.9 GB** | **2.2 GB** |

F 盘仅剩 2.2GB，而 `.git` 占 6.8GB —— 这是此前 `git gc` 因磁盘不足失败（`Out of diskspace`）的直接原因。

## 3. 根因归纳

| # | 根因 | 性质 | 是否可修复 |
|---|---|---|---|
| R1 | **二进制产物曾提交进 Git**：`release-assets/` 下 2711 个 blob、6.70GB 永久留在历史里 | 历史事实 | 需历史重写才能回收 |
| R2 | **zip 内容不可再压缩**：pack 压缩率 99%，`gc`/`repack` 收益接近零 | 物理事实 | 无法通过常规整理解决 |
| R3 | **338 次资产提交 × 每次数十 MB** 的累积效应 | 流程问题 | 已于 2026-10-18 从跟踪中移除，不再新增 |
| R4 | 本地 `release-assets/` 缓存 282MB（含 4 个过期版本） | 可清理 | 可直接删除 |
| R5 | `Python/` 便携运行时 136MB 放在仓库目录内 | 布局问题 | 可移出 |
| R6 | `.git` 中 2.64GB 是松散对象，未打包 | 可整理 | 需 ≥5GB 可用空间 |

**不是根因的项**（已排除）：

- 不是源码膨胀：全部源码 + 文档仅约 20MB。
- 不是工作树异常：工作树 443MB 中 418MB 是可清理的缓存与运行时。
- 不是不可达对象堆积：`git fsck --unreachable` 仅列出少量提交与 blob，量级远小于 6.7GB。

---

## 4. 清理方案（按收益/风险排序）

### 方案 1：删除本地 `release-assets/` 缓存（收益 282MB，零风险，立即可做）

**依据**：`release-assets/` 已进 `.gitignore`，二进制权威源是 GitHub Release（`registry.json` 的 72 个 artifact URL 全部指向 `releases/download/...`）。本地缓存可随时重新下载。

**操作**：
```bash
rm -rf F:/cpa-plugin/release-assets
```

**风险**：无。下次发布时 `scripts/download-release-assets.py` 会重新拉取。

**顺带收益**：其中 4 个是过期版本目录（qoder-ai 0.1.24、qoderwork 0.9.44、workbuddy-ai 0.1.17、workbuddy 0.16.5），共约 72MB，本来就不该留。

---

### 方案 2：把 `Python/` 移出仓库目录（收益 136MB，低风险）

`Python/pythoncore-3.15-64` 是便携 Python 运行时，与项目代码无关，却放在仓库根目录下。

**操作**：移动到 `D:\tools\Python` 或类似位置，并更新引用路径（若有脚本硬编码）。

**风险**：低。需先 grep 确认无脚本依赖相对路径 `./Python`。

---

### 方案 3：历史重写移除 `release-assets/`（收益 4–6GB，高风险，需明确授权）

这是唯一能真正回收 `.git` 6.7GB 的手段，但代价明确：

| 维度 | 影响 |
|---|---|
| 方法 | `git filter-repo --path release-assets --invert-paths` |
| 影响范围 | 全部 1249 个提交被重写，所有 commit SHA 变更 |
| 协作者 | 所有本地副本必须重新 clone（4 个远端分支、349 个 tag 需同步重建） |
| 远端 | 必须 `git push --force`（历史上从未执行过，属破坏性操作） |
| 磁盘需求 | 重写过程需要约 7–10GB 临时空间；**F 盘当前仅剩 2.2GB，无法在本机完成** |
| 已有阻塞 | 存在 2 个孤儿 idx（`pack-1a7d77cb…`、`pack-eb775385…`）导致 `git fsck` 报 missing，重写前必须先处理 |

**结论：不建议现在做。** 前置条件不满足（磁盘不足 + pack 索引既有损坏），且该操作会重写全部历史、影响所有协作者与 349 个 tag。

**若确需执行，正确顺序**：
1. 先把仓库迁移到有 ≥15GB 空闲的盘（D 盘有 36.6GB）；
2. 处理 2 个孤儿 idx；
3. 用 `git filter-repo` 重写；
4. 本地验证 `git fsck` 无 missing、历史完整；
5. 与用户确认后，才 force push 并重建远端分支/tag。

---

### 方案 4：常规 `git gc --aggressive`（收益不确定，中风险，不推荐）

**为什么收益有限**：pack 压缩率已达 99%，`gc` 只能把 2.64GB 松散对象打回 pack，减少的是**松散对象重复存储**，不是 6.7GB 历史本身。

**为什么现在不能做**：F 盘仅剩 2.2GB，而 `git gc` 需要至少与现有对象库相当（约 5–7GB）的临时空间。此前已因此失败一次。

---

### 方案 5：只清理过期缓存版本（收益约 72MB，零风险）

如果暂时不想删全部 `release-assets/`，至少删掉这 4 个过期目录：

```
release-assets/qoder-ai-provider-0.1.24
release-assets/qoderwork-provider-0.9.44
release-assets/workbuddy-ai-provider-0.1.17
release-assets/workbuddy-provider-0.16.5
```

## 5. 已确认不会复发的部分

2026-10-18「发布链路提速」已完成的改动，从流程上根治了 R3：

- `release-assets/` 加入 `.gitignore`；
- 资产改为托管 GitHub Release；
- `registry.json` 的 72 个 artifact 全部指向 `releases/download/<id>-v<version>/<zip>`；
- 一次发布只产生 2 次推送（代码 + registry），不再有资产提交。

**这意味着历史不会再增长**，剩余问题只是「历史存量」与「本地缓存」。

## 6. 未验证与边界

- **历史重写的实际回收量**：按 `filter-repo` 通常能回收 95%+ 推算约 6.4GB，但未实跑（磁盘条件不满足）。
- **2 个孤儿 idx 的具体成因**：仅确认 `git fsck` 报 2 个 missing、`git cat-file` 仍可读出，未深入定位；这是重写前的必须先解决项。
- **`Python/` 是否有脚本硬编码依赖**：未逐脚本 grep 确认。
- **远端仓库体积**：未查询 GitHub 侧的仓库大小（`gh api repos/.../  | jq .size`），不影响本机结论。

**立即执行（零风险，回收 418MB）**：
1. 删除 `release-assets/`（282MB）
2. 把 `Python/` 移出仓库目录（136MB）

**暂不执行**：

## 8. 证据命令

```bash
du -sh .git                                   # 6.8G
du -sh --exclude=.git .                       # 443M
git rev-list --objects --all | wc -l          # 7176 个历史对象
git cat-file --batch-check=...                # 按 blob 聚合 → release-assets 6.70GB / 97.0%
git verify-pack -v <idx>                      # pack 压缩率 98.7%~99.5%
git fsck --unreachable                        # 仅少量不可达对象
git log --all --oneline -- "release-assets/*" | wc -l   # 338 个相关提交
git rev-list --all --count                    # 1249 个提交
git tag | wc -l                               # 349 个 tag
```
