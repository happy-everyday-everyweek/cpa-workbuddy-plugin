# Qoder 模型对外 ID 暴露内部代号致生产模型表与客户端不一致根因诊断

- 编号：BUG-QODER-MODELS-EXPOSE-INTERNAL-KEY-20261020
- 发现时间：2026-10-20（用户报「客户端看到这么多模型，我们 qoder 插件接口获取的一个都没有」）
- 判定时间：2026-10-20 22:10（北京时间）
- 状态：**已定位根因，修复已提交并进入发布链路（0.9.49 / 0.1.29）**
- 关联：
  - `doc/4-bugs/2026-10-20_021500_Qoder模型清单跨账号缓存污染根因诊断.md`（同链路上一层缺陷，0.9.48 / 0.1.28 修复）
  - `doc/4-bugs/2026-10-12_015500_Qoder模型发现接口COSY签名失效根因诊断.md`（0.9.47 / 0.1.27 修复）

## 1. 现象

生产 QoderWork / Qoder AI 插件在 CPA 模型表里暴露的模型名，与 Qoder 官方客户端下拉完全对不上：客户端显示 `Qwen3.8-Max`、`Qwen3.8-Flash`、`GLM-5.3` 等官方名，插件侧只有 `qmodel_38max`、`qfmodel`、`gmodel` 这类内部代号。

用户侧的直接感受是「客户端能看到很多模型，插件接口一个都没有」。

## 2. 证据链

### 2.1 动态发现本身没有失败

生产日志 `dynamic discovery ok: 14 models`（qoderwork）/ `15 models`（qoder-ai）持续正常，说明上游 `model/list` 调用与解析都是成功的。

把上游返回的 `chat` 场景与官方目录逐项比对后确认：**数量完全吻合**，qoderwork 的 14 个即官方 CN 全量；qoder-ai 的 15 个 = 国际版 17 个减去被 `enable=false` 过滤掉的 `smodel` / `cmodel`。

⇒ 缺陷不在「取不到」，而在「取到了之后怎么命名」。

### 2.2 上游只返回内部代号

`/algo/api/v2/model/list?Encode=1` 的响应形如：

```json
{"chat":[{"key":"qmodel_38max","display_name":"Qwen3.8-Max","enable":true,...}]}
```

`key` 是内部代号，`display_name` 才是官方名。插件原先把 `key` 直接当模型 ID 注册给宿主，把 `display_name` 塞进 `ModelInfo.Name`。

### 2.3 宿主的 `/v1/models` 只渲染 id

宿主渲染器 `internal/registry/model_registry.go:1654 convertModelToMap` 只输出 `id`、`object`、`owned_by`，以及可选的 `display_name` / `context_length` / `max_completion_tokens`。

插件的 `ModelInfo.Name` 字段**不在渲染范围内**，因此官方名在 `/v1/models` 上彻底丢失，只剩内部代号。

### 2.4 同名模型的 provider 归属

宿主模型注册表按 modelID 全局去重（`model_registry.go:671 addModelRegistration`，`existing.Info = cloneModelInfo(model)`，最后注册者覆盖元数据）。qoderwork 与 qoder-ai 共享 `qmodel_38max` 等 12 个内部代号，因此这 12 个模型在全局表里只出现一次，`owned_by` 归最后注册的 qoderwork，qoder-ai 只剩 3 个独有模型可见。

这是用户看到「qoder-ai 只有 3 个」的结构性原因，不是发现失败。

## 3. 方案取舍

### 3.1 provider 前缀方案被宿主硬阻断

用户最初选择「插件侧加 provider 前缀区分同名模型」，实测不可行：

```
POST /v1/chat/completions  {"model":"qoderwork-provider/Qwen3.8-Max"}
→ 400 {"error":{"message":"unknown provider for model qoderwork-provider/Qwen3.8-Max","code":"model_not_found"}}
```

根因：`internal/util/provider.go:46 GetProviderName` 只按完整模型名在注册表里反查，宿主在这条路径上**不解析 `provider/model` 形式**。带前缀的 ID 因此无法路由。

### 3.2 采纳方案：官方名作主 ID + 保留内部代号兼容条目

参照外部项目 `shuishuipingan/qoder2api-hub` 的做法（用官方 `display_name` 作为对外模型 id），插件侧新增 `exposeModelIDs`：

- **主条目**：`ID` 与 `DisplayName` 都是官方名（`Qwen3.8-Max`），客户端下拉直接可见；
- **兼容条目**：`ID` 是内部代号（`qmodel_38max`），保证旧调用方仍能反查到 provider。

兼容条目必须**真实注册**而非只做映射：宿主按完整模型名反查 provider（`GetProviderName`）与匹配账号（`conductor_selection.go:996 authSupportsRouteModel`），未注册的名字直接 400。

### 3.3 执行链必须同步回译

暴露官方名后，客户端会直接发 `Qwen3.8-Max`。执行链 `cpaToUpstreamKey` 必须能把它回译成上游 key，否则请求会**静默落到 `auto`**（上游对未知模型名的兜底行为），参数与计费全错且无报错。

排查发现两处缺口：

| 官方名 | 修复前 | 修复后 |
| --- | --- | --- |
| `Qwen3.7-Flash` | 无映射 → 透传 → 上游不识别 | `q37fmodel` |
| `GLM-5.2` | 错映射到 `gmodel`（实为 GLM-5.3） | `gm51model` |

qoder-ai 侧另有四个国际版档位缺失映射：`Ultimate`/`Performance`/`Efficient`/`Sonus`。

## 4. 修复内容

| 改动 | 文件 | 说明 |
| --- | --- | --- |
| 新增 `exposeModelIDs` | 两插件 `models.go` | 内部代号 → 官方名主条目 + 兼容代号条目；未知 ID 原样透传 |
| 静态表收敛 | 两插件 `models.go` | `wbModels()` 只存内部代号，避免「表内已含官方名 + 展开再加一份」重复 |
| 回译补齐 | 两插件 `body.go` / `models.go` | `Qwen3.7-Flash`、`GLM-5.2`；国际版四个档位 |
| 排除规则多形态 | 两插件 `models.go` | `filterExcludedModels` 按「完整 ID / 官方名 / 内部代号」任一命中即排除 |
| 面板下拉口径 | 两插件 `models.go` | `authModelsForIndex` 同样经 `exposeModelIDs`，与 `/v1/models` 一致 |

## 6. 残留边界

- qoderwork 与 qoder-ai 仍共享一个全局模型名空间，同名模型由宿主 `GetModelProviders` 返回多 provider 并按调用账号择路；这是宿主能力边界，非本插件可改。
- 生产 `model-alias` 中存在 `Qwen3.8-Max → qwen-3.8-max`（fork）条目，但 `fork` 语义是「别名作为额外模型加入列表，原 ID 保留」，反解方向为 `alias → name`，直接请求官方名不会被改写。发布后需以生产 `/v1/models` 实测确认。
