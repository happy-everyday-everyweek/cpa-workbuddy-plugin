# zcode GLM-5.3-Flash 每日额度耗尽导致全池 503

结论：**不是账号故障、不是插件缺陷、也不是上游故障**，而是 **GLM-5.3-Flash 这一个模型的「每日 500 万 token」额度已被打满**。生产全部 7 个 zcode 账号该模型均为 `used=5,000,000 / remain=0`，上游对每次请求稳定返回 `HTTP 200 + {"code":1005,"msg":"exceed quota limit"}`；宿主持续换号重试（每次轮完全部 9 个 auth 文件）后统一汇总为 `503 auth_unavailable`。同账号的 `GLM-5.3`（非 flash，额度 300 万）同期仅用 45 / 19 / 0，全部正常——这是**模型级配额**问题，与账号池健康无关。

## 一、问题现象

用户截图：new-api 通用日志 2026-10-15 01:44:51–01:45:01，全天 123 条，渠道 **#4 混合**，模型 `glm-5.3-flash`，流 `—`，Tokens `-`，费用 `$0`，耗时 1.0–4.0s，首字「不适用」，详情 `status_code=503, auth_unavai…`（截断）。

生产实测补全完整错误体：

```
status_code=503, auth_unavailable: no auth available
(providers=zcode-provider, model=glm-5.3-flash;
 last upstream error: empty_stream: upstream stream closed before first payload)
```

## 二、证据链

### 2.1 上游对 GLM-5.3-Flash 稳定返回 1005（逐账号实测）

绕过 CPA，用生产各账号 JWT 直连 `https://zcode.z.ai/api/v1/zcode-plan/anthropic/v1/messages`：

| 账号 | HTTP | 响应体 |
| --- | --- | --- |
| zcode-3f656fef06ccd323 | 200 | `{"code":1005,"msg":"exceed quota limit","logid":"…"}` |
| zcode-49b04c10caefdbca | 200 | 同上 |
| zcode-58bf43ba8d06d774 | 200 | 同上 |
| zcode-5f59450c99a565fb | 200 | 同上 |
| zcode-91fee13b3c26883a | 200 | 同上 |
| zcode-d7a0cb4afa8f77c0 | 200 | 同上 |
| zcode-fe1fe1bae6dc09c4 | 200 | 同上 |

**7/7 全部 1005**，耗时 0.14–0.22s（快速拒绝，非超时）。错误体为 **85 字节、非 SSE 的纯 JSON**，`Content-Type` 非 `text/event-stream`。

### 2.2 同一账号对照：GLM-5.3（非 flash）完全正常

同一账号 `zcode-3f656fef06ccd323`、同一时刻：

```
POST …/v1/messages  {"model":"GLM-5.3", …}
→ 200 {"id":"msg_20261015020910ba4dee…","type":"message","content":[{"type":"thinking",…}]}
```

即**鉴权、JWT、端点、指纹全部有效**，仅 `GLM-5.3-Flash` 这一个模型被拒 → 排除账号/鉴权/风控类原因。

### 2.3 额度真相：Flash 每日 500 万全部耗尽

用 `billing/balance`（0.1.30 起插件即以此端点取真实用量）逐账号拉取：

| 账号 | GLM-5.3 (3M/daily) | GLM-5.3-Flash (5M/daily) |
| --- | --- | --- |
| zcode-3f656fef06ccd323 | used 45 / remain 2,999,955 | **used 5,000,000 / remain 0** |
| zcode-5f59450c99a565fb | used 0 / remain 3,000,000 | **used 5,000,000 / remain 0** |
| zcode-d7a0cb4afa8f77c0 | used 19 / remain 2,999,981 | **used 5,000,000 / remain 0** |
| zcode-fe1fe1bae6dc09c4 | used 0 / remain 3,000,000 | **used 5,000,000 / remain 0** |

`billing/current` 下发的权益定义（`entitlements`）印证额度口径：

```
GLM-5.3       | cap model:glm-5.3       | grant 3,000,000 | period daily
GLM-5.3-Flash | cap model:glm-5.3-flash | grant 5,000,000 | period daily
```

**决定性对照**：同一账号 GLM-5.3 仅用 45/19/0，Flash 精确打满 5,000,000——这是**模型级每日配额耗尽**，不是账号级故障。

### 2.4 额度消耗速率：大上下文请求在约 1.7 小时内打满

new-api `logs` 表显示当日 Flash 的大请求特征：

| 时间 | prompt_tokens | completion_tokens |
| --- | --- | --- |
| 01:07:08 | 192,472 | 8,838 |
| 01:08:32 | 214,789 | 2,191 |

单次请求 prompt 即 19–21 万 token（`/v1/responses` 长上下文客户端）。按此量级，**约 25 次**即可吃掉 500 万日额。失败起点 `01:44:43` 距配额周期起点（当日 00:00）仅 104 分钟。

### 2.5 失败与成功的时间分界（new-api logs 表）

```
glm-5.3-flash  type=2(成功)  首 2026-10-14 09:59:57  末 2026-10-15 01:44:10  共 140
glm-5.3-flash  type=5(失败)  首 2026-10-15 01:44:43  末 2026-10-15 01:50:55  共  66
```

成功止于 `01:44:10`、失败起于 `01:44:43`，**33 秒内完成从「正常」到「全池拒绝」的切换**——典型的额度打满瞬变，而非账号逐个劣化。

### 2.6 CPA 侧 100% 同源

CPA 日志中 `empty_stream` 全量 64 次，聚合后 **64/64 全部为 `provider=zcode-provider model=GLM-5.3-Flash`**，零例外：

```
[2026-10-15 01:48:06] [warn] [conductor_execution.go:1968] upstream execution failed:
  provider=zcode-provider model=GLM-5.3-Flash auth_file=zcode-fe1fe1bae6dc09c4.json
  duration=2.025s err=empty_stream: upstream stream closed before first payload
```

同一秒内连续换 9 个 auth 文件（`3f656fef06ccd323` → `49b04c10caefdbca` → `58bf43ba8d06d774` → `5f59450c99a565fb` → `91fee13b3c26883a` → `d7a0cb4afa8f77c0` → `fe1fe1bae6dc09c4` → `1185ceb16c25ae48` → …），每个都是 1.7–3.4s 的 `empty_stream`，全轮失败后宿主编织为 `auth_unavailable`。

### 2.7 跨模型对照：glm-5.3 曾在 10-14 出现同类 223 次

| 模型 | 失败窗口 | 次数 | 错误分类 |
| --- | --- | --- | --- |
| glm-5.3 | 2026-10-14 10:54:49 – 11:56:36 | 223 | 214× `503 auth_unavailable` + 7× `429 code 3009` + 2× `405 code 3012` |
| glm-5.3-flash | 2026-10-15 01:44:43 – 01:50:55 | 66 | 60× `503 auth_unavailable` + 6× `500 empty_stream` |

同一机理（额度打满 → 全池拒绝）在 `glm-5.3` 上已于前一日发生过一次。用户只看到 flash，是因为在 new-api 日志页按 `model=glm-5.3-flash` 做了筛选。

## 三、根因

| 层 | 事实 | 归属 |
| --- | --- | --- |
| **直接原因** | `GLM-5.3-Flash` 每日 500 万 token 额度已在 2026-10-15 约 01:44 被全部耗尽（7/7 账号 `remain=0`），上游对每次请求返回 `200 + code 1005 exceed quota limit` | 上游额度事实（运营层） |
| **表现放大 1** | 宿主逐账号重试（每次轮完全池）后统一汇总为 `503 auth_unavailable`，用户看到的是"账号不可用"而非"配额耗尽"，**误导排查方向** | CPA 宿主 |
| **表现放大 2** | 上游 `200 + 非 SSE 错误体` 经 `/v1/responses` 转换路径无法解析出有效流事件，被记为 `empty_stream: upstream stream closed before first payload`，**掩盖真实错误码 1005** | CPA 宿主（responses 转换层） |
| **插件侧缺陷** | `handleExecStream` **仅按 HTTP 状态码判成败**（`executor.go:155` 的 `resp.StatusCode < 200 \|\| >= 300`），上游「200 + 错误码体」被判为成功流并进入 `pumpUpstreamStream`；该次调用在尾部以 `failed=false` 记入用量，且 `resetAccountFailover` 清掉冷却，**既不换号也不上报错误** | 本仓库 `zcode/executor.go` |
| **插件侧缺陷（次）** | `shouldRotateOnUpstreamErr`（`zcode/failover.go:74`）虽已含 `"quota"` 文本匹配，但该函数**只在非 2xx 分支被调用**，200+1005 永远走不到 | 本仓库 `zcode/failover.go` |

**核心判定**：即使插件正确识别 1005，结果也只是「快速返回配额错误」而非「推理成功」——**全部账号该模型额度均为 0，无号可换**。插件缺陷的作用是**掩盖错误码、误导排障方向**，不是造成失败的原因。

## 四、为什么不是其他原因

| 候选原因 | 排除依据 |
| --- | --- |
| 账号被禁用 / 冷却 | 同账号同分钟 `GLM-5.3` 请求成功（§2.2）；`billing/current` 全部 `status=active` |
| JWT / 鉴权失效 | 同 JWT 打 `GLM-5.3` 正常返回 200（§2.2） |
| 上游风控（3012） | 本次 64 次失败**零** 3012；`X-ZCode-App-Version: unknown` 保持放行值（`internal/mimic/fingerprint.go:42`） |
| 网络 / 超时 | 失败耗时 1.7–3.4s，上游本身 0.14–0.22s 返回（§2.1）；非 `Client.Timeout` 类 |
| 15 秒整体超时掐断 | 该缺陷已于 0.1.23/0.1.24 修复（见 `doc/4-bugs/2026-10-14_023000_*`），且本次错误文案是 `empty_stream` 而非 `context deadline exceeded` |
| new-api 性能监控 503（143 字节类） | 响应体 **262 字节**，非 143 字节类；且 new-api 侧日志有完整 `last upstream error` 透传 |

## 五、恢复方式

额度按 `period: daily` 重置，`billing/balance` 返回的周期边界：

```
period_start = 1791993600 → 2026-10-15 00:00:00 CST
period_end   = 1792079999 → 2026-10-15 23:59:59 CST
```

即 **2026-10-16 00:00:00（北京时间）自动恢复**，无需人工干预。但按 §2.4 的消耗速率（约 1.7 小时打满），若不改变用量结构，次日在相同时间点会再次耗尽。

## 六、修复建议（待确认后实施）

分两层，**均不改变"额度耗尽"这一上游事实**，只解决"错误被掩盖、方向被误导"：

1. **插件层（本仓库，建议做）**：`handleExecStream` 在 2xx 分支增加「响应体非 SSE 且含上游业务错误码」识别，命中 `code 1005/3006/3009/3012` 时按上游错误处理——透传真实错误码与文案（如"GLM-5.3-Flash 每日额度已用尽"）、计入 `noteAccountFailure`、按 `shouldRotateOnUpstreamErr` 语义决定是否换号。同时修正 `pumpUpstreamStream` 尾部对该类响应的 `failed=false` 误记。
2. **运营层（不在本仓库）**：
   - 提高 `GLM-5.3-Flash` 日额或改用额度更高的模型承接长上下文流量（单次 19–21 万 prompt 的客户端最易打满）；
   - 或在 new-api 侧对该模型配置额度预警，避免在用户侧表现为"账号故障"。

## 七、当前状态
