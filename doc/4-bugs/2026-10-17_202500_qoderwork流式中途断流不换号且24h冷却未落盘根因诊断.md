## 3. 根因

### 3.1 主根因：流式断流分支没有换号路径（实现缺陷）

`qoderwork/stream.go` 的 `pumpUpstreamStream` 在 SSE 扫描结束后按三类失败分别处理：

| 分支 | 代码位置 | 是否换号 |
|---|---|---|
| HTTP ≥400 | [qoderwork/stream.go:259](file:///f/cpa-plugin/qoderwork/stream.go#L259) | ✅ 满足 `isAccountLevel4xx` 且预算允许时换号 |
| HTTP 200 + SSE 业务错误帧 | [qoderwork/stream.go:348](file:///f/cpa-plugin/qoderwork/stream.go#L348) | ✅ `shouldRotateOnUpstreamErr` 命中且零泄漏时换号 |
| **扫描器读错误（断流）** | **[qoderwork/stream.go:330-335](file:///f/cpa-plugin/qoderwork/stream.go#L330-L335)** | ❌ **直接 `return`，无任何换号判定** |

断流分支原文：

```go
if err := scanner.Err(); err != nil {
    publishUsage(..., true, 0, err.Error(), ...)
    noteAccountFailure(curAuthID, 0, err.Error())
    streamEmitError(streamID, fmt.Sprintf("upstream stream read error: %v", err))
    return          // ← 直接收尾，未进入 pickNextAuth
}
```

同一缺陷在同步路径同样存在：[qoderwork/stream.go:515-517](file:///f/cpa-plugin/qoderwork/stream.go#L515-L517) 的 `collectUpstreamStreamQoder` 对 `scanner.Err()` 直接 `return chunks, 0, ...`，不换号。

**兄弟插件同源**：`workbuddy/stream.go:227-232`、`qoder-ai/stream.go:330-335` 逐字同构，同一缺陷在三插件共存（qoderwork 本次先暴露）。

### 3.2 该分支为何"不能简单换号"（关键约束）

断流分支与 4xx/错误帧分支的**本质差异**是：断流发生时 `emitted` 很可能已经是 `true`（本例 `ttft=6.58s` 证明首帧已下发）。

- 已泄漏内容后再换号重试，会把**第二个账号的完整回答拼接在已下发片段之后**，客户端收到语义错乱的双份输出。
- 这正是 200 错误帧分支设置 `if emitted || ...` 零泄漏守卫的原因（[qoderwork/stream.go:348](file:///f/cpa-plugin/qoderwork/stream.go#L348)）。
- 因此本缺陷**不是"漏了一个 if"**：断流在 `emitted=true` 时换号会引入新缺陷，正确修法必须区分"零泄漏断流"与"已泄漏断流"两种情况。

### 3.3 次生根因：24h 冷却 92 次触发却零落盘（独立缺陷）

生产日志近 6 小时：

```
92 条  [qoderwork] account qoderwork-<uid>.json triggered 24h daily cooling until 2026-10-18T...
```

分布：`01a03dc6` 36 次、`01a04386` 31 次、`01a06079` 18 次、`01a01535` 7 次。

但检查全部 11 个 qoderwork auth 文件：

```
qoderwork-01a01535-....json -      ← 无 daily_cooling_until
qoderwork-01a03dc6-....json -
...（11/11 全部无该字段）
```

**触发日志持续产出，持久化字段 100% 缺失**，两者不可能同时成立——说明 `triggerDailyCooldown` 在写完日志后、落盘环节失败，而调用方全部使用 `_ = triggerDailyCooldown(...)` 丢弃错误（[qoderwork/stream.go:244](file:///f/cpa-plugin/qoderwork/stream.go#L244)、[:341](file:///f/cpa-plugin/qoderwork/stream.go#L341)、[:451](file:///f/cpa-plugin/qoderwork/stream.go#L451)、[main.go:796](file:///f/cpa-plugin/qoderwork/main.go#L796)、[:817](file:///f/cpa-plugin/qoderwork/main.go#L817)），失败静默。

直接后果：**内存镜像只在进程内生效，进程重启或 watchdog `refreshDailyCoolingSetFromDisk()` 重建（[qoderwork/watchdog.go:81](file:///f/cpa-plugin/qoderwork/watchdog.go#L81)）时从磁盘读不到冷却字段，冷却被整体清空**——已 110 冷却的账号重新进入路由。本次 19:57 请求落在 19:49 刚触发过冷却的 `01a01535` 上，与该机制失效吻合。

> 落盘失败的具体原因尚未取证到（`triggerDailyCooldown` 的 error 被丢弃，无日志）。`persistAuthDirect` 在 `phys.Path == ""` 时返回 `no physical auth path`，这是首要嫌疑，需在修复中补可观测性后确认。

### 3.4 为什么宿主没有兜底跨 provider 轮转

宿主 conductor 的跨 provider 轮转依赖 `StatusCode()` 数字接口（见 2026-10-15 排队帧 Bug 结论）。插件在断流分支通过 `streamEmitError` 发出的错误信封**未携带 `http_status`**：

```go
func envelopeHTTPStatusForError(message string) int {
    if isQueueFrame(message) {   // 只对排队帧返回 503
        return queueFrameHTTPStatus
    }
    return 0
}
```

`upstream stream read error: ...` 不命中 `isQueueFrame` → 返回 0 → 宿主拿不到状态码 → 不做跨 provider 轮转。这是"没有换号"的**第二层原因**，与 3.1 叠加。

## 4. 影响面

- 所有走流式（async stream）的 qoderwork 请求：上游中途断流一律直接失败，用户需手工重试。
- 已泄漏内容（`ttft` 非零）时**本就不该自动换号**，此场景插件行为正确；但当前实现无法区分，导致零泄漏断流也被放弃。
- 110 冷却失效会让已达日限额的账号反复承接请求，制造更多断流/失败。
- 同源缺陷存在于 `workbuddy` 与 `qoder-ai`（逐字同构），需横向评估。

## 5. 修复建议

> 本节为方案建议，实施前需用户裁定范围（见 §7）。

### 5.1 断流分支分级处理（主修）

在 `pumpUpstreamStream` 的 `scanner.Err()` 分支引入与错误帧分支一致的**零泄漏守卫**：

| 条件 | 处理 |
|---|---|
| `emitted == false`（零泄漏） | 按可重试失败处理：`noteAccountFailure` + 预算内 `pickNextAuth` 换号重建请求；无候选则报错 |
| `emitted == true`（已泄漏） | 保持现状：记录失败 + `streamEmitError` 收尾，**禁止换号** |

- 断流是否属"账号级"需判定：`connection reset by peer` / `INTERNAL_ERROR` / 超时类属传输层，可换号；若断流前收到过额度类错误帧则应走 3.1 表中错误帧分支。
- 同步路径 `collectUpstreamStreamQoder` 同构补齐（其 `len(chunks) > 0` 天然等价于 `emitted`）。

### 5.2 断流信封补 `http_status`（打通宿主跨 provider 轮转）

在 `envelopeHTTPStatusForError` 增加断流识别，返回 502/503（避免用 403 触发宿主 30 分钟冷却）：

```go
if isEmptyStreamBody(message) || strings.Contains(message, "stream read error") {
    return http.StatusBadGateway   // 或 503
}
```

- 与 3.3 联动：仅当**零泄漏**时携带状态码，已泄漏场景不应让宿主换 provider 重放。

### 5.3 24h 冷却落盘可观测性与失败处置（次修）

1. 把 5 处 `_ = triggerDailyCooldown(...)` 改为记录错误日志（不改变主流程返回）。
2. 落盘失败时至少保留内存冷却，并输出可定位原因（`phys.Path` 是否为空、host RPC 是否失败）。
3. 补回归用例：模拟 `hostAuthGetPhysical` 返回空 Path，断言日志含明确原因且内存冷却仍生效。

### 5.4 横向同步

- `workbuddy/stream.go:227`、`qoder-ai/stream.go:330` 同构分支需同轮评估修复。
- `traework` / `zcode` 的断流分支需单独核对（协议不同，不默认同形）。

### 5.5 测试方案

| 用例 | 断言 |
|---|---|
| 零泄漏断流（首帧前 reset） | 触发换号，第二次请求成功，最终返回成功 |
| 已泄漏断流（首帧后 reset） | 不换号，返回 `stream read error` 错误信封 |
| 断流信封状态码 | `http_status` 非 0（502/503） |
| 冷却落盘失败 | 日志含原因、内存冷却仍生效、无静默吞错 |
| 哨兵反证 | 移除零泄漏守卫 → 已泄漏用例 FAIL；移除状态码 → 信封用例 FAIL |

## 6. 未覆盖与后续

### 6.1 未覆盖

- 落盘失败的确切原因（`phys.Path` 为空 / host RPC 失败 / 文件权限）未取证，因错误被丢弃且无日志。
- 上游 `47.86.185.172:443` 断流的触发条件（时段 / 上下文规模 / 账号状态）未做对照实验。
- `upstream served model "auto"` 现象（本次请求日志亦有）属独立模型键问题，未在本轮展开。

### 6.2 独立观察项：面板「来源」与实际承载账号不一致

面板来源列显示 `u7d5058ff`（`01a0b6d9`），宿主日志实际承载为 `udbee4bb0`（`01a01535`）。在**未发生换号**的前提下二者应一致，需单独核对 `accountLabel` 的取值时机与宿主 conductor 的账号选择链路。本项不影响本次根因结论，但会影响面板排障准确性。

### 6.3 风险

- 断流分级修复涉及流式主路径，属高影响面改动，须走完整回归（cgo-shim build/vet/test + 6-review + 生产热重载验收）。
- `http_status` 补值会改变宿主跨 provider 轮转行为，需评估是否引发同 provider 内重复请求。

## 7. 结论

**用户诉求「失败后没有换号继续」成立，且是两层原因叠加：**

1. **插件层（主因）**：`pumpUpstreamStream` / `collectUpstreamStreamQoder` 的**扫描器读错误（断流）分支完全没有换号路径**，直接记录失败并返回；该缺陷在 `workbuddy` / `qoder-ai` 同构存在。
2. **宿主层（次因）**：断流错误信封未携带 `http_status`，宿主 `StatusCode()` 得 0，不触发跨 provider 轮转。

**但断流不能无条件换号**：本例 `ttft=6.58s` 证明内容已泄漏，此时换号会产生双份输出。正确修复必须按"零泄漏 / 已泄漏"分级，已泄漏场景维持现状是正确行为。

**另发现一个独立缺陷**：24h 日限额冷却近 6 小时触发 92 次但磁盘零落盘，错误被 `_ =` 静默吞掉，导致冷却在内存重建时整体丢失，已耗尽账号重新承接流量。
