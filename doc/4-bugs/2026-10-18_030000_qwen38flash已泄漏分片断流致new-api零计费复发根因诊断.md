## 3. 根因

本次不是 2026-10-17 那个缺陷（流式断流分支无换号路径）的复发，而是**该修复明确排除的场景被真实触发**。完整的四层失效链如下：

### 3.1 第一层（插件）：`emitted` 语义过粗，把「仅思考分片」也判为不可换号

[qoderwork/stream.go:325](file:///f/cpa-plugin/qoderwork/stream.go#L325)：

```go
emitted = true
```

该赋值在**任何** `cleaned != ""` 的分片发出后置位，不区分该分片承载的是 `reasoning_content`（思考摘要）还是 `content`（正文）。

本次请求 `reasoning_effort=max`、输入约 30 万 token，前 33.99s 上游持续输出的是**思考分片**，正文尚未开始。此时断流，`emitted` 已为 true。

[qoderwork/policy.go:209-216](file:///f/cpa-plugin/qoderwork/policy.go#L209-L216)：

```go
func shouldRotateOnStreamReadError(emitted bool, attempt, budget int, hasEncodedBody, hasNextAuth bool) bool {
	if emitted || !hasEncodedBody || !hasNextAuth {
		return false
	}
	return attempt < budget
}
```

→ **零泄漏守卫直接拒绝换号**。

### 3.2 第二层（插件）：已泄漏时错误信封不带状态码

[qoderwork/policy.go:193-202](file:///f/cpa-plugin/qoderwork/policy.go#L193-L202) 中 `isStreamReadError` 遇到 `after partial output` 标记即返回 false，于是 `envelopeHTTPStatusForError` 返回 0，而非 502。

设计意图是「已泄漏时避免宿主跨 provider 轮转造成输出错乱」，但这同时**剥夺了宿主唯一可用的失败信号**。

### 3.3 第三层（宿主）：错误 chunk 被转成 `event: error`，而 new-api 不认

链路验证（`F:\CLIProxyAPI` 只读）：

1. 插件 `streamEmitError` → `MethodHostStreamEmit` 带 `error` 字段（[qoderwork/stream.go:55-70](file:///f/cpa-plugin/qoderwork/stream.go#L55-L70)）；
2. 宿主 `streamBridgeStream.run` 将其转为 `ExecutorStreamChunk{Err: ...}`（[internal/pluginhost/stream_bridge.go:88-96](file:///f/CLIProxyAPI/internal/pluginhost/stream_bridge.go#L88-L96)）；
3. `wrapStreamResult` 把带 Err 的 chunk 继续下发（[sdk/cliproxy/auth/conductor_stream.go:113-160](file:///f/CLIProxyAPI/sdk/cliproxy/auth/conductor_stream.go#L113-L160)）；
4. Responses handler 在 `dataFrames > 0` 时走 `forwardResponsesStream`，最终由 `writeTerminalError` 输出 **`event: error`**（[sdk/api/handlers/openai/openai_responses_handlers.go:1009-1048](file:///f/CLIProxyAPI/sdk/api/handlers/openai/openai_responses_handlers.go#L1009-L1048)）。

### 3.4 第四层（new-api）：`event: error` 不提取 usage，且流以 EOF 正常收尾

[new-api/relay/channel/openai/relay_responses.go:91-118](file:///f/new-api/relay/channel/openai/relay_responses.go#L91-L118) 的 `OaiResponsesStreamHandler` **只从三个事件提取 usage**：

```go
case "response.completed", "response.done", "response.incomplete":
    ... usage = dto.MergeUsageNonZero(usage, incomingUsage)
case "response.failed", "response.cancelled", "response.canceled":
    ... usage = dto.MergeUsageNonZero(usage, incomingUsage)
```

`event: error` 不在其中。同时 [new-api/relay/helper/stream_scanner.go:289](file:///f/new-api/relay/helper/stream_scanner.go#L289) 在扫描器正常 EOF 时无条件 `SetEndReason(StreamEndReasonEOF)`，而 `IsNormalEnd()` 把 EOF 视为正常（[relay/common/stream_status.go:88-95](file:///f/new-api/relay/common/stream_status.go#L88-L95)）→ 记为 `status:ok`。

**结论：`$0` 的直接机制是「CPA 发 `event: error`（无 usage） + new-api 只认 responses 系列终态事件提取 usage + EOF 被判正常」三者叠加。**

### 3.5 与 2026-10-15 零正文截断事件的区别（严禁并案）

| 维度 | 2026-10-15 零正文截断 | **本次 2026-10-18** |
|---|---|---|
| 断点 | 上游正常生成到 `finish_reason=length` | **TCP 连接被对端复位** |
| `frt` | 正常值（如 2334） | 正常值 4792（首帧已到） |
| `end_reason` | `eof` / `status:ok` | `eof` / `status:ok` |
| feed tokens | `output == reasoning > 0`（吃满上限） | **全 0**（未收到 usage） |
| CPA 错误 | 无（正常终态） | **`upstream stream read error ... connection reset by peer`** |
| 根因层 | 生成层截断 + CPA 守卫吞掉 incomplete | **传输层断流 + 插件不换号 + 事件类型不匹配** |

两者表面现象相同（$0 + 无法扣费），但**根因与修复落点完全不同**，不可套用 10-15 的方案。

## 4. 为什么 2026-10-17 的修复没能覆盖

| 修复项 | 覆盖场景 | 本次是否命中 |
|---|---|---|
| `isStreamReadError` + `shouldRotateOnStreamReadError` | 零泄漏断流 → 换号 | ❌ 已泄漏，被守卫拒绝 |
| 断流信封补 `http_status=502` | 零泄漏断流 → 宿主跨 provider 轮转 | ❌ 已泄漏时主动抑制 |
| 冷却落盘失败可观测 | 落盘异常 | 无关 |

原修复的正确性成立（已泄漏换号会破坏输出），但其**判定粒度**把「仅思考分片」与「已出正文」混为一谈，导致绝大多数长上下文 qwen 请求在思考阶段断流时必然落入不可换号分支。

## 5. 影响面

- **计费**：new-api 侧该请求 `$0`，但上游实际已消耗约 30 万 input token 与数十秒生成；成本由我方承担。
- **用户体验**：客户端收到 `event: error` 前已看过一段思考内容，最终无正文，表现为「回答到一半消失」。
- **账号健康**：本次断流经 `noteAccountFailure(curAuthID, 0, ...)` 计入阶梯冷却，账号 `01a03dc6` 会被冷却（状态码 0 走传输错误路径）。断流属上游网络问题，**惩罚本账号不合理**。
- **影响范围**：qoderwork / qoder-ai / workbuddy 三插件同源（`stream.go` 结构一致），`qwen-3.8-flash` 在 `/v1/responses` 路径下均可能复现。

## 6. 修复方向（三选一，需用户裁定）

### 方案 A：细化 `emitted` 语义——区分「仅思考分片」与「已出正文」（推荐）

- 在 [qoderwork/stream.go:298-326](file:///f/cpa-plugin/qoderwork/stream.go#L298-L326) 的扫描循环中，额外维护 `contentEmitted`：仅当分片包含非空 `choices[].delta.content` 或 `tool_calls` 时置位。
- 换号守卫由 `emitted` 改为 `contentEmitted`：**仅思考阶段断流允许换号**（思考摘要被重放是可接受的，因为客户端会把它作为 reasoning 展示，且第二次请求的思考是同一问题的重新推理）。
- 风险：客户端会看到两段思考摘要。需评估是否在换号前发一个「reasoning 重置」帧，或接受拼接。
- 三插件同改，改动量约 30 行/插件。

### 方案 B：断流时补发携带 usage 的 `response.incomplete`

- 插件在断流且已泄漏时，主动构造一个带 `usage`（按已收分片估算）与 `incomplete_details.reason="upstream_error"` 的终态帧，替代当前的纯错误信封。
- 需宿主支持：CPA 的 Responses 转译层需把该帧透传给 new-api。
- 收益：即使不换号，也能让 new-api 正确计费，消除 `$0`。
- 风险：usage 为估算值，计费精度下降；需确认 `incomplete` 事件在 CPA 侧不被守卫拦截（2026-10-15 已修复过该守卫）。

### 方案 C：断流不计入账号冷却

- 将 `noteAccountFailure(curAuthID, 0, "stream read error")` 改为不记账或只记软失败。
- 收益：避免上游网络抖动误伤健康账号。
- 局限：不解决换号与计费问题，只能作为 A/B 的配套。

**推荐组合：A + C**。A 解决「本可换号却不换」的核心体验问题，C 修正误伤。B 作为后续独立项（涉及跨项目 new-api 与 CPA 宿主，成本更高）。

## 7. 验证标准（修复后）

1. 构造「思考阶段断流」单测：mock 上游先发 3 个 `reasoning_content` 分片再返回 `connection reset by peer`，断言插件发生换号且第二次请求成功。
2. 构造「正文阶段断流」单测：先发 1 个 `content` 分片再断流，断言**不换号**且错误透传（保持既有不变量）。
3. 生产观察：下一次真实断流时，`docker logs` 应出现 `attempt=2` 或第二条 `upstream execution failed`（换号后成功则无第二条失败日志）。
4. 计费验证：若同时实施方案 B，new-api 日志中该请求应出现 `completion_tokens > 0`。

## 8. 未验证项（诚实标注）

- 本次断流的对端 `47.86.185.172:443` 是 Qoder 上游 IP，但 `connection reset by peer` 的具体触发条件（上游主动断 vs 中间网络设备）无法从现有日志区分。
- new-api 是否还有其他事件类型可提取 usage（未穷举其 `dto.ResponsesStreamResponse` 全部类型）。

| 检查项 | 结果 |

| 断流信封 `http_status` | **缺失**（`marshalStreamErrorEnvelope` 只发 `stream_id` + `error`） |
| 断流账号记账 | 有 `noteAccountFailure(curAuthID, 0, ...)`（误伤） |

证据：[workbuddy-ai/stream.go:227-232](file:///f/cpa-plugin/workbuddy-ai/stream.go#L227-L232) 原文为「只记录失败 + 透传错误 + return」，**任何情况下都不换号**——连零泄漏断流也不重试。该插件从未同步 2026-10-17 那轮修复。

已按同一方案补齐：断流识别、分级换号（仅思考可换）、502 信封、断流不记账；新增 3 组共 29 个用例；变异反证精确命中。版本 0.1.17 → **0.1.18**。

### 9.2 traework：**不属于同类缺陷（产品语义不同）**

traework 使用 `traeSSETerminal` 三态分类（`terminationDone` / `terminationOutputEOF` / `terminationInvalid`），并在「有部分输出但 EOF 无 done」时**主动补 `finish_reason=length` 正常收尾**，让客户端保留已生成内容（[traework/stream.go:468-480](file:///f/cpa-plugin/traework/stream.go#L468-L480)）。

- 该行为是 `PROJECT_STYLE.md` 明确记录的产品决策：「Trae SSE 必须以明确完成事件收口；部分输出后 EOF 按截断失败处理」，而非漏修。
- 与 Qoder 系的关键差异：Trae 上游断流时客户端已收到完整可读内容，补 `length` 后 new-api 可正常计费（不会 `$0`）。
- 空响应（`terminationInvalid`）才真正报错，此时尚未发出任何分片，不存在「已泄漏」问题。
- **结论：不修改。**

### 9.3 coze：**不承载推理流量，不适用**

`coze/main.go:263` 的插件注册声明 `Executor: false`，该插件只做认证（Cookie/设备登录）与管理面板，不实现 `Execute` / `ExecuteStream`，因此不存在流式断流路径。

**结论：不适用。**

## 10. 方案 B 落地结论（2026-10-18 05:20 补充）

用户裁定「traework 式收尾作为『正文已泄漏』分支的补充」后，方案 B 已按**不注入 usage**的形态落地，五插件版本见 §9.4。

### 10.1 与 §6 方案 B 的差异：无需构造 usage

原方案 B 设想「插件构造带 `usage` 的终态帧」。逐行核验 new-api 后发现**不必注入 usage**：

- new-api 在 `usage.CompletionTokens == 0` 时会回退到 `response.output_text.delta` 累计文本估算（[relay_responses.go:146-154](file:///F:/new-api/relay/channel/openai/relay_responses.go#L146-L154)），只要终态事件合法且正文已下发，就能算出 token。
- 反之，若插件自行注入估算 usage，反而会把 CPA 的 `st.UsageSeen` 置真、让 new-api 采用插件估算值而非其自身口径，计费精度与一致性都更差。

因此最终实现只合成 `finish_reason=length` 分片，usage 交给 new-api 侧兜底。

### 10.2 宿主链路验证（三段）

| 环节 | 事实 | 位置 |
|---|---|---|
| 插件合成 length | `buildStreamTerminalChunk` 产出空 delta + `finish_reason=length` | 各插件 `policy.go` |
| 宿主补 DONE | 插件正常关流后 `emitTranslatedExecutorStreamTail` 追加 `data: [DONE]` | [adapters_executors.go:627-647](file:///F:/CLIProxyAPI/internal/pluginhost/adapters_executors.go#L627-L647) |
| 转译层映射 | `isDone` 分支 + `incompleteByFinishReason("length")` → `response.incomplete`（`reason=max_output_tokens`） | [openai_openai-responses_response.go:74-92](file:///F:/CLIProxyAPI/internal/translator/openai/openai/responses/openai_openai-responses_response.go#L74-L92) |
| 宿主不补 502 | `response.incomplete` 属 `responsesSSETerminalEvent` | [openai_responses_handlers.go:262-269](file:///F:/CLIProxyAPI/sdk/api/handlers/openai/openai_responses_handlers.go#L262-L269) |
| new-api 提用量 | `response.incomplete` 在计费 switch 内 | [relay_responses.go:91-96](file:///F:/new-api/relay/channel/openai/relay_responses.go#L91-L96) |

### 10.3 语义边界（三条不变量）

1. **只有 `contentEmitted=true` 才合成 length**：零泄漏或仅思考分片仍走换号；换号失败仍透传 error。避免把真实失败伪装成成功截断。
2. **同步路径（`StreamID == ""`）不改**：宿主 `rpcPluginAdapter.ExecuteStream` 恒填 `StreamID`（[rpc_client_stream.go:16-23](file:///F:/CLIProxyAPI/internal/pluginhost/rpc_client_stream.go#L16-L23)），该分支仅为防御性 fallback；其调用方在 `err == nil` 时把请求记为成功，若在此合成终止分片会让截断在 dashboard 上伪装成成功。
3. **日志仍记失败**：`publishUsage(..., failed=true, ...)` 保持在合成 length 之前，可观测性不丢。

### 10.4 未消除的取舍

客户端会看到「成功但内容被截断」（`status=incomplete`）而非显式错误。这是保留已生成内容与恢复计费的必然代价；对 Agent 类客户端（Codex / Qoder）而言，`incomplete` 是可识别的续写信号，优于整条请求失败。
