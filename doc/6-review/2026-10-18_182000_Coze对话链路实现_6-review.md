## 具体检查

### 命名一致性

- `frontierFrame` / `frontierHeader` / `frontierMessage` / `frontierEvent`：
  与 `frontier_frame.go` 的领域术语一致。
- `clawEnvelope` / `clawMessage` / `clawReplyPayload`：与上游端点命名对齐。
- 常量用全大写 + 领域前缀（`frontierServiceClaw`、`clawRequestTimeout`），
  与既有 `modelListPath` / `tokenBeatPath` 风格一致。

### 注释质量

块注释回答「为什么」的样例：

- `frontier_frame.go` 头部：解释为何不引入 protobuf 运行时（12 个标量字段，
  手写 150 行，避免抬高 c-shared 交叉编译复杂度）。
- `frontier_frame.go` 的 `frontierServiceClaw`：标注实测值并警告
  不要与 `connection-params` 的 `33555616` 混淆。
- `executor.go` 的 `replyCollector.pending`：解释为何与 `deltas` 分开维护
  （分开才能逐帧下发，否则会「卡一下蹦一大段」）。
- `convert.go` 头部：解释多轮折叠是**有损**的取舍及其理由。

### 错误处理

所有错误路径都带操作上下文：

```go
return nil, fmt.Errorf("取 frontier 凭证失败：%s", env.describe())
return "", fmt.Errorf("session/get_main 解析失败：%w", errUnmarshal)
```

业务错误与传输错误分开处理：`clawEnvelope.isSuccess()` 判 `code`，
非 2xx 单独上报——避免「HTTP 200 + code=1000001」被误判为成功。

### 并发安全

- `replyCollector` 的读写全部持锁；`notify` 通道用非阻塞发送避免死锁。
- `frontierClient` 的 `conn` / `closed` 由 `mu` 保护。
- 读循环独占 `conn`（gorilla 不允许并发读），心跳只写不读。
- 心跳协程通过 `context.WithCancel` 感知退出，无 goroutine 泄漏。

### 资源释放

- `runOnce` 的 `defer conn.Close()`。
- `runStream` 的 `defer stopWS()` 与 `defer client.Close()`。
- `readLoop` 的 `defer close(stopWatch)`。
- 所有 `http.Response.Body` 均 `defer Close()`。
