# Coze 执行失败状态码回传验证（0.5.1）

- 日期：2026-10-19
- 插件版本：`coze-provider 0.5.1`
- 关联问题：生产生图偶发失败后，同一个坏号在后续请求中仍被反复选中
- 验证入口：`python scripts/cgo-shim-build.py coze`

## 1. 问题与证据

生产日志（2026-10-19 22:27–22:28）：

```
upstream execution failed: model=coze/doubao-seedream-5-0-pro
  auth_file=coze-1185dd02733b1278.json duration=1.906s
  err=提交消息失败：该用户积分已耗尽（code=1000521）
upstream execution failed: model=coze/doubao-seedream-5-0-pro
  auth_file=coze-75c74487dec08055.json duration=5.668s
  err=上游未返回任何图片
```

两次失败间隔约 6 秒，宿主均未换号，第二次仍选中 coze 供应商下的账号。

## 2. 根因

插件与宿主之间存在状态码契约缺口：

| 环节 | 位置 | 行为 |
| --- | --- | --- |
| 插件回写 | `coze/main.go` `writeExecutionError` | 旧实现只对 4xx 走带状态码信封，其余走 `errorEnvelope`（无 `http_status`） |
| 宿主解码 | `internal/pluginhost/rpc_client.go:360` `decodeEnvelopeResult` | `statusCode = envelope.Error.HTTPStatus`，缺省为 0 |
| 宿主取值 | `sdk/cliproxy/auth/conductor_cooldown.go:1448` `statusCodeFromError` | 无 `StatusCode()` 实现或值为 0 时返回 0 |
| 宿主判定 | `conductor_selection.go:1452` `isCredentialRetryRoundStatus` | 白名单只含 403/408/429/500/502/503/504；0 不在其中 |
| 后果 | `conductor_selection.go:1337` `shouldRetryAfterErrorWithAttempted` | `isRequestRetryRoundError` 为 false → 提前返回 `(0, false)`，不进入换号重试轮 |

补充确认：
- 图片端点走 `Manager.Execute`（`conductor_execution.go:121`），本身具备 `for attempt := 0; ; attempt++` 换号循环，能力存在，只是被状态码缺失挡住。
- 插件返回 `rc != 0` 时宿主仍会解析错误信封（`loader_unix.go:208-211`：`isPluginErrorEnvelope(out)` 为真则直接返回信封字节），因此插件侧补 `http_status` 有效。
- 旧注释「缺失时宿主一律当 5xx」与宿主实际行为不符，已修正。

## 3. 修复方案

新增 `coze/faults.go` 作为失败分类唯一出口：

| 失败类型 | 状态码 | 错误码 | 宿主行为 |
| --- | --- | --- | --- |
| 请求级 4xx（如 413 内容超长、400 解析失败） | 原样 4xx | `invalid_request` | 直接返回用户，不换号不冷却 |
| 积分耗尽（`code=1000521`） | 403 | `quota_exhausted` | 冷却该号 30 分钟 + 换号重试 |
| 未分类上游失败（未返回图片、回复为空、未知业务码） | 502 | `upstream_error` | 冷却该号（瞬时冷却）+ 换号重试 |

选型依据：
- **不用 402**：`conductor_cooldown.go:856` 的 402 分支只设置冷却，不在 `isCredentialRetryRoundStatus` 白名单内，不会换号。
- **不用 429**：`conductor_cooldown.go:872` 走配额退避阶梯，`minQuotaCooldownFloor = 10s`，积分耗尽不可能在 10 秒内自愈。
- **用 403**：既在换号白名单内，又在 `MarkResult` 里固定冷却 30 分钟；且 `clienterror.IsRequestFault` 不会把它误判为请求故障，`tryRefreshAfterUnauthorized`（仅 401）也不会触发无意义的凭证刷新。
- **底层状态码优先**：`withStatus` 先用 `errors.As` 检查已有状态码，避免外层把 413 升级成 502。

### 7.3 换号生效实证（本轮最关键证据）

同一时间窗的生产日志：

```
[2026-10-19 23:17:04] [warn] [conductor_execution.go:1965] 403 | 1.907s |
  upstream execution failed: provider=coze-provider
  model=coze/doubao-seedream-5-0-pro
  auth_file=coze-1185dd02733b1278.json
  err=提交消息失败：该用户积分已耗尽（code=1000521）
```

随后同一请求在另一账号上成功出图（对应验收第 1 轮 200 / 29.07s）。

对照修复前（2026-10-19 22:27）：
- 日志无状态码前缀，`coze-1185dd02733b1278.json` 失败后请求直接结束，用户看到失败；
- 修复后日志出现 `403 |` 前缀，该号被冷却并换号，请求最终成功。

**结论：`code=1000521` → 403 → 宿主冷却该号 30 分钟并换号重试，已在生产实证生效。**

## 8. 未覆盖与后续

- **`message/list` 等握手失败的分类**：已统一走 `clawBusinessError`，但业务码表目前只登记 `1000521`；其余码保持无状态码并由兜底 502 处理，属有意保守。
- **流式路径**：流式失败通过 `host.stream.emit` 的 `error` 字段上报（`emitStreamError`），该通道不携带状态码，宿主侧仍无法据此换号。图片端点是非流式的，本轮未涉及；若后续要让对话流式也参与换号，需要宿主侧支持错误帧带状态码。
- **同池只剩坏号时**：换号重试仍会全部失败（属预期），此时用户看到的是兜底错误文案而非无限重试。
