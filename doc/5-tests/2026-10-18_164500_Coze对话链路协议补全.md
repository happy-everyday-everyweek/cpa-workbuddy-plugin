## 1. 推翻了什么

| 原计划假设 | 实测结论 |
|---|---|
| `claw_id` 来自桌面端运行时上下文，插件拿不到 | **错**。`POST /api/coze_claw/claw/info` 传 `{}` 即返回 `data.user_claw_info.claw_id`，只需会话 Cookie |
| `message/chat` 是 SSE 流式返回 | **部分错**。它不是 HTTP SSE，而是**异步提交**（立即返回 `message_id`）；但流式增量**确实存在**，走独立的 WebSocket 通道（`wss://frontier.coze.cn`），见 §4 |
| 无法真流式（初版结论，已撤销） | **错**。claw 对话走 WS 推送，`content_v2` 增量形态已实测；帧 schema 与 `service` 见 §4.6 |

这两点直接改变 TASK-004 的设计：不是「SSE 增量转 chunk」，而是
**「HTTP 异步提交 + WebSocket 接收增量 + 增量转 chunk」**。
`message/list` 只作为断线兜底，不承担实时增量（实测延迟约 4 秒且只返回完整消息）。

## 2. 完整调用链（真实实测）

### 2.1 取 claw_id

```
POST https://www.coze.cn/api/coze_claw/claw/info
Cookie: <会话 Cookie>
Content-Type: application/json

{}
```

响应（HTTP 200）：

```json
{"code":0,"msg":"","data":{"user_claw_info":{
  "claw_id":"7697639566446149898",
  "name":"扣子",
  "model_name":"{\"model_name\":\"glm-5.3-flash\",\"custom_model_id\":\"\",\"is_custom\":false}",
  "is_deleted":true,
  "avatar_url":"https://lf-coze-web-cdn.coze.cn/..."
}}}
```

要点：
- **body 必须是 `{}`**，不是空 body。
- `is_deleted:true` 不影响可用性（实测仍能建会话、能对话）。
- `model_name` 是**内层 JSON 字符串**，需二次解析；这里是 `glm-5.3-flash`。

### 2.2 取主会话

```
POST /api/coze_claw/session/get_main
{"claw_id":"7697639566446149898"}
```

响应：

```json
{"code":0,"data":{"session":{
  "id":"7697640660014383411",
  "claw_id":"7697639566446149898",
  "status":2,"is_pin":true,"create_time":"1792246633607"
}}}
```

要点：
- 缺 `claw_id` 时返回 `{"code":1000001,"msg":"参数错误"}`。
- 主会话是**每个 claw 固定的**，可直接复用，不必每次 `session/create`。

### 2.3 发消息（异步）

```
POST /api/coze_claw/message/chat
{"session_id":"7697640660014383411","content":"只回复两个字：收到",
 "files":[],"skill_ids":[],"at_members":[],
 "video_option":null,"quick_reply":null,"reference_cards":[],"plugins":[]}
```

响应（HTTP 200，`application/json` **不是** SSE）：

```json
{"code":0,"msg":"","data":{"message_id":"20e59cc7-a3d8-4e70-b29c-75c5103b16cb"}}
```

要点：
- 只返回 `message_id`（用户消息 ID），**不含任何回复内容**。
- 因此不能边收边转；必须轮询。

### 2.4 取回复（轮询）

```
POST /api/coze_claw/message/list
{"session_id":"7697640660014383411","size":6,"asc_mode":false}
```

响应关键结构：

```json
{"code":0,"data":{"messages":[
  {"id":"7697925994237182218","source":2,"message_type":"reply",
   "content":"{\"id\":\"7697925994237182218\",\"session_id\":\"7697640660014383411\",
     \"message_type\":\"reply\",
     \"message_data\":{\"reply\":{\"content\":\"收到\",
       \"reply_to_message_id\":\"20e59cc7-a3d8-4e70-b29c-75c5103b16cb\",
       \"stream\":false}},
     \"create_time_ms\":1792313065821,\"turn_id\":\"7697925977149833481\"}",
   "sender":{"user_type":2,"claw_id":"7697639566446149898","nickname":"扣子"}},
  {"id":"20e59cc7-...","source":1,"message_type":null,
   "content":"只回复两个字：收到","sender":{"user_type":1,"user_id":"3735510093922464"}}
],"next_cursor":""}}
```

要点（实现必读）：
- `messages` 按**时间倒序**（`asc_mode:false`），第一条是最新。
- 用户消息 `source=1`，AI 回复 `source=2` 且 `message_type="reply"`。
- **AI 回复的 `content` 是内层 JSON 字符串**，正文在 `message_data.reply.content`。
- `message_data.reply.reply_to_message_id` 与第 3 步拿到的 `message_id` 对应 —— **这是配对请求与回复的唯一可靠键**。
- `message_data.reply.stream` 为 `false` 表示该回复已完整；真实长回复可能先出现 `stream:true` 的中间态。
- `turn_id` 标识一轮对话，可用于后续增量去重。

### 2.5 task/events 不是对话增量的入口

```
GET /api/coze_claw/task/events?session_id=...&after_cursor=&size=50
→ HTTP 400: binding: expr_path=task_id, cause=missing required parameter
```

`task_id` 是**后台 Base Agent Task** 的标识，与 `message/chat` 的 `message_id` 不是同一体系。
结论：**对话回复走 `message/list` 轮询，不走 `task/events`**。原计划 H-02 假设（「会话增量可通过 task/events 游标轮询获得」）**不成立**。

## 4. 流式能力实测（**已更正：支持真流式，且已抓到真实帧**）

> **重要更正（2026-10-18 17:00）**：本节初版结论「无法真流式」是**错的**。
> 初版只测了 HTTP 轮询接口（`message/list`）就下结论，未查客户端的真实接收通道。
> 经二次逆向 + 实连验证：**扣子 claw 对话走 WebSocket 流式推送，可以真流式。**

### 4.1 初版错误的原因

| 环节 | 初版做法 | 问题 |
|---|---|---|
| 观察面 | 只看 `message/list` HTTP 响应 | 该接口只返回**已落库**的完整消息，天然看不到中间态 |
| 遗漏 | 未查客户端如何接收增量 | 实际走 WebSocket，与 HTTP 轮询是两条独立通道 |

`message/list` 返回的 `message_data.reply.stream` 字段本身即为流式能力的反证——
非流式场景不需要该字段。

### 4.2 真实流式通道（二次逆向实证）

**入口**：`GET /api/coze_claw/resource/get_frontier_key`

```
Cookie: <会话 Cookie>
→ {"code":0,"data":{"access_key":"<32 字符>","device_id":"<19 字符>"}}
```

生产实测 HTTP 200，两个字段均返回（长度分别为 32 / 19）。

**连接**：`wss://frontier.coze.cn/ws/v2`

```
wss://frontier.coze.cn/ws/v2
  ?device_platform=web&version_code=fws_1.0.0
  &access_key=<access_key>&fpid=1289&aid=751148&device_id=<device_id>
  &xsack=0&xaack=0&xsqos=0&qos_sdk_version=2
```

**参数来源（页面 bundle 实证）**：

```js
new e_({ appId: 751148, fetchKey: em, fpId: 1289, frontierUrl: "wss://frontier.coze.cn" })
// fetchKey → GET /api/coze_claw/resource/get_frontier_key → { access_key, device_id }
```

`aid`（app_id）= **751148**、`fpid`（product_id）= **1289**，均为硬编码常量；
`xsack`/`xaack`/`xsqos` 全为 `0`，即 claw 通道**不启用** ACK/QoS（与 §4.4 的通用 fws 默认值不同）。
`subprotocol` 必须传 `pbbp2`。

> **易错点**：`GET /api/fullstack_chux/v1/frontier/connection-params?service_type=agent`
> 返回的是**另一条通道**（`app_id=578287`、`message_service_id=33555616`、`xsack=1`），
> 属于 fullstack/space 场景。claw 对话必须用 `aid=751148` 这条，
> 用错参数连上去只能收到 `hi` 心跳，收不到任何业务帧（本轮已实测踩坑）。

**实连验证（Node v24 内置 WebSocket，WSL 出网）**：

```
[0.21s] OPEN                    ← 握手成功
[0.21s] sent hi (heartbeat)
[0.27s] FRAME len=2 hi          ← 心跳应答，通道健康
```

心跳协议：客户端发字符串 `hi`，服务端回 `hi`。**每 10 秒一次**（页面实测 `__sendHits` 间隔 10005ms）。

### 4.3 事件模型（asar 逆向 + 实测校正）

claw 对话的 frontier handler 判定：

```js
isNeedHandle(e){return["message","stream","session","conversation"].includes(e)}
```

四类事件，其中 **`stream` 就是流式增量**：

```js
stream: e => {
  this.isValidMessageData(e,"stream") && (
    z(e),
    e.content_v2
      ? this.streamV2Handler.handleStreamV2(e)
      : this.streamHandler.handleStream(e)
  )
}
isValidMessageData(e,t){ return !!e?.id && !!(e?.content||e?.content_v2) && !!e?.session_id }
```

关键字段：
- `e.id`：消息 ID
- `e.content` / `e.content_v2`：**两种内容形态**，`content_v2` 走新的 `handleStreamV2`
- `e.session_id`：会话归属

> **实测校正（18:10）**：上述 `stream` 事件是 **asar（桌面端）内部**的 handler 分支名，
> 不是网络层的事件名。**真实 WS 帧上没有名为 `stream` 的 `payloadType`**——
> 100 帧实测中 `payloadType` 只有 `session` / `message` 两种，
> 流式增量全部是 `payload.message_type="reply"` 的帧，
> 通过 `content_v2.session.phase` 区分 `event_start` / `event_delta` / `event_final`。
> 桌面端 handler 的 `stream` 分支应是其内部对 `event_delta` 帧的归类结果。
> **实现以 §4.6 的网络层实测为准。**

### 4.4 帧编码：protobuf，不是 JSON

这是初版测试收不到业务帧的直接原因：

```js
_onMessage = r => {
  ...
  if ("hi" !== r.data) {
    try { eD(this, r, [eH, eF, to, tx, ti, eB]) } catch(n) { ... }
  }
}
```

帧结构字段（protobuf）：

| 字段 | 说明 |
|---|---|
| `frameType` | 帧类型（含 cursor 类） |
| `SeqID` / `LogID` / `LogIDNew` | 序列号与日志 ID |
| `service` | 服务编号（claw 有独立 service id） |
| `method` | 方法编号 |
| `headers` | 键值头（含 `need_ack` / `is_ack` / `x_frontier_qos` / `x_frontier_ack_msgid`） |
| `payload` | 业务负载（`Uint8Array`，可带 `payloadEncoding` / `payloadType`） |

配套机制：
- **QoS 与 ACK**：`enableAutoAck` + `x_frontier_qos_ack`，服务端要求确认时客户端回 `_sendAck`
- **游标续传**：`cursor_file_name` 头 + IndexedDB 游标管理器，断线后可续
- **重连退避**：`initReconnectInterval` × `reconnectIntervalGrowFactor`，上限 `maxReconnectInterval`

### 4.6 真实 stream 帧实测（**本轮新增，阻断解除**）

**取证方式**：在已登录扣子页面内给 `WebSocket.prototype.send` 打补丁，
在首次发送（心跳 `hi`）时把真实 `WebSocket` 实例捕获到，再挂 `message` 监听，
从而读到**页面自身 claw 连接**的入站帧（自建连接收不到，见 §4.2 易错点）。

#### 4.6.1 帧 schema（protobuf，字段号实证）

从 SDK 的 `encodeFrame` / `decodedFrame` 反出完整定义，并用真实帧逐字段验证：

| 字段号 | 名称 | 类型 | 实测值示例 |
|---|---|---|---|
| 1 | `SeqID` | varint | `1424008517` |
| 2 | `LogID` | varint | `3672102781` |
| 3 | `service` | varint | **`33555657`**（claw 业务） |
| 4 | `method` | varint | `0` |
| 5 | `headers` | message[] | `{key, value}` |
| 6 | `payloadEncoding` | string | `""` |
| 7 | `payloadType` | string | **事件名**：`session` / `message` |
| 8 | `payload` | bytes | JSON UTF-8 |
| 9 | `LogIDNew` | string | `""` |
| 10 | `serverTiming` | string | `frontier;sta=1792315531190` |
| 11 | `msgID` | string | 长串 |
| 12 | `frameType` | varint | `0`（业务）/ `16`（流数据）/ `32`（游标） |

`headers` 内层同样是 `{1: key, 2: value}` 的 protobuf message。

**关键纠正**：初版推断的 `service` 是 `33555616`（来自 `connection-params`），
**实际 claw 业务帧的 `service` 是 `33555657`**。`payloadType` 承载事件名，
不是 `content-type` 之类的 MIME。

#### 4.6.3 reply 帧的完整结构

```json
{
  "claw_id": "7697639566446149898",
  "session_id": "7697640660014383411",
  "id": "7697937541999264035.1",
  "source": 2,
  "content": "{\"id\":\"...\",\"session_id\":\"...\",\"message_type\":\"reply\",
    \"message_data\":{\"reply\":{\"content\":\"<增量片段>\",
      \"reply_to_message_id\":\"b810eb92-...\",\"stream\":true}},
    \"create_time_ms\":1792315756487,\"turn_id\":\"7697937541999214883\"}",
  "content_v2": "{\"source\":0,\"session\":{...}}",
  "message_type": "reply",
  "sender": {"user_type":2,"claw_id":"7697639566446149898"},
  "reference_message": {...},
  "create_time": "1792315756487",
  "log_id": "202610181729153B94C18BD43BAC230A42"
}
```

**两种 content 形态必须区分**：

| 字段 | 类型 | 内容 |
|---|---|---|
| `content` | **内层 JSON 字符串** | `message_data.reply.content` = **增量片段**（delta） |
| `content_v2` | **内层 JSON 字符串** | `session.final.agent_message_event.content[].text.content` = **累积快照** |

> 初版 §4.3 逆向推测的「`stream` 事件 vs `message` 事件」在**实测中不成立**：
> 真实链路上没有独立的 `stream` 事件名，流式增量全部承载在
> `message_type="reply"` 的帧里，通过 `content_v2.session.phase` 区分阶段。

#### 4.6.4 `content_v2.session` 的阶段机（实证）

```json
{
  "source": 0,
  "session": {
    "phase": "event_start" | "event_delta" | "event_final",
    "session_id": "7697640660014383411",
    "seq_num": "7",
    "event_id": "7697937541999264035",
    "turn_id": "7697937541999214883",
    "client_message_id": "b810eb92-57bc-4df7-8ae4-6c5b0523f49c",
    "session_kind": "",
    "final": {
      "processed_at_ms": "1792315756487",
      "type": "agent.message",
      "agent_message_event": {
        "content": [{"type": "text", "text": {"content": "<累积全文>"}}],
        "device_info": {"device_id": "vefaas-...", "device_type": "vefaas"}
      }
    },
    "trace": {"trace_id": "...", "log_id": "..."}
  }
}
```

**实测阶段序列（同一 `turn_id`）**：

```
seq=7  event_start   delta=""                          ← 起始空帧
seq=8  event_delta   delta="1,2,3,...,14,"             ← 增量
seq=9  event_delta   delta="15,16,...,29,"
...
seq=16 event_delta   delta="...,120"
seq=17 event_final   final.type="agent.message"        ← 收尾，含累积全文
```

**增量拼接校验（实测通过）**：10 个 delta 拼接后 `joinedLen=371`，
与 `event_final` 的 `agent_message_event` 全文 `textLen=371` **完全相等**。
→ 结论：**delta 可安全累加，`event_final` 可用于最终校对**。

**收尾判据**：`content_v2.session.phase === "event_final"`。
不存在 `is_finish` 字段（已确认 `'is_finish' in reply === false`）。
另有独立的 `session.status_idle` 消息可作为整轮结束的兜底信号。

#### 4.6.5 去重与重放

同一帧会被投递多次（100 帧里 reply 仅 44 条，但去重前观察到大量重复）。
去重键用 **`turn_id + seq_num + phase`**：

```js
const key = `${session.turn_id}:${session.seq_num}:${session.phase}`
```

仅按 `id` 去重会漏——`event_start` 与 `event_delta` 的 `id` 相同（都是 `7697937541999264035.1`）。

#### 4.6.6 订阅帧与游标（实测）

首次连接后服务端先下发一帧 `frameType=16`（流数据）或 `32`（游标）的帧，
携带 `cursor_file_name` 头。客户端需回发订阅帧：

```
frameType 省略, SeqID=<自增>, LogID=<时间戳*1e4+随机>, service=9000, method=5,
```

#### 4.6.7 对 TASK-004 的最终落地口径

| 环节 | 实现要点 |
|---|---|
| 连接 | `wss://frontier.coze.cn/ws/v2`，`aid=751148`、`fpid=1289`、`xsack=0`、subprotocol `pbbp2` |
