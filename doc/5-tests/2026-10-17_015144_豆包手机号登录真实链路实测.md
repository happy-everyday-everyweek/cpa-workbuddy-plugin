# 豆包登录链路实测（浏览器取证 + 纯 HTTP 对照）

- 实测时间：2026-10-17
- 关联需求：`REQ-DOUBAO-PROVIDER-20261017`
- 关联前序侦察：`doc/5-tests/2026-10-17_014158_豆包Passport手机号登录端点可行性侦察.md`
- 实测方式：真实手机号 + 真实短信验证码，经浏览器完成登录，用 DevTools 网络日志 + 页面内 `fetch` 取证；并对三条认证路径做**纯 HTTP 裸请求对照**
- 结论：**扫码路径纯 Go 可实现（无需风控签名）；手机号路径需浏览器风控签名** —— 技术推荐扫码，但**用户已裁定采用「复用用户浏览器登录态」，插件内不实现登录**（见 §5）

## 0. 重要更正（2026-10-17 补测）

**本文档初版结论有误**：初版仅测试了 `www.doubao.com` 域的 `send_code`（返回 1003），据此判定「手机号登录必须依赖浏览器风控签名」，并据此推荐选项 A（内嵌浏览器，270MB）。**该前提未经验证充分——未测 `accounts.doubao.com` 域下的扫码端点，也未做扫码与手机号的裸请求对照。**

**补测后的正确结论**：

| 认证路径 | 裸 HTTP 请求（无任何签名） | 风控要求 |
|---|---|---|
| **扫码 `get_qrcode`** | `error_code=0`（成功，返回 token + qrcode_index_url + expire_time） | **无需签名** |
| **扫码 `check_qrconnect`** | `error_code=3`（缺 token 参数，非风控拒绝） | **无需签名** |
| 手机号 `send_code` | `error_code=1003`（手机号错误） | **需 `a_bogus`/`sign`/`qs` 风控签名** |

**即：扫码链路纯 Go 可实现，零浏览器依赖、零风控签名** —— 这正是 rex-zsd 能用纯 Go `.so` 实现扫码登录的原因。**选项 A（内嵌浏览器 270MB）不再必要。**

## 1. 关键结论（按重要性）

### 1.1 【更正后核心结论】扫码路径纯 HTTP 可跑通

实测 `accounts.doubao.com` 域下扫码端点，**裸请求（仅 UA + Referer，无任何签名）**：

```text
GET  /passport/web/get_qrcode/?aid=497858&next=https%3A%2F%2Fwww.doubao.com&device_platform=web&language=zh&region=CN&sys_region=CN
  → error_code: 0
  → token: "096557a714540aa005b59c8eabf749be_lf"（35 字符）
  → qrcode_index_url: "https://www.doubao.com/flow-account/scan-login?biz_aid=..."
  → expire_time: 1792173725
  → copywriting: {"title":"请使用已登录账号的设备扫码","desc":"...请使用「抖音 APP」扫码验证..."}

GET  /passport/web/check_qrconnect/?aid=497858&token=<token>&...
  → status: "new", error_code: 0     ← 轮询链路通（未扫码状态）
```

**完整扫码闭环（取码 → 轮询）已用纯 Python urllib 验证通过**，无浏览器、无签名、无 SDK。

### 1.2 手机号路径确实需要浏览器风控签名（原结论对手机号成立）

手机号 `send_code` 在 `accounts.doubao.com` 域下**裸请求仍返回 1003**，真实浏览器请求则携带 `msToken` + `a_bogus` + `sign` + `qs` + `verifyFp` 等一整套参数（`a_bogus`/`sign`/`qs` 由 `webmssdk.es5.js` 在浏览器动态生成）。

**即：风控签名要求只存在于手机号路径，不存在于扫码路径。**

### 1.3 手机号登录本身是官方正常路径

浏览器实测完成完整登录：填手机号 → 收到真实短信 → 填验证码 → 选择账号 → 进入对话界面（`is_login: true`）。登录弹窗明确提供「手机号登录」入口。**技术可行，但对本插件不是最优路径**（见 1.1）。

### 1.4 登录后会话有效，IM 链路可达（GAP-001 部分关闭）

登录后用会话直连 IM 端点，实测：

```text
POST https://www.doubao.com/alice/basic/launch
  → HTTP 200, code: 0, is_login: true, country: "CN", model_list: 67 条
```

**关键**：`/alice/basic/launch` 返回 `code: 0` 且带 `model_list`，证明**登录会话可直接用于业务 API**。

**`flow_cur_user_sec_id` 存在**（`document.cookie` 可读，非 HttpOnly）——这是 Lxapk 版 `validate()` 硬校验的字段，也是 GAP-001 的核心。**扫码与手机号两条路径均能得到该字段**（同为 Passport 会话），GAP-001 的核心担忧（会话不带该字段）**已被否定**。

### 1.5 真实端点清单（与 Lxapk 版有差异）

实测抓到的真实端点，**与 Lxapk 版代码有出入**：

| 用途 | 实测真实端点 | Lxapk 版使用 | 差异 |
|---|---|---|---|
| 业务启动 | `/alice/basic/launch` | `/alice/user/launch` | **不同** |
| IM 启动 | `/alice/im/launch` | 未用 | 新增 |
| 对话补全 | `/chat/completion` | `/im/send/message` | **不同** |
| 拉取会话 | `/im/chain/recent_conv` | 同 | 一致 |
| 拉取消息 | `/im/chain/single` | 同 | 一致 |
| 会话管理 | `/im/conversation/batch_get`、`/info`、`/modify` | 部分 | 新增 |
| 限流查询 | `/im/message/send_rate_limit` | 未用 | 新增 |
| 已读标记 | `/im/message/mark_conv_read` | 同 | 一致 |
| 用户资料 | `/alice/profile/self` | 未用 | 新增 |

**结论**：Lxapk 版（2026-10-02）的端点路径**已部分过时**，实现前必须以本次实测清单为准。这印证了原 GAP-002（协议时效性）。

### 1.6 其他实测发现

- **HttpOnly 分布**：`sessionid` / `sessionid_ss` / `sid_tt` / `sid_guard` / `uid_tt` / `odin_tt` / `d_ticket` / `ttwid` 均为 **HttpOnly**（`document.cookie` 不可见）；`flow_cur_user_sec_id` / `passport_csrf_token` 非 HttpOnly。
- **模型清单字段**：`model_list` 的 `model_name` / `name` 字段实测返回**非 ASCII 可读值**（如 `Aoe`、`anceba`），提示响应可能经编码层（Lxapk 走 `qoderEncode` 类编码），需进一步解包。
- **测试账号状态**：该账号「当前订阅已过期 6 天」，但 `/alice/basic/launch` 仍返回 `code:0` —— 说明**基础对话能力不依赖订阅**，但生图/生视频等高级能力可能受限（未验证）。
- **风控参数在业务请求上同样存在**：`/alice/*` 业务请求的 query 也带 `msToken` + `a_bogus`（见网络日志），但实测用**省略这两个参数的 fetch** 调 `/alice/basic/launch` **仍返回 `code:0`** —— 说明**业务 API 的风控宽松**。结合 1.1 的扫码结论，**全链路（扫码登录 + 业务调用）均可纯 Go 实现，无需浏览器**。

## 3. 认证路径选型结论（更正）

**推荐：扫码路径（纯 Go 实现）**。三条路径实测对照：

| 路径 | 纯 Go 可行性 | 浏览器依赖 | 用户操作 |
|---|---|---|---|
| **扫码（推荐）** | ✅ 实测 `error_code=0` 跑通 | 无 | 用豆包 App 扫面板二维码 |
| 手机号 | ❌ 需 `a_bogus`/`sign`/`qs` | **需浏览器**（270MB） | 输入手机号 + 验证码 |
| 复用浏览器 Cookie | ⚠️ 可用但凭据是一次性快照 | 需用户手工导出 | 手工抓 Cookie |

**扫码路径优势**：零浏览器依赖（保持插件 7.7MB 轻量）、零风控签名逆向、会话可续期（配合 Cookie Jar 写回）、用户操作直观。

**原「选项 A（内嵌浏览器 270MB）」不再需要** —— 该方案是为绕开手机号风控签名而提出，但扫码路径本身无此约束。

## 5. 用户裁定（2026-10-17，覆盖 §3 技术推荐）

§3 的技术推荐是**扫码路径**（零浏览器、零签名）。用户裁定为**选项 1：复用用户浏览器登录态**，理由与落地口径：

| 项 | 裁定内容 |
|---|---|
| 认证路线 | 复用用户浏览器登录态（用户在自有浏览器登录豆包，凭据导入插件） |
| 插件内登录 | **不实现**——不调 `send_code`/`sms_login`、不内嵌浏览器、不扫码 |
| 扫码路径 | 技术可行（§1.1 已实测），但需「抖音 APP」扫码，用户不采用；**作为备选保留** |
| 手机号路径 | 弃用（需浏览器风控签名，正是 GAP-008 的成因） |
| 导入可行性 | 由用户从浏览器侧导出 Cookie；关键 Cookie 为 HttpOnly，页面 JS 不可读，故必须用户侧导出（详见需求文档 GAP-009） |

**对 GAP 的影响**：GAP-008（登录强依赖浏览器）**关闭**——登录移出插件后该约束对插件不成立；GAP-007（缺先例）**改判**——Lxapk 走的正是此路线，先例存在，本需求修补其「只发不收、无续期、无 failover」三个硬缺口。

**技术事实与用户裁定的关系**：§3 推荐扫码是**纯技术最优**（对插件最轻），用户选择登录态导入是**产品决策**（对用户最熟、与 Lxapk 生态一致、无需装抖音 APP）。两者不冲突——本需求按用户裁定落地，扫码作为备选路径记录在案。

## 6. v1.4 复查验证（2026-10-17 二次探测）

对需求文档 v1.3 的关键假设做逐条复验，**发现 2 个阻断级问题 + 修正 1 个错误判据**。

### 6.1 【阻断级修正】登录判据端点错误

**原需求 AC-001 判据**（抄自 Lxapk 的 `client.go:launch`）：「`/alice/basic/launch` 返回 `code:0` 且 `sec_user_id` 非空」。

**实测推翻**：

| 探测 | 结果 |
|---|---|
| 未登录裸请求 `/alice/basic/launch` | `{"code":0,"msg":"","data":null}` —— `code:0` 但无数据 |
| 伪造 Cookie（`sessionid=fake...`） | `code:0`、**`is_login:false`**、`model_list:67` —— **仍返回 67 条模型** |
| 响应字段探测 | `sec_user_id` **在该端点根本不存在**（`absent`） |
| 有效会话 | `code:0`、`is_login:true`、`model_list:67` |

**结论**：`code:0` 完全无区分度（未登录也是 0）；`model_list` 也无区分度（未登录也有 67 条）；`sec_user_id` 在该端点不存在。**原判据三个要素全部失效。**

**正确判据（已实测验证区分度）**：

```text
GET https://accounts.doubao.com/passport/account/info/v2/
  ?pc_version=3.41.4&version_code=20800&language=zh&device_platform=web
  &aid=497858&real_aid=497858&pkg_type=release_version&use-olympus-account=1
  &region=CN&sys_region=CN&account_sdk_source=web&sdk_version=2.2.10
  &doubao_from=inject_html

有会话 → message: "success", data.sec_user_id 非空（76 字符）+ user_id + mobile + screen_name
无会话 → message: "error", data 无 sec_user_id
```

### 6.2 【阻断级新增】`/chat/completion` 请求体契约未解明

`/chat/completion` 实测行为：
- 页面真实请求：`Content-Type: text/event-stream`（SSE 流式），带 `fp` / `tz_name` 等参数
- 省略 `msToken`/`a_bogus` 调该端点：**能建立 SSE 流**（未触发签名校验），但缺参数返回 `STREAM_ERROR: 710020202 common invalid param`
- 按 Lxapk 记录的形态构造（`content_block` 数组 + `mode_id:"1"`）仍返回 `710020202`
- **页面真实请求体未被捕获**——SPA 模块持有原始 `fetch` 引用，注入的拦截器未生效；页面导航会清空拦截器

**处置**：需通过 DevTools 手动抓取真实请求体，或从豆包前端 JS bundle 提取构造逻辑。**未解明前不得编码。**

### 6.3 【已修正】模型名编码层（AC-003 新增障碍）

`model_list` 共 67 条但 `name` 字段**仅 26 个 distinct 值**，且非可读：

```text
样本：Aoe, anceba, "anceba an", ogt, ogf, xmm, "ances sc", "ances ci", ...
字段：{model_name, model_type, name, support_pic_gen_switch, support_web_search_switch, typewriter_switch}
```

`model_type` 为数字 ID（如 `1737521813`）。须解明编码层才能产出可读模型名。

### 6.4 【已验证】协议约束 1 仍有效（重要利好）

对 `/im/chain/recent_conv` 做 `Content-Type` 四变体对照：

| Content-Type | 返回 |
|---|---|
| `application/json; encoding=utf-8` | `712012003 不支持CMD类型` ← **编码校验通过** |
| `application/json; encoding=UTF-8` | `712012002 不支持编码类型` |
| `application/json; charset=utf-8` | `712012002 不支持编码类型` |
| `application/json` | `712012002 不支持编码类型` |

**证明 Lxapk 记录的 `encoding` 参数名（非 `charset`）要点仍适用**，且值必须精确为小写 `utf-8`。

### 6.5 【已新增】业务 API 需完整 query 参数集

同一端点 `/alice/basic/launch` 的对照：

| 请求形态 | 结果 |
|---|---|
| 仅 UA + Content-Type + `{}` | `{"code":0,"data":null}` |
| 补完整 query 参数集（无签名） | `code:0` + 完整 data（含 `model_list:67`） |

完整参数集（须与凭据一同持久化）：

```text
version_code=20800&language=zh&device_platform=web&doubao_device_platform=web
&aid=497858&real_aid=497858&pkg_type=release_version
&device_id=<设备ID>&pc_version=3.41.4&doubao_pc_version=3.41.4
&web_id=<web标识>&tea_uuid=<tea标识>&region=CN&sys_region=CN
&samantha_web=1&web_platform=browser&use-olympus-account=1
```

**其中 `device_id` / `web_id` / `tea_uuid` 为设备级标识**——多账号若共用同一组可能被关联（GAP-004 新增风险）。

### 6.6 【已确认】端点特异性：风控宽松度非全局一致

| 端点 | 无签名调用结果 |
|---|---|
| `/alice/basic/launch` | `code:0` + 完整 data |
| `/alice/im/launch` | `code:0` + 3.6KB 配置 |
| `/chat/completion` | 能建 SSE 流 |
| **`/alice/profile/self`** | **`710010202 系统错误`** ← 非宽松 |

**结论**：不得假设全链路宽松，须逐端点验证。

### 6.7 【部分验证】AC-002 续期前提

| 端点 | Set-Cookie |
|---|---|
| `accounts.doubao.com/ttwid/check/` | **有** —— `gd_random=...; HttpOnly; Path=/; Max-Age=604800` |
| `accounts.doubao.com/passport/token/beat/web/` | 无 |
| `www.doubao.com/alice/basic/launch`（假凭据） | 无 |

**结论**：`accounts.doubao.com` 域确有滚动下发行为（证明 Cookie Jar 写回有实际收益），但**会话主 Cookie（`sessionid`/`sid_guard`）的续期路径尚未验证**。若主 Cookie 不滚动下发，AC-002 须降级为「长有效期 + 失效重导入」。
