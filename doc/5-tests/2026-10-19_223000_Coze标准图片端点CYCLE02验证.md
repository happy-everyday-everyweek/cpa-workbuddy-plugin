# Coze 标准图片端点（CYCLE-02）验证

- 日期：2026-10-19
- 版本：`coze-provider 0.5.0`
- 关联实施总览：`doc/3-实施/2026-10-18_221134_Coze插件图片生成链路打通_实施总览.md`（`CYCLE-02`）
- 关联 AC：`AC-104`、`AC-105`、`AC-106`

## 1. 问题与根因

用户现象：new-api 图片页调用失败，报文为
`CLI 通道返回 503：该中转商没有可用的 gpt-image-2.5-sunburst 上游（coze 提供方不接受 openai-image 格式）`。

生产实测确认这是**两处叠加的宿主闸门**，且都不在插件内的业务逻辑：

| 编号 | 现象 | 根因 | 代码位置 |
| --- | --- | --- | --- |
| A | 原名 `coze/doubao-seedream-5-0-260128` 请求 → HTTP 400 `Model ... is not supported` | 模型 `Type` 是 `"image"`，而图片白名单只认 `"openai-image"` | 宿主 `openai_images_handlers.go:252-259` `isOpenAICompatImagesModel` |
| B | 别名 `gpt-image-2.5-sunburst` 请求 → HTTP 500 `plugin executor coze-provider does not support input format "openai-image"` | 插件 `ExecutorInputFormats` 只声明了 `["openai"]` | 宿主 `adapters_executors.go:462-475` `selectExecutorInputFormat` |

两条路径的实测报文（发布前）：

```
# 原名
400 {"error":{"message":"Model coze/doubao-seedream-5-0-260128 is not supported on /v1/images/generations or /v1/images/edits...","type":"invalid_request_error"}}

# 别名（模型名命中 Codex 硬编码白名单，穿过 A 但撞上 B）
500 {"error":{"message":"plugin executor coze-provider does not support input format \"openai-image\"","type":"internal_server_error"}}
```

## 2. 修复

- `coze/models.go`：`modelListTypes` 的 `image_generation` 映射、`hostTypeForCapability("image_gen")`、
  **以及静态兜底目录 `staticFallbackModels`** 三处统一改为 `openAIImageModelType = "openai-image"`。
  静态兜底是本地验证时发现的遗漏：只改动态发现会出现「有账号可用、无账号 400」的双轨不一致。
- `coze/main.go`：`ExecutorInputFormats` / `ExecutorOutputFormats` 增加 `"openai-image"`。
- `coze/images.go`（新增）：请求解析、尺寸/张数翻译成提示词、`{created,data[]}` 响应构造、
  `b64_json` 真实下载后编码、下载域名白名单。
- `coze/executor.go`：入口按 `Format` / `SourceFormat` 分流到 images 路径，
  不与 chat 解析混用（images 请求没有 `messages`）。

### 变异反证（5 项，全部精确失败）

| 变异 | 改法 | 命中用例 |
| --- | --- | --- |
| M1 入口分流失效 | `if isImagesExecution(req)` → `if false && ...` | `TestHandleExecExecuteDispatchesImagesBeforeChatParsing` → `请求缺少 messages` |
| M2 类型回退 | `image_gen` 返回 `"image"` | `TestImageModelTypeIsOpenAIImage` + `TestHostTypeForCapability` |
| M3 SSRF 白名单调用点被删 | 移除 `verifyImageHost` 调用 | `TestDownloadImageBase64RefusesNonCozeHost` |
| M4 吞掉下载失败 | `if errDownload != nil` → 忽略 | `TestBuildImagesResponseB64PropagatesDownloadFailure` |
| M5 响应格式口径 | 默认值改 `"url"` | `TestImagesResponseFormatDefaultsToB64` |

**方法论教训**：M1 与 M3 第一版都**没被抓到**——单函数用例只测函数本身，抓不到「调用点被删」。
两处都补了经过真实入口的用例后才精确失败。只测纯函数的变异反证是不充分的。

## 4. 生产验收

部署：`plugin-store install?version=0.5.0` → `restart_required=false`，
`plugin hot reloaded active_version=0.5.0 retired_version=0.4.6`，**容器未重启**。
落盘 `.so` sha256 `2c54b7e4eee425f11444ff61cf9e4aea06141b693dabb029202de2d264c2cf4f`
与本地 release zip 内一致。

### 4.1 直连 CPA（`http://127.0.0.1:8317`）

| 场景 | 结果 |
| --- | --- |
| 原名 + `response_format=url` | HTTP 200，`created` + `data[0].url`（`static.coze.site`） |
| 图片可下载 | HTTP 200、`image/jpeg`、374,554 字节、JPEG 魔数 `ffd8ff` |
| 别名 `gpt-image-2.5-sunburst` + `b64_json` | HTTP 200，base64 解码 477,991 字节、魔数 `ffd8ff` |
| 对话链路回归 | HTTP 200，`content=可用`，usage 正常 |

### 4.2 经 new-api（`http://127.0.0.1:5566`，渠道 6「生图」）

| 别名 | 映射到的 CPA 模型 | 结果 |
| --- | --- | --- |
| `gpt-image-2` | `coze/doubao-seedream-5-0-260128` | HTTP 200，`data[0].url` |
| `gpt-image-2.5-flare` | `coze/doubao-seedream-5-0-260128` | HTTP 200，`data[0].url` |
| `gpt-image-2.5-sunburst` | `coze/doubao-seedream-5-0-pro` | HTTP 200，`data[0].url` |

稳定性：同一模型连续 5 次，**5/5 成功**，全部返回 `static.coze.site` 图片直链。

### 4.3 期间观测到的偶发失败（非缺陷）

第一次经 new-api 调用 `gpt-image-2.5-sunburst` 返回
`{"error":{"message":"上游未返回任何图片",...}}`，CPA 日志显示同一账号
`duration=13~51s` 后失败。该文案来自插件 `images.go:170`，
即请求确实到了插件、到了上游，但上游这轮没有产出附件。

接着用**完全相同的模型与提示词**直连 CPA 成功，随后 3 个别名各 1 次、
同一模型连续 5 次全部成功。判定为**上游生图的模型自主性偶发**（对话模型未必每轮都调用生图工具），
不是插件或宿主缺陷。已知限制：当前无法从协议层强制上游必须出图，
失败时返回明确错误而不是空结果。

## 5. 遗留与边界

- `n>1`：扣子一轮对话产出一组图，插件把 `n` 写进提示词（`请生成 N 张不同的图片`），
  但**不保证上游真的产出 N 张**；当下游要求精确张数时存在偏差。
- `size` 同样是提示词约束，不是上游参数。
- 编辑端点（`/v1/images/edits`）未实现：本次只做 `/v1/images/generations`。
- `b64_json` 会增加一次下载与 base64 膨胀（约 1.33 倍），大图时响应体明显变大。
