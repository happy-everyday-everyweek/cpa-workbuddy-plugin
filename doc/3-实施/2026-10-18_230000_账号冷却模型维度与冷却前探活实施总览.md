# 需求实施总览：账号冷却模型维度与冷却前主动探活

结论：把账号冷却从「纯账号维度」升级为「账号维度 + 账号×模型维度」双层结构，并在冷却窗口临近结束时对冷却账号发起一次主动探活——成功则解除冷却，失败则继续阶梯递增——从而避免恢复冷却的账号再次被路由到、白白消耗请求时间后再次失败。影响：workbuddy / workbuddy-ai / traework / zcode / copilot 五个非 Qoder 插件（Qoder 系因 110 日限额禁止后台探活而排除）；范围：失败分类边界、冷却状态结构、冷却判定调用面、探活触发时序、探活模型选择；非范围：Qoder 系（qoderwork / qoder-ai）任何探活逻辑、`test_failed` 标签语义、上游配额规则、宿主侧跨 provider 重试白名单。

---

## 1. 当前计划最终方案简要说明

- 推荐方案一句话结论：冷却仍是账号维度，但新增「账号×模型」子维度只在失败可归因到模型时记录；冷却窗口到期前由独立探活循环主动探测，探测成功解除冷却、失败继续递增，绝不写 `test_failed`。
- 主落点 / 主路径：`<plugin>/accountFailover.go`（状态结构 + 判定函数 + 记账函数）、`<plugin>/active_ping.go`（模型指定探活 + 成功清冷却）、`<plugin>/failover_retry.go` 与 `<plugin>/scheduler.go`（冷却判定带模型参数）、新增 `<plugin>/cooldown_probe.go`（冷却到期前探活循环）。
- 为什么先走这条路线：冷却状态与判定函数已经是同族插件的稳定结构，扩维是局部改动；而 400 / 客户端取消 / 模型级故障这三类不能进冷却的边界必须先固定，否则扩维后会把误判放大成整池不可用。

## 2. 基本信息

- 对应需求文档：用户实时需求对话（2026-10-18「失败进入冷却的问题」「只要失败就进入冷却可行吗」「探活就也应该用失败模型」）
- 来源对象标识：REQ-COOLDOWN-MODEL-SCOPE-20261018
- 当前实施文档命名主干：`2026-10-18_230000_账号冷却模型维度与冷却前探活实施总览`
- agent 理解的问题 / 目标：账号失败后进入冷却，但冷却到期时无法判断它是否真的恢复；恢复后的首次业务请求会再次打到仍然故障的账号，既消耗客户端等待时间（截图实测单次 4.5–10.3 秒）又再失败一次。目标是在冷却结束前主动验证，把「验证成本」从业务请求转移到后台一次性探测。
- 当前计划范围：
  1. 固定失败分类边界（哪些失败进冷却、哪些不进）；
  2. 冷却状态扩为账号维度 + 账号×模型维度；
  3. 冷却判定与换号选择带模型参数；
  4. 冷却到期前主动探活（含失败继续递增、成功清冷却）；
  5. 探活使用当初失败的模型；
  6. 自激防护与探测次数上限。
- 明确不在范围：
  1. Qoder 系（`qoderwork` / `qoder-ai`）的任何自动探活——会触发上游 110 日调用限额（见 `qoderwork/active_ping.go:3` 的历史记录）；
  2. `test_failed` 标签语义与过期策略——探活失败一律不写该标签；
  3. 宿主侧跨 provider 重试白名单与 `MarkResult` 冷却时长分支；
  4. 400 / 422 请求形状错误的根因修复（属独立缺陷，见第 6 节）。
- 当前优先闭环：先固定失败分类边界与冷却状态扩维，再接入探活循环；400 的根因定位并行推进。
- 关键假设 / 已确认点（均见第 10 节）：
  1. **已确认**：接受「放宽后的失败边界」——只有可归因到账号或账号×模型的失败才进冷却；400/422（正文无标记）、客户端取消、已泄漏正文后的断流不冷却；
  2. **已确认**：探活必须使用当初失败的模型，不是任意模型成功即算恢复；
  3. **已确认**：不对探测加 `count >= 3` 门槛——只要进入冷却就探测；
  4. **已确认**：探测触发点为「冷却到期前 5 秒」，不是到期后立即探测（后者等于把首次探测成本推给业务请求）；
  5. **已确认**：账号×模型冷却**不**在面板上单独展示，面板继续只展示账号级冷却。

## 3. 失败分类边界（已确认）

| 失败类型 | 是否进冷却 | 维度 | 依据 |
|---|---|---|---|
| 传输错误（status 0） | 是 | 账号 | 现有 `isAccountFailure` |
| 5xx | 是 | 账号 | 现有 |
| 429 / 限流文案 | 是 | 账号×模型 | 限流通常按账号+模型生效 |
| 401 / 403 / 404 / 405 | 是 | 账号 | 凭据或权限问题与模型无关 |
| 硬额度（402 / 额度标记） | 是 | 账号 | 额度耗尽换模型也不可用 |
| HTTP 200 内的账号级错误帧 | 是 | 账号×模型 | 业务错误帧多与模型/配额绑定 |
| 零字节断流 | 是 | 账号×模型 | 现有 `isTransientThrottle` |
| 400 / 422（正文无标记） | **否** | — | 请求形状问题，换账号同样失败 |
| 400 / 422（正文含明确限流标记） | 是 | 账号×模型 | 部分网关用 400 承载限流，正文标记优先于状态码 |
| 400 / 422（正文含明确额度标记） | 是 | 账号 | 额度耗尽与状态码无关，换模型同样不可用 |
| 客户端取消 / emit 失败 | **否** | — | 用户主动断开，非账号故障 |
| 已向客户端泄漏正文后的断流 | **否** | — | 无法换号重试，也不代表账号坏了 |
| 同一模型跨多账号短窗口失败 | **不逐个冷却** | 模型级抑制 | 模型级故障，冷却账号只会放大成整池不可用 |

**理由**：当前 [workbuddy-ai/accountFailover.go:147](file:///f:/cpa-plugin/workbuddy-ai/accountFailover.go#L147) 的 `isAccountLevel4xx` 只含 401/403/404/405/429，400 已被排除——这个边界保持不变。扩维只改变「记到哪个维度」，不改变「哪些失败计数」。

**判定优先级（T-1 裁定，2026-10-18）**：正文标记优先于状态码。`isHardCreditError` 与
`isSoftRateLimit` 先扫描正文，因此 400/422 携带 `quota exceeded`、`insufficient credit`
等额度标记时归账号级，携带 `too many requests`、`rate limit` 等限流标记时归账号×模型级；
只有正文无标记时才按「请求形状」放行不记账。该口径已在
`failure_class.go` 的 `classifyUpstreamFailure` 与 `TestClassifyUpstreamFailureTable` 中锁定。

## 4. 冷却状态扩维设计

### 4.1 现状

```go
// workbuddy-ai/accountFailover.go:53
type authFailoverState struct {
    count         int
    cooldownUntil time.Time
}
```

`failoverStates` 是 `map[string]*authFailoverState`，键为账号 ID。**没有模型维度。**

### 4.2 目标结构

```go
type authFailoverState struct {
    count         int
    cooldownUntil time.Time
    lastModel     string   // 最近一次触发冷却的上游模型（用于冷却前探活）
    modelStates   map[string]*modelFailoverState  // 账号×模型级冷却
}

type modelFailoverState struct {
    count         int
    cooldownUntil time.Time
}
```

- 账号级字段保持原语义不变，避免影响面板与既有测试；
- `modelStates` 仅在失败被判定为模型级时写入；
- `lastModel` 记录最近一次触发冷却的上游模型（已过 `resolveUpstreamModel` 归一化的上游名，不是客户端别名），供探活回放。

### 4.3 判定函数

- `isAccountCoolingDown(authID)` 保持现有签名（账号维度，供面板与全池让位使用）；
- 新增 `isAuthModelCoolingDown(authID, model string) bool`；
- **调度与换号必须改用后者**：`scheduler.go:119`、`failover_retry.go:60`、`stream.go:120/364`、`main.go:580`。否则同请求内换号仍会选到「该模型冷却中」的账号。

### 4.4 调用面清单（workbuddy-ai 实测）

| 文件 | 行 | 用途 | 是否需带模型 |
|---|---|---|---|
| `scheduler.go` | 119 | 调度候选过滤 | 是 |
| `failover_retry.go` | 60 | 同请求换号 | 是 |
| `stream.go` | 120 | 流式前置拦截 | 是 |

## 5. 冷却前主动探活设计

### 5.1 触发时机

- **已确认不接受** `count >= 3` 门槛：只要进入冷却就探测；
- 触发点：`cooldownUntil - 5s`（**已裁定**），保证最小时长 30s 的冷却也有 25s 的准备窗口；
- 冷却到期后若探测仍未完成，正常放行（不能因为探测慢而延长冷却）；
- **探测前置条件**：仅对「账号级冷却」探测。若该账号最后一次失败被判为模型级风控（见 11.2 的 11128），不探测——探测只会复现同样拦截。

### 5.2 探活内容

- **必须使用 `lastModel`**（当初失败的上游模型）；
- 请求形态复用现有 `sendActivePingWorkbuddy`：`hi` + `stream:true` + `max_tokens` 经 `applyMaxTokensFloor` 拉到 32768 底线；
- 首字节或首个有效帧到达即判定成功，随后异步关闭流（现有实现已如此，见 [active_ping.go:181](file:///f:/cpa-plugin/workbuddy-ai/active_ping.go#L181)）；
- 超时沿用 `defaultActivePingTimeout`（20s），但探测不得阻塞任何业务请求。

### 5.3 结果处理（关键，现有实现有缺口）

| 探测结果 | 动作 | 现有实现 |
|---|---|---|
| 成功 | `resetAccountFailover(authID)` + 清该模型冷却 | **缺失**：workbuddy / workbuddy-ai 探活成功只清 `test_failed`，不清冷却；zcode 已清（[zcode/active_ping.go:250](file:///f:/cpa-plugin/zcode/active_ping.go#L250)） |
| 失败 | `recordAccountFailure(authID, status, body)` 继续阶梯递增 | **缺失**：探活失败只写 `test_failed`（必须移除该行为） |
| 失败且账号仍有积分 | **不得写 `test_failed`** | 现行为相反：`doActivePing` 全模型失败且有积分 → `persistTestFailedToggle(..., true)`（[active_ping.go:237](file:///f:/cpa-plugin/workbuddy-ai/active_ping.go#L237)） |

**这是本方案最高风险点**：若直接复用现有 `doActivePing`，探测失败会把账号打进 `test_failed`（硬排除、永不自动过期，见 [scheduler.go:119](file:///f:/cpa-plugin/workbuddy-ai/scheduler.go#L119)），比冷却严重得多。冷却前探活必须是**独立函数**，不复用 `doActivePing` 的标签写入路径。

### 5.4 自激防护

- 每个账号的探测次数上线（建议每个冷却周期最多 1 次）；
- 探测失败后冷却继续递增，下一次探测跟随新的 `cooldownUntil`，不会连续触发；
- 探测本身失败**不**消耗 `activePing` 的 4 小时节流（那是另一套机制），但需要独立的探测计数，防止「探测失败 → 冷却递增 → 再探测」在极端情况下高频循环。

### 5.5 实现位置

新增 `<plugin>/cooldown_probe.go`，由现有 watchdog 循环驱动（`watchdogIntervalDefault = 10 分钟` 的粒度对 30s 冷却太粗），因此需要独立的 `time.Ticker`（建议 5s 或 15s 粒度），只遍历 `failoverStates` 中即将到期的条目——不能每 tick 遍历全部账号。

## 6. 并行排查项：那批 400 的真实归因

截图显示 2026-10-18 21:54:06–21:54:10 期间，`deepseek-v4.1-flash` 在 workbuddy-ai-provider 上跨 5 个账号连续失败，400 与 429 混杂，耗时 4.5–10.3 秒。**这批请求当前完全不进冷却、不换号**（[stream.go:167](file:///f:/cpa-plugin/workbuddy-ai/stream.go#L167) 的 `!isAccountLevel4xx` 分支直接 `emitError` 返回）。

### 6.1 已确认的事实

1. **400 不记账 → 不清会话绑定。** `evictSessionBindingsForAuth` 只在 `noteAccountFailure` 返回 true 时调用（[lifecycle.go:532](file:///f:/cpa-plugin/workbuddy-ai/lifecycle.go#L532)），而 400 被 `isAccountFailance` 排除 → 绑定保留 → 同一会话在下一轮仍被亲和钉回同一批账号。这是「反复失败却不换号」的直接机制。
2. **`deepseek-v4.1-flash` 是三服务商同名认领模型。** 历史诊断 `doc/4-bugs/2026-10-11_212700_deepseek多服务商同名认领导致推理零首字节断开根因诊断.md` 已确证：workbuddy / workbuddy-ai / traework 三家都通过动态发现认领该名字，`owned_by` 归属取决于登记顺序。**该结论今日仍成立**——三个插件的模型列表仍走动态发现，该名字不在任何静态列表中。
3. **模型级故障无任何抑制机制。** 全仓检索 `modelFailover` / `modelCooldown` / `modelCircuit` 零命中，当前只有账号级冷却。

### 6.2 待取证

1. **400 的响应正文**——决定归入「请求形状」还是「账号×模型不可用」；
2. 该时段是否真的发生了模型级过载，还是请求本身有问题（两者处理路径完全不同）。

### 6.3 可用的治理入口

- `oauth-excluded-models`：宿主配置，按 provider 定向摘除模型；插件侧 `filterExcludedModels`（[models.go:420](file:///f:/cpa-plugin/workbuddy-ai/models.go#L420)）已实现，但只影响 `model.static` / `model.for_auth` 的返回，**不影响运行期路由**，因此不能替代模型级熔断；
- 若取证确认是模型级故障，建议先在运维侧用该配置摘除，再决定是否在插件内做运行期熔断。

**这一项独立于本方案**，但收益比探活大：它直接消除截图里的主要失败形态。

**与 `active_ping` 的硬边界**：`doActivePing` 在失败时会写 `test_failed`（硬排除、

**参数与触发**

| 项 | 取值 | 说明 |
|---|---|---|
| `cooldownProbeLeadTime` | 5s | 用户裁定：到期前 5 秒 |
| `cooldownProbeInterval` | 5s | 必须远小于最短冷却 30s，否则 30s 档位整轮错过 |
| 探测模型 | `state.lastModel` | 必须回放当初失败的模型 |
| 探测范围 | 仅账号级冷却 | 模型级冷却不探测——模型级失败重试无法自愈 |
| 每周期次数 | 最多 1 次 | 以 `cooldownUntil` 作为周期标识 |

**结果处理**

- 成功：`resetAccountFailover` 清冷却与计数，账号立刻可承载流量；
- 失败：`recordFailureScoped(..., failureScopeAccount)` 沿阶梯递增；传入空模型，
  因此不会覆盖 `lastModel`，下一次探测仍用原模型；
- 解析不到凭据：跳过且**不标记已探测**，避免宿主 RPC 抖动让该账号整轮错过。

**轮次防堆积**：单轮可能阻塞到 20s 超时，远大于 5s tick。用
`TryLock` 实现「上一轮未结束就跳过本轮」，而非排队——排队只会造成重复探测。

**实施中发现并修复的真实缺陷**

初版在**探测前**用旧的 `cooldownUntil` 标记已探测。探活失败会沿阶梯延长冷却，
新周期因此被误判为「本周期已探测」而**永久跳过**——探活失败一次，该账号在后续
所有冷却中再也不会被探测。改为「先探测、再以最新 `cooldownUntil` 标记」，并把去重
判据从时间窗口比较改为周期标识直接相等比较。

**验证证据**

- 9 个单测：触发窗口 9 档边界（10s/6s/5s/1s/已过期/无模型/无冷却/已探测/跨周期）、
  成功清冷却、失败递增且延后、**任何路径不写 `test_failed`**、使用失败模型回放、
  模型级冷却不探测、每周期仅一次、解析失败不消耗配额、失败延长后新周期重新探测；

## 11. 生产取证结论：400 = 上游风控拦截，非账号故障

取证环境：生产容器 `cli-proxy-api`（`45.207.222.65:18998`，经 SSH 宿主机只读执行 `docker logs`），窗口 `--since 3h`（2026-10-18 19:20–22:22）。

### 11.1 硬证据

| 维度 | 实测值 |
|---|---|
| 错误码 | `{"code":11128,"msg":"request illegal", "displayMsg":{"zh":"请求被拦截，请重新发送"}}` |
| 出现次数 | **1,173 次**（3 小时内） |
| 涉及 provider | `workbuddy-ai-provider` **唯一一个**（2324 条匹配含重复行） |
| 涉及模型 | `deepseek-v4.1-flash` **1162 次**（占 99%+） |
| 涉及账号 | **20 个不同 auth_file**，分布高度均匀（55–73 次/账号） |
| 时间跨度 | 19:33:07 → 22:22:00 持续存在 |
| 响应耗时 | 主流 0.5–3.7s，最长 7.2s / 9.6s |

### 11.2 结论

**这是模型级 + provider 级的风控拦截，不是账号级故障。**

判据：
1. **20 个账号均匀命中**——账号级故障不可能让全池每个账号失败次数几乎相同（55–73 次）；
2. **只打一个 provider、一个模型**——同一批账号在其他模型上正常；
3. **文案是"请求被拦截"**——上游风控/内容安全拦截语义，不是鉴权、额度或限流；
4. **响应耗时 0.5–3.7s**——说明请求完整到达上游并被处理后被拒，不是连接层失败。

**因此**：
- 这批失败**不应触发账号冷却**（workbuddy 系实现正确：400 不进冷却；
  zcode / copilot 原本是无条件记账，已于周期 2 接入分类门禁后同样不再计入）；
- 但**必须触发模型级抑制**——同一 provider × 模型在短窗口内跨多账号出现 11128，应直接快速失败或摘除该模型，而不是继续轮转 20 个账号（**已于周期 5 实现**，见 `model_circuit.go`）；
- **冷却前探活对这批失败完全无效**——探测同样会被 11128 拦截（探测请求与业务请求同形），只会把探测本身也变成一次失败。

### 11.3 附带发现：11140 是账号级封禁信号

同一窗口内 8 次 `{"code":11140,"msg":"request illegal","displayMsg":{"en":"Your accoun...`（文案被截断，以 "Your account" 开头），且**全部由 workbuddy 的 `active ping` 触发**，集中在单一账号 `workbuddy-ca6b8da8-...`。

- 该错误码与 11128 语义不同（"Your account..." 指向账号），当前 `isAccountFailure` 只看 HTTP 状态码 403 → 会进入账号冷却，方向正确；
- 但**同一错误码 11140 用了 `request illegal` 的 msg**，若未来出现 HTTP 200 承载的变体，现有 body-marker 匹配可能漏判，需要补 marker。

### 11.4 时间损耗来源（对应截图 4.5–10.3s）

截图中单次 400 耗时 4.5–10.3s，而生产实测 11128 主体在 0.5–3.7s。差额来自：同一请求在多个账号间轮转重试（截图 21:54 前后多 trace 交叉），每次 1–3s 叠加。**不是单次请求慢，是失败重试链累加。**

## 12. 待用户裁定项

第 10 节三项已裁定。周期 1 实施中发现两项边界问题，处理状态如下：

**T-1：`400` 携带限流/额度文案时是否仍记账？—— 已裁定：维持现状（2026-10-18）**

- 裁定结论：**正文标记优先于状态码**，`classifyUpstreamFailure` 保持现有扫描顺序不变。
- 理由：限流与额度文案并不总配 429，部分网关统一用 400 承载。若按状态码一刀切排除 400，
  会漏掉真实限流，让被限流的账号继续被路由，反而放大失败面。
- 已落地：第 3 节表格已拆成「正文无标记 / 含限流标记 / 含额度标记」三行；
  分类函数与单测（`TestClassifyUpstreamFailureTable` 的 400 限流用例、
  `TestClassifyUpstreamFailureMatchesLegacyCountGate` 全枚举）已锁定该口径。
- 附带说明：`400 + 额度标记` 会同时触发硬额度生命周期（停用），这是既有行为，
  与本裁定一致，不另作调整。

**T-2：zcode / copilot 记账路径接入分类的时机 —— 已裁定并已落地（2026-10-19）**

- 裁定结论：**与周期 2 的冷却状态扩维同批落地，不单独提前、不推迟到周期 4。**
- 理由：分类门禁与「记到哪个维度」是同一处代码的两个判断。若先加门禁、后加维度，
  中间会存在一个「400 突然不记账、但模型维度尚未生效」的窗口，冷却行为发生无对应
  收益的变化；若推迟到周期 4，zcode / copilot 会长期带着与第 3 节冲突的记账边界。

**接入前必须处理的三个风险点**（已勘察确认，落代码时逐条核对）：

1. **流式读取错误用 200 记账，不能直接套门禁。**
   `zcode/stream.go:129` 与 `copilot/stream.go:117` 在 `err != io.EOF` 分支调用
   `noteAccountFailure(authID, resp.StatusCode, err.Error())`，而流式读取阶段
   `resp.StatusCode` 恒为 200。分类函数对 `200 + 无标记正文` 返回 `none`，
   直接加门禁会让真实断流（RST、超时）**不再计数**。
   处理方式：这两处必须改为传 `0`（传输层失败）或显式走 `isTransientThrottle` 分支，
   与 workbuddy-ai 的处理对齐——后者的读错误分支传的是 `0`
   （[workbuddy-ai/stream.go:149](file:///f:/cpa-plugin/workbuddy-ai/stream.go#L149)）。
   **这一条是本裁定里最容易出错的地方，必须以单测锁定断流仍会计数。**
2. **换号判定与记账顺序必须调整。** 当前两插件是「先记账、再判换号」
   （`zcode/executor.go:75`、`copilot/executor.go:71`）。接入分类后，400 天然不入账，
   顺序无需改动；但要确认 `shouldRotateOnUpstreamErr` 对 400 返回 false，
   否则会出现「不记账却仍换号」的不一致。已确认二者对 400 均返回 false，无需改动。
3. **哨兵用例必须随之改写。** `TestNoteAccountFailureStillCountsUnconditionally`
   当前断言「400 会进入冷却」，接入后必须改为反向断言（400 不冷却、400+限流标记冷却）。
   该用例失败即是「接入已完成」的信号，不允许在接入时直接删除。

**接入判定标准**：zcode / copilot 的 `noteAccountFailure` 或调用点出现分类门禁后，
`TestNoteAccountFailureStillCountsUnconditionally` 失败 → 改写为
`TestNoteAccountFailureHonorsClassification` 正向用例 → 全绿，三项同时成立才算接入完成。
