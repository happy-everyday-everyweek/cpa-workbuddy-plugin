# Qoder 系模型发现风暴与 OOM 修复（P0/P1/P2）实施总览

- 根因链诊断：`doc/4-bugs/2026-10-12_015500_Qoder模型发现接口COSY签名失效根因诊断.md`（§9 为本轮实施结论）。
- 约束：用户当轮明确 **不要发布生产**——不 dispatch CI、不更新 registry、不 plugin-store install、不重启容器；只做代码 + 真实单测 + 变异验证 + 文档回填。

## 1. 问题与目标

生产 `cli-proxy-api` 容器多次内核 OOM（exit 137）重启。归因修正后的完整链条：

1. `callModelsAPI` 签名声明 body 为 `qoderEncode("{}")`，但 GET 实际不带 body → 服务端恒判 `403 {"code":"101","message":"Signature invalid"}`（累计 5449 条，qoder-ai 5208 / qoderwork 241，从未成功过一次）。
2. 失败后**不写任何缓存**（只有成功才写 `dynamicModelsCache`）→ 宿主每次 auth 文件重写触发 `model.for_auth` → 逐账号全量重扫 → N+1 请求风暴（实测 8409 条）。
3. 次级放大器：`retry_on_4xx` 默认 10 且换号循环无退避；`readAllUpstreamErr` 无上限 `io.ReadAll`。

目标：消除风暴源头（P0）、切断风暴放大（P1）、压低次级放大（P2）。P3（容器内存上限 + swap）属运维侧，不在代码范围。

## 2. 关键决策与证据

### P0 修复方向裁定（签名与请求都带 body）

Bug 文档 §6 原本把「服务端对无 body GET 用哪个值校验」列为未直测。本轮以**可正常工作的外部实现**裁定：qoder2api-hub（`shuishuipingan/qoder2api-hub`，commit `fd7a3740`，`qoder_proxy.py::read_dynamic_models`）：

- `sign_body = qoder_encode(b"{}")` 同一字符串既进签名、又作为 GET 请求体发出（`Request(url, data=sign_body.encode("utf-8"), method="GET")`）；
- 其注释明确裸 GET 会被上游拒 403。

本地红线禁止用生产凭据直连上游补证，故以该参照 + 仓库内唯一成功路径（推理 POST：签名 body 与实际 body 同源）的一致性不变量为准。

### P1 负缓存窗口参数

- `dynamicModelsFailCacheTTL = 5min`，与正向 `dynamicModelsCacheTTL` 同量级：风暴期每账号事件的重扫被窗口挡住，上游恢复后 5 分钟内重新获得动态列表，不需要额外配置项（最小实现原则）。
- `markDynamicModelsFailed` 只在「真实向上游发起过尝试且全败」时置位（`scanned>0` / `attempted>0` / 单账号拒绝），无凭据、无账号不置位——避免把「本地没有账号」误判成「上游故障」。
- `storeDynamicModels` 成功即清零 `failedAt`。

### 注入缝 `callModelsAPIFn`

各插件新增包级函数变量（沿 `sendActivePingQoderFn` / `probePingFn` 既有惯例），生产路径默认指向真实现，测试注入假上游。生产代码测试污染扫描 PASS。

### P2 退避收口点

所有换号路径（执行器循环、流式循环、前置冷却拦截）都经过 `pickNextAuth` 唯一 chokepoint，在其选定候选、返回前统一 `time.Sleep(50ms)`——单点补齐，不改 21 个调用位。`readAllUpstreamErr` 对齐仓库惯例 `io.LimitReader(r, 1<<20)`（zcode / copilot / cursor / doubao 均如此）。

## 4.1 复核追加修复（2026-10-19 21:07）

首轮实现后按用户「再次检查本次会话的调整」复核，发现并修复一处自查缺陷：

- **缺陷**：qoder-ai / qoderwork / qwenwork 的 `fetchDynamicModelsFromStorage` 在「本账号调用被拒」分支先 `markDynamicModelsFailed()`、再 `return fetchDynamicModels()`。而 `fetchDynamicModels` 入口第一件事就是 `inDynamicModelsFailWindow()`，窗口刚被自身置位 → 回退恒被拦住返回 nil。函数注释声明的「回退到已注册凭据扫描」成为死路径：本账号凭据损坏/被限流时，另一账号本可成功的全量扫描永远走不到。
- **修复**：改为「先回退、回退无果再开窗」，并抽出调用点接缝 `fetchDynamicModelsFallbackFn`（包级函数变量，沿 `callModelsAPIFn` 惯例）。`parseStored` 失败分支同样回退且不开窗（保持 HEAD 语义，且不把「凭据不可解析」当成上游故障）。
- **回归**：新增 `TestNegativeCache_StorageFallbackRunsBeforeWindow`（三插件同构）。判据是回退桩复刻真实入口的窗口检查；变异（恢复「先开窗再回退」）→ `回退结果应被采用，got []` 精确 FAIL，还原后全绿。
- **复核已确认无问题的项**：P0 宿主转发链（`internal/pluginhost/http_bridge.go:156` 用 `bytes.NewReader(bytes.Clone(req.Body))` 重建请求，GET 携带的 body 会真实发出）；`storeDynamicModels` 成功清窗；`scanned>0` / `attempted>0` 才开窗（无账号不误判上游故障）；`pickNextAuth` 退避点在返回前且不持锁；面板/探活的直连调用（`authModelsForIndex` / `pickRandomQoderModels`）只由人工点按与定时探活触发，不在宿主 `model.for_auth` 热路径上。
