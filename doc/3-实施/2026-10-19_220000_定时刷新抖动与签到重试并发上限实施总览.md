# 4h 槽位随机抖动 + 签到重试并发上限 实施总览

- 编号：IMP-SCHEDULE-JITTER-RETRY-CAP-20261019
- 来源：用户当轮需求（2026-10-19），基于同会话的定时刷新并发盘点结论，用户逐项确认「需要」。
- 状态：**已发布**。代码 `8401b31` + notion 版本修正 `e353821` + registry `9117d7b`；
  7 个已启用插件已热重载到新版本（零容器重启），详见 §5。

## 1. 问题与目标

同会话盘点确认的两处风险：

1. **整点尖峰**：workbuddy / workbuddy-ai / traework / qoderwork / qoder-ai / qwenwork 的 4 小时槽位全部按**本地整点**对齐（00/04/08/12/16/20）。所有插件在同一秒醒来，叠加启动/热重载立即跑首轮的行为，整机峰值估算约 70–80 个上游请求同时在场，且与账号规模正相关。
2. **无界并发**：`traework/checkin_retry.go` 的 `checkinRetryLoop` 对每个到期账号直接 `go processCheckinRetry(e)`，是**全仓唯一没有并发上限**的定时分派点。账号多时一次 tick 可瞬时打出 N 个上游请求。

目标：把整点尖峰摊平到数分钟窗口；给唯一的无界点补上与签到主链路一致的并发上限。

## 2. 关键决策

### 2.1 抖动只加在「创建定时器」这一步

六个插件的排期都遵循同一形状：

```
next := nextCheckinTime(now)   // 纯函数：算出下一个绝对槽位
timer := time.NewTimer(time.Until(next))
```

新增 `nextCheckinFireTime(now)` 包住纯函数并在结果上叠加抖动，**循环里只换成这一个调用**。

这样做的原因：`nextCheckinTime` 的绝对槽位语义已被既有测试锁定（`checkin_schedule_test.go` 断言 `nextCheckinTime(07:00) == 08:00`）。把随机性塞进纯函数会让这些断言变成概率性通过，且难以区分「排期算错」与「抖动偏移」。

### 2.2 抖动上界 5 分钟

| 约束 | 要求 | 5 分钟是否满足 |
|---|---|---|
| 不跨槽 | 远小于 4 小时槽位间隔 | ✅ 1/48 |
| 保活窗口 | `shouldRunKeepaliveNow` 的窗口是 `[t, t+1h)` | ✅ 远小于 1 小时，抖动后仍落在同窗口 |
| 签到有效性 | trae 签到无「窗口内才算」门控，晚几分钟仍算当日 | ✅ |
| 摊平效果 | 6 个插件、每个随机 0–5 分钟 | 尖峰从「同一秒」摊到约 5 分钟窗口 |

### 2.3 抖动源可注入

`schedulerJitterFn` 是包级函数变量（沿 `callModelsAPIFn` / `sendActivePingQoderFn` 既有惯例），单测注入确定值以验证「槽位 + 抖动」的精确关系；生产使用 `math/rand/v2` 的全局函数（自带随机种子、并发安全）。

`math/rand/v2` 在此处**不涉及安全场景**——只用于分散定时触发时刻，不生成凭据、不参与签名。

### 2.4 签到重试并发上限 4

取 4 的理由：`runAutoCheckin` 的签到主链路本身就是 `sem=4`，重试只是补签，不应比正常签到更激进。

同时补了「等本轮全部结束再进下一个 tick」：`popDueCheckinRetries` 会把条目**先移出队列**，若不等待本轮完成，未处理的条目会在下一轮重新排期前处于「既不在队列也不在处理」的悬空状态。

### 3.4 追加：watchdog 首轮抖动（6 插件）

背景：`schedulerJitterMax` 上一轮只接在 4h 槽位的定时器上，watchdog 的 10 分钟节拍
一个 jitter 引用都没有。六个插件都在 `init()` 启动 `watchdogLoop`，宿主就绪后**立刻**
跑首轮全量刷新，而就绪检查是 `watchdogReadyPoll = 250ms` 的轮询——这个轮询粒度会把
各插件的首轮吸附到同一窗口，形成约 6 × 10 = 60 并发的瞬时尖峰（`workbuddy` 的 Global
账号与 `workbuddy-ai` 还共用 `workbuddy.ai` 上游）。

改动落点（每个插件两处）：

| 插件 | 新增函数 | 插入点 |
|---|---|---|
| workbuddy | `watchdogFirstTickDelay` | `watchdog.go: watchdogLoop` |
| workbuddy-ai | `watchdogFirstTickDelay` | `watchdog.go: watchdogLoop` |
| traework | `watchdogFirstTickDelay` | `watchdog.go: watchdogLoop` |
| qoderwork | `watchdogFirstTickDelay` | `watchdog.go: watchdogLoop` |
| qoder-ai | `watchdogFirstTickDelay` | `watchdog.go: watchdogLoop` |
| qwenwork | `watchdogFirstTickDelay` | `watchdog.go: watchdogLoop` |

```go
func watchdogFirstTickDelay() time.Duration {
	return schedulerJitterFn()
}
```

调用位置在 `waitHostReadyForWatchdog` 之后、drain 的 `select` **之前**：

```go
waitHostReadyForWatchdog(watchdogStartupWait, hostReadyForWatchdog)
time.Sleep(watchdogFirstTickDelay())
select {
case <-watchdogTickCh:
default:
}
```

两个关键决策：

1. **只抖动首轮**。后续每轮从各自上一轮结束时刻起算，首轮错开后相位不会重新对齐，
   不需要每轮都抖（每轮都抖还会让节拍相对 wall clock 持续漂移）。
2. **等待不可被 tick 打断**。`configure` 在插件加载时就会投递一次 tick；若抖动等待写成
   `select` 的 tick 分支，六个插件会被同一个 configure 事件同时唤醒，抖动等于没加。
   等待期投递的 tick 由随后的 drain 丢弃，首轮仍在抖动后的时刻执行——语义与原有
   「等待期内丢弃 tick」一致。

复用既有的 `schedulerJitterFn`，因此上界仍由 `schedulerJitterMax = 5 * time.Minute`
统一约束，且单测可用 `withFixedJitter` 注入确定值。

### 3.5 新增测试（追加）

`watchdog_test.go`（6 插件各一份）：

- `TestWatchdogFirstTickDelay`：注入 90s，断言 `watchdogFirstTickDelay()` 返回 90s。
- `TestWatchdogFirstTickDelay_UsesSharedBound`：真实抖动源 200 次采样均落在
  `[0, schedulerJitterMax)`，确认复用同一上界而非另立常量。

## 4. 验证结论

- 六插件 `python scripts/cgo-shim-build.py <plugin>`：build + vet + test 全绿。
- 全部改动文件 gofmt 干净；`POLLUTION: PASS`。
- **变异验证（抖动）**：把 `nextCheckinFireTime` 中的抖动改为 0 →
  `TestSchedulerJitter_Applied` FAIL：`唤醒时刻 = 08:00:00, want 08:01:30（槽位 + 抖动）`。
- **变异验证（并发上限）**：去掉 `runCheckinRetryRound` 的信号量 →
  `TestCheckinRetryRound_CapsConcurrency` FAIL：`峰值并发 = 20，超过上限 4（旧缺陷：每项直接 go 无上限）`。
- **变异验证（watchdog 首轮抖动）**：把 `watchdogFirstTickDelay` 改为返回 `0` →
  `TestWatchdogFirstTickDelay` FAIL：`首轮抖动 = 0s, want 90s`。
- 三处变异均已还原并重跑全绿（workbuddy 还原后 md5 `8244f28c943cf17660c0878f08f1597d`）。
- `workbuddy/watchdog.go` 与 `traework/watchdog.go` 的 `gofmt -l` 报警属于改动前既有
  问题（英文注释列表缩进 + 文件尾多余空行），已用 `HEAD` 版本单独复核确认，本轮未引入。

## 6. 未覆盖与边界

- 抖动的生产效果（整点尖峰是否真的被摊平）需发布后通过上游请求时间分布观测。
- 抖动只覆盖 6 个有 4h 槽位的插件；`copilot`（冷却探活 5s ticker）、`zcode`（额度刷新单 worker）、`cursor`/`doubao`/`notion`（无插件侧账号定时循环）不在本轮范围。
- **coze `/accounts` 的无上限账号级扇出未修**（并发清单中的 P0）：该路径每账号一个
  goroutine 且无信号量，失败结果又不写缓存，账号越多瞬时并发越大。属独立改动项，
  用户本轮未指示，保持原状。
- 3.4 只消除「首轮同刻对齐」，不改变各插件自身 10 并发的上限，也不解决跨插件并发之和。
- `copilot` / `doubao` / `zcode` 三个新版本已出包并进入 registry，但因生产端处于禁用态而未部署；
  若后续重新启用，需再走一次 `plugin-store install` 才能用上本批次改动。
- zcode 的每账号 `listAllAuthFiles()` 全量重扫（O(N²)）仍存在：并发不高（串行），
  但账号规模大时是纯 CPU/IO 放大，未在本轮处理。
- 各插件之间的**共享限流**仍未做（属第三优先级，用户本轮未选择）。当前改动只解决「同刻对齐」与「单点无界」，不解决「多插件并发之和」。
