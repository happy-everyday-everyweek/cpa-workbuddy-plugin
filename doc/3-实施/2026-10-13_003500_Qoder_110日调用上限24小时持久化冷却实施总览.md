# 需求实施总览：Qoder 110 日调用上限 24 小时持久化冷却

结论：为 Qoder 服务商（qoder-ai 与 qoderwork）建立针对 110（Billing daily count exceeded）上游日请求次数上限的专属 24 小时持久化冷却机制，命中后打上冷却标记并排除调度，支持到期自然解除与面板手动解除，保障健康账号平稳轮转与服务连续性；影响：Qoder 国际版与国内版所有账号的故障切换、调度路由与面板监控交互；范围：qoder-ai-provider 与 qoderwork-provider 的 110 错误识别、24h 物理 auth 文件持久化冷却标记、内存路由排除、面板冷却状态徽章及手动解除管理接口；非范围：修改非 Qoder 插件、修改上游配额规则或更改常规 15s 短故障冷却机制；变化：当 Qoder 账号遭遇 110 错误时自动进入 24 小时持久化冷却且不再承接流量，面板显示醒目的橙色冷却徽章与剩余时间，并提供手动解除按钮；完成标准：两插件单测与编译全绿，110 错误命中后物理 auth 文件写入 24h 冷却截止时间，调度器自动绕开，面板精准回显并支持一键清除冷却；术语说明：110（阿里 Qoder 上游 HTTP 200 下返回的 `code:"110", message:"Billing daily count exceeded"` 业务限制帧，表示该账号当日请求次数配额已耗尽）；验证状态：技术方案收敛，已完成单发对照取证，待实施。

## 1. 当前计划最终方案简要说明
- 推荐方案一句话结论：在 Qoder 专属故障处理层拦截 `110 / Billing daily count exceeded` 错误，将账号标记为 24 小时持久化冷却（写入物理 auth JSON 文件 `daily_cooling_until` 字段），并在调度层彻底排除，仅允许 24h 到期自然恢复或面板人工手动解除。
- 主落点 / 主路径：`qoder-ai` 与 `qoderwork` 的 `policy.go`（新增 110 错误判定）、`daily_cooldown.go`（新增 24h 物理文件持久化读写与内存判定）、`accountFailover.go` / `scheduler.go`（路由排除集成）、`management.go`（新增手动解除 API）及 `panel.html`（卡片徽章与解除按钮）。
- 为什么先走这条路线：Qoder 账号额度机制与常规大模型不同（积分充足但日请求调用次数独立受限），常规 15s 软冷却会在 15s 后重新把请求打到已受限账号制造二次失败；24 小时持久化冷却既能准确隔离已耗尽账号，又因落盘保证了 CPA 容器重启或热重载后冷却状态不丢失。

## 7. 方案选择
- 方案 A（纯内存冷却）：用内存 `time.Now().Add(24*time.Hour)` 标记。缺点：CPA 容器重启或插件配置热重载后内存清空，已超限账号立刻重新承接流量被上游 110 拒绝。
- 方案 B（物理 auth 文件持久化 + 内存镜像，**推荐**）：
  - 触发 110 时，通过 `writeAuthFileDirect` / `persistAuthDirect` 写入物理 auth 文件的 `daily_cooling_until` 字段（ISO8601 / RFC3339 字符串）；
  - 启动与运行时维护只读内存时间集合，避免每次调度都产生磁盘 I/O；
  - 优点：彻底免疫重启与重载，物理文件单一真相源，与 CPA 现有 disabled / note 持久化体系完美兼容。

    Trigger110 --> PersistDisk[直写物理 auth 文件: daily_cooling_until]
    PersistDisk --> UpdateMem[更新内存 dailyCoolingSet]
    UpdateMem --> Rotate[触发当前请求自动换号重试]

## 10. 风险与阻断项
- 风险 1：直接修改物理 auth 文件必须使用原子重命名机制（复用现有的 `writeAuthFileDirect`），严禁使用丢失未知顶层字段的 `host.auth.save`。
