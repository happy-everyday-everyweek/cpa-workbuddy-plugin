# 自动测试多模型依次探活改造实施总览

结论：将 workbuddy / workbuddy-ai / traework 三个插件的自动定时探活逻辑，从「随机挑选 1 个模型、10s 超时」改造为「随机挑选最多 5 个模型依次测试、单次 20s 超时、叠加整轮 30s 预算熔断，任意一个模型成功即判定账号健康，全部失败才打上测试标签」；影响：三个插件后台 Watchdog / Refresh Runner 定时活跃探活的健康判定精度与标签打标率，大幅降低因单模型瞬时故障或下线导致的账号误杀率；范围：三个插件的 active_ping.go、active_ping_test.go、CHANGELOG 与版本；非范围：不改动面板手动「测试」弹窗的指定模型测试链路、不改动物理 JSON 打标存储格式与内存镜像结构、不改动调度器路由硬排除规则；变化：定时探活时健康账号只要首次成功即刻返回（常态仍只发 1 次请求），异常账号在 5 个模型均失败后才打标；完成标准：三个插件 cgo-shim build/vet/test 全绿、新增多模型轮测与熔断单测全绿、6-review STYLE PASS。

## 1. 当前计划最终方案简要说明

- 推荐方案一句话结论：在 active_ping.go 中新增 pickRandom*Models(sa, 5) 获取最多 5 个去重候选模型，doActivePing 中按顺序依次发起单次 20s 的轻量探活请求，叠加 30s 总预算截止时间；任意一次成功立即清标并退出循环，全部失败且剩余积分>0 时打 test_failed 标签。
- 主落点 / 主路径：三个插件各自的 `active_ping.go`（探活执行与多模型轮测）、`active_ping_test.go`（多模型轮测、any-success、全失败打标单测）、`CHANGELOG.md`。
- 为什么先走这条路线：不改动外部接口与面板交互，纯内部探活精度提升；成功即停保证对上游并发压力零新增，总时长熔断保证不会长时间拖累刷新队列 worker。

## 2. Agent 对当前问题的理解

- 问题 / 目标：当前自动定时探活仅随机挑选 1 个模型发 10s 请求，若恰好选到上游维护或下线的模型，即使账号本身完全正常也会被误打【测试】标签并被调度器硬排除；需要支持随机挑选最多 5 个模型依次测试、单次 20s 超时，只要有任意一个模型成功即代表账号可用。
- 本轮计划范围：workbuddy、workbuddy-ai、traework 三插件的 active_ping 逻辑改造、对应单测补充、版本记录与验证。
- 明确不在范围：面板手动测试按钮（保持单模型指定测）、test_failed 存储与内存 set 结构、scheduler 路由硬排除逻辑。
- 当前优先闭环：CYCLE-01 三插件 active_ping 逻辑升级与多模型轮测单测全绿。
- 关键假设 / 待确认点：若账号可用模型少于 5 个，取实际数量并打乱测试；无模型时回退单一默认模型；单次请求超时从 10s 放宽至 20s；整轮探活设置 30s 熔断保护。
- unresolved_decisions：无未决决策。
