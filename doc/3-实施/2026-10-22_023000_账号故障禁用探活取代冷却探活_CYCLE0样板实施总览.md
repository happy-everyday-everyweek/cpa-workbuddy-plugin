# 账号故障禁用探活取代冷却探活 实施总览

> 周期：2026-10-21 ~ 2026-10-22
> 范围：CYCLE-0（workbuddy 样板）；其余 9 插件在样板验收通过后复制
> 状态：**CYCLE-0 已完成并通过真实宿主四态验收**

## 1. 当前计划最终方案的简要说明

失败时**双写**：内存阶梯冷却（保留原有机制）+ 盘上 `disabled: true`（宿主路由判据本身）。
每 10 分钟串行遍历被本机制禁用的账号，**只回放失败的那一个模型**，该模型探通才写回
`disabled: false` 并清冷却；没有记录到失败模型则跳过该账号。冷却探活（`cooldown_probe*.go`）已删除。

主落点：`workbuddy/failover_disable.go`（新增，禁用/恢复/探活引擎）+ `workbuddy/accountFailover.go`（记账落点改双写）。

## 2. 背景与目标

- 问题：冷却只存在插件内存，宿主选择器看不见。生产实测**单个请求连试 14 个账号**，
  每个已知坏号都要付一次失败往返，用户侧表现为长时间等待后仍失败。
- 目标：请求进来一次就路由到真正可用的账号/模型，一次性成功。
- 手段：把「不可用」写进宿主的 `disabled`——宿主 watcher 毫秒级感知、选择器直接跳过，
  跨请求与同请求轮转一起挡住，且宿主自身**永不自动恢复**，恢复权完整留在插件。

## 3. 用户裁定（口径，10 个插件统一）

| 裁定项 | 结论 |
|---|---|
| 禁用粒度 | **整账号**（接受精度损失；11128 模型级拦截也禁用整号） |
| 探活模型范围 | **只探失败的那一个模型；它成功才恢复**（2026-10-22 改判：每个账号的每个模型额度独立，别的模型通不能证明失败模型已恢复） |
| 探活节奏 | 固定 **10 分钟**（2026-10-22 改判：账号规模将到 200 个，60 秒扫一轮不可行）；上一轮未完成则本轮直接跳过（不排队、不重叠、不加整轮预算） |
| 冷却机制 | **保留**；只删除冷却探活 |
| 失败落点 | **双写**：失败即同时冷却 + 禁用；探活成功两侧一起清 |
| 空池护栏 | **不设**，严格「失败即禁」 |
| 发布 | 本次会话所有改动**不发布** |

## 4. 关键设计

### 4.1 为什么必须双写

- 禁用是**宿主可见**的状态：写盘 → watcher → `Auth.Disabled=true` / `Status=StatusDisabled`
  → 选择器跳过（`sdk/cliproxy/auth/selector.go` `isAuthBlockedForModel`）。
- 冷却仍是**插件内**判据，职责收窄为两段禁用覆盖不到的地方：
  写盘到 watcher 生效之间的毫秒级窗口；写盘失败（宿主 RPC 不通 / auth_index 解析不到）时的唯一排除手段。
- 两侧必须在**写**（`recordFailureScoped`）与**清**（`reenableAccountForFailover`、
  `resetAccountFailover`）两个点严格配对，否则会出现「盘上可用、插件仍排除」的半恢复账号。

### 4.2 认领边界（最重要的约束）

本机制只认领、只解除**自己写的** `failover_disable` 标记：

- `manual_disable`（用户手动禁用）：永不接管、永不自动恢复。
- `exhausted_disable`（额度耗尽，4 小时签到 reconcile 恢复）：不带本机制标记，天然被排除。
- 回传到宿主 `Metadata` 时同样受此门控（`failoverMarkersFromMap` 只认带标记的文档），
  避免把用户手动禁用的号塞进探活候选、被自动启用。

### 4.3 锁序

- `failoverMu`（冷却表）与 `failoverProbeModelMu`（本地禁用集合）：禁止嵌套，先释放前者再取后者。
- `failoverDocLock(authIndex)`：只罩住「读盘 → 判 disabled → 写盘」这一段读改写，不跨宿主 RPC 等待。

## 5. 实施过程中发现并修复的三个真实缺陷

这三个都是**单元测试全绿、只有真实宿主端到端才暴露**的缺陷。

### 5.1 子 goroutine 数据竞争（已修）

`confirmFailoverHostState` 原先在子 goroutine 里读全局注入变量 `failoverWaitConfirmed`，
与单测 Cleanup 中的还原构成竞争，`go test -race` 报出。
修法：等待函数由调用方在 `go` 之前读取并作为参数传入。

### 5.2 同一次失败重复写盘（已修）

现象：一个失败请求触发 2 条 `failover disabled account` 日志。
取证（WSL 内打点）：两个记账入口的身份别名（宿主文件名 ID `workbuddy-e2etest01.json`
与账号 UID `e2etest01`）**解析到同一个 auth_index**，各自做「读盘 → 判未禁用 → 写盘」，
读改写非原子。
修法：按 auth_index 分片加 `failoverDocLock`，锁罩住整段读改写。
回归：`TestConcurrentDisableFromAliasIDsWritesOnce`；变异（去掉锁）实测写盘 4 次、用例 FAIL。

### 5.3 宿主回存抹掉本机制标记（致命，已修）

现象：禁用写盘成功、宿主也吸收了（`NOT confirmed = 0`，路由立即停），
但盘上随后只剩 `disabled: true`，`failover_disable` 消失：

```
keys: ['account','auth','disabled','failed_count','logo','note','provider','success_count','type']
```

后果：探活候选按盘上标记枚举（`failoverProbeTargets`），标记没了 → **永不探活 →
账号被宿主永久禁用，只能人工启用**。这正是本方案要杜绝的「静默遗忘」。

根因（宿主源码证据）：

- `sdk/auth/filestore.go:113-122`：落盘前把 `disabled` 写进 `Auth.Metadata` 再 `SaveTokenToFile`。
- `internal/pluginhost/auth_provider.go:540` `mergedStorageJSON(raw, meta)`：
  以插件回传的 `StorageJSON` 为底，用 `Metadata` 逐键覆盖。
- 而插件 `enrichAuthMetadata` 只回传 `type/provider/logo/note/disabled` 五个键。
  `disabled` 在白名单里所以**存活**，`failover_disable` 不在所以**被抹掉**。

修法（让标记经宿主回环）：

1. `carryFailoverKeysIntoMetadata`（`failover_disable.go`）：把宿主交来的文档里本机制的三键并入回传的 `Metadata`。
2. `handleParseAuth`（`main.go`）：以 `req.RawJSON` 为源回传。
3. `toAuthDataForRefresh`（`oauth.go`）：以 `req.Metadata` 为源回传，且**不再固定 `disabled:false`**。

第二处同时修掉一个更危险的同源缺陷：宿主挑选刷新候选时**不看 `Disabled`**
（`sdk/cliproxy/auth/auto_refresh_loop.go:357 nextRefreshCheckAt` 只判 unauthorized/invalid_grant），
而 `toAuthDataForRefresh` 原先硬编码 `disabled: false` ——
即「禁用中的号会被一次后台 token 刷新静默解封，完全绕开禁用探活」。

回归用例（均做变异验证，去掉修复必失败）：

- `TestParseAuthCarriesFailoverMarkersIntoMetadata`
- `TestRefreshAuthKeepsDisabledAndMarkers`（刷新不得改变禁用状态）
- `TestParseAuthOmitsMarkersWhenNotFailoverDisabled`（手动禁用/健康号不得被塞入标记）
- `TestHostRebuildFromParseAuthDataKeepsMarkers`（离线复刻宿主 `mergedStorageJSON`，证明重建后标记存活）

## 9. 变更记录：探活范围收窄为「仅失败模型」（2026-10-22）

用户改判：**每个账号的每个模型额度彼此独立**，在别的模型上探通不能证明失败模型已恢复。
原口径「全量候选模型串行、任一成功即恢复」会把仍带着坏模型的账号放回路由，下一个同模型
请求照样失败，只是把故障推迟到下一次请求去发现，还白烧了其它模型的额度。

| 项 | 改前 | 改后 |
|---|---|---|
| 探活目标 | 失败模型 + 该账号全部候选模型 | **仅失败模型** |
| 恢复条件 | 任一模型成功 | **失败模型成功** |
| 无失败模型时 | 退化为全部候选模型 | **跳过该账号**（无法验证就不恢复，保持禁用） |
| 单账号单轮请求数 | 1 ~ N 次 | **恒为 1 次** |

配套删除：`failoverModelsFn` 注入点与 `failoverProbeModelList`（三插件），
qoderwork 的 `orderedAllQoderModels`（本会话新增、随本次改判失去唯一消费者）。
`orderedAllWorkbuddyModels` / `orderedAllTraeModels` 保留——它们仍被 4 小时健康探活使用。

测试改写：`TestRunFailoverProbeAnyModelSuccessRecovers` → `TestRunFailoverProbeOtherModelSuccessDoesNotRecover`
（断言别的模型通**不**恢复）；`TestRunFailoverProbeStopsAfterFirstSuccess` →
`TestRunFailoverProbeStopsAfterOnePing`；`TestRunFailoverProbeNoCandidateModelsSkips` /
`TestFailoverProbeModelListWithoutFailedModel` → `TestRunFailoverProbeWithoutFailedModelSkips`；
新增 `TestRunFailoverProbeSyncsLatestFailedModel`。

验证（本轮实跑）：

```
python scripts/cgo-shim-build.py workbuddy   # build + vet + test 全绿 1.383s
python scripts/cgo-shim-build.py traework    # 全绿 2.692s
python scripts/cgo-shim-build.py qoderwork   # 全绿 2.807s
# WSL CGO=1 go test -race（探活相关用例）：三插件均 ok
```

变异验证（在临时副本上做，已还原）：
1. 把「只探失败模型」改回「失败模型 + 另一模型」→ `TestRunFailoverProbeOtherModelSuccessDoesNotRecover`
   失败（`got [blocked-model mutant-extra-model]`），精确命中。
2. 把「无失败模型即跳过」改成用默认模型探活 → `TestRunFailoverProbeWithoutFailedModelSkips`
   失败（`无失败模型时应跳过, probed = 1`），精确命中。

## 10. 变更记录：探活周期 60 秒 → 10 分钟（2026-10-22）

用户改判：账号规模会达到 **200 个**，60 秒扫一轮不可行，三种插件统一改为 **10 分钟**。

改了点：`failoverProbeInterval` 常量（三插件各一处）、`failoverProbeLoop` 与常量注释、
各插件描述恢复通道的注释与面板文案、周期断言用例（`want 10m`）。
**未改**：冷却阶梯基数仍是 60s（那是冷却时长，不是扫描周期）；单账号探活超时
仍是 20 秒；不重叠调度与「只探失败模型」语义不变。

**为什么 10 分钟可以接受**：候选只包含「被本机制禁用的账号」（`failoverProbeTargets`
要求 `f.Disabled && doc.failoverDisable`），200 个健康账号根本不进扫描范围。所以扫描
规模取决于当前坏号数，不随账号总量线性膨胀；稳态下通常只有个位数候选。

**代价**：坏号恢复的发现延迟从 ≤60 秒变成 ≤10 分钟。用户已认可——坏号本来就被
宿主路由排除，延后恢复只影响「池子回血速度」，不影响正在服务的请求。

**验证**：三插件 cgo-shim build+vet+test 全绿；变异（常量改回 60s）被
`TestFailoverProbeIntervalMatchesUserRuling` 精确捕获（`探活周期 = 1m0s, want 10m`）。
