# 需求实施总览：Coze（扣子）桌面端 CPA Provider 插件立项（登录授权版）

结论：以**登录授权流程**为插件的一等公民——用户在扣子页面完成官方登录后，由同源脚本取一次性 `x_tt_token` 交给插件，插件调 `passport/token/beat/v2/` 换取 Cookie 会话，再以该 Cookie 调用 `coze_claw` 通道；影响：CPA 用户无需手工抓 Cookie，也无需安装本地程序；范围：登录授权链路、Cookie 续期、账号池、模型发现、流式转换、面板、用量、发布链；非范围：不做手机号/密码服务端登录、不逆向 `msToken`/`a_bogus` 签名、不读浏览器 Cookie 库、不做生图生视频；变化：面板出现「登录扣子」按钮与一次性授权脚本，授权完成后账号自动入池；完成标准：真实账号完成一次授权并成功对话；术语说明：`x_tt_token` 是扣子签发的一次性令牌，`token beat` 是用它换会话 Cookie 的端点（带 Cookie 调用则反向返回 `x-tt-token`）；验证状态：桌面端 1.1.45 登录链路已完成静态逆向取证，未做真实端到端登录。

## 1. 当前计划最终方案简要说明

- **推荐方案一句话结论**：插件内实现「授权登录」——面板引导用户在扣子页面完成官方登录，再用一次性授权脚本取 `x_tt_token` 交给插件回调页，插件调 `POST https://www.coze.cn/passport/token/beat/v2/` 换取 Cookie 会话并落盘。
- **主落点 / 主路径**：`coze/login.go`（授权会话状态机）+ `coze/bridge.go`（回调桥接页与授权脚本）+ `coze/credentials.go`（token beat 换 Cookie、续期）；上游对话仍走 `coze_claw`。
- **为什么走这条路线**：桌面端的 deep link 回调协议被硬编码白名单锁死（只认 `coze-desktop:` 系列），插件无法作为回调接收方；但同源脚本可以拿到 `x_tt_token`，且 token beat 的换 Cookie 契约是纯 HTTP。**插件不需要内嵌浏览器、不需要扫码协议、不需要逆向风控签名、不读 Cookie 库**。

**TASK-000 已执行，两次更正后结论稳定**（详见 `doc/5-tests/2026-10-17_233000_Coze授权登录redirect_uri可行性验证.md` 与 `doc/5-tests/2026-10-17_234500_CozeDesktopLogin授权入口复验.md`）：

**已排除的替代路线**：

| 路线 | 排除原因 |
|---|---|
| 官方编程 API OAuth（`/api/permission/oauth2/*`） | 覆盖的是扣子编程 API 的付费 token 计费，**不是桌面端每日积分**，与本插件目标不符 |

## 3. 登录授权链路（核心设计）

### 3.1 桌面端实证链路（仅供契约参考，协议不可复用）

```text
用户点登录
  → 主进程 openLoginPopup(authUrl)
  → buildAuthUrlWithRedirect：注入 redirect_uri=<APP_PROTOCOL>://auth/callback 与 state
  → shell.openExternal：系统浏览器打开扣子授权页
  → 用户完成授权（抖音/飞书/火山）
  → 浏览器 302 到 coze-desktop://auth/callback?state=..&x_tt_token=..&login_method=..
  → 应用校验 state
  → POST /passport/token/beat/v2/  (sdk-version: 2 + x-tt-token)  → Set-Cookie
  → GET  /passport/account/info/v2/                              → 校验登录态
```

**不可复用点**：`redirect_uri` 协议白名单硬编码 `coze-desktop:` 系列，插件无法注册该协议（运行在服务器且与桌面端冲突）。

### 3.2 插件采用链路（同源授权脚本）

```text
面板点「登录扣子」
  → 打开 https://www.coze.cn（用户按官方页面登录：手机号/抖音/飞书/火山）
  → 面板展示「完成授权」：一次性脚本 + 复制按钮
  → 用户在 www.coze.cn 页面执行脚本（DevTools Console 或书签）：
       fetch('/passport/token/beat/v2/', {
         method:'POST', credentials:'include',
         headers:{'sdk-version':'2','Content-Type':'application/json'},
         body:'{}'
       })
       .then(r => r.headers.get('x-tt-token'))
       .then(t => location.href =
         '<CPA>/v0/resource/plugins/coze-provider/login-callback?state=<state>&token='+encodeURIComponent(t))
  → 插件回调页收到 state + token
  → 插件 POST /passport/token/beat/v2/  (sdk-version: 2 + x-tt-token) → Set-Cookie
  → 插件 GET  /passport/account/info/v2/  → sec_user_id 非空 → 落 auth 文件
```

**为什么这条能成**：脚本运行在 `www.coze.cn` 同源上下文，`credentials:'include'` 自动带登录 Cookie，因此能读到 `x-tt-token` 响应头；token 经 URL 交给插件后，换 Cookie 是纯 HTTP 契约，与桌面端完全一致。

**为什么不是一键**：`redirect_uri` 协议白名单锁死，登录页无法把 token 送到插件域名。这一步骤是白名单约束下的最小代价——不需要装本地程序、不需要读 Cookie 库、不需要注册协议。

### 3.3 与桌面端的差异对照

| 环节 | 桌面端 | 插件侧 | 说明 |
|---|---|---|---|
| 登录页 | `shell.openExternal` 打开授权页 | 用户自建浏览器打开 `www.coze.cn` | 无差异 |
| token 获取 | 登录后 deep link 回传 | 同源脚本读取 `x-tt-token` 响应头 | 插件不依赖 deep link |
| token 传递 | `coze-desktop://auth/callback?...` | 脚本跳转插件 HTTP 回调页 | 插件唯一可用的接收面 |
| 换 Cookie | 主进程 `net.fetch` token beat | 插件 `http.Client` 调同一端点 | 契约一致 |
| Cookie 存储 | Electron `session.cookies` | 插件 auth 文件 + Cookie Jar | 需实现写回 |
| 续期触发 | `webRequest` 拦截 passport 响应 | watchdog 主动调 token beat | 插件不能被动拦截，只能主动换发 |

### 3.4 续期机制（用户核心要求，已实测通过）

`passport/token/beat/v2/` 是**双向**换发端点（2026-10-17 23:55 真实账号实测）：

| 调用方式 | 实测响应 |
|---|---|
| 带会话 Cookie（`credentials: include`） | HTTP 200 / `message=success` / **返回 `x-tt-token` 响应头（355 字符）** / Set-Cookie **0 条** |
| 带 `x-tt-token` 请求头（不带 Cookie） | HTTP 200 / `message=success` / **Set-Cookie 13 条** |

完整闭环实测结果：

```text
首轮：token(355) → 13 条 Cookie → account/info/v2 通过（sec_user_id 76 字符）
续期：13 条 Cookie → 新 token(355) → 13 条新 Cookie → account/info/v2 仍通过
```

因此插件 watchdog 只需周期性执行「Cookie → 新 token → 新 Cookie」即可滚动续期，**不存在豆包那种 Cookie 快照硬失效**。

**实现注意**：13 条 Set-Cookie 中存在同名重复（`uid_tt` / `uid_tt_ss` / `session_tlb_tag` 各 2 条，对应不同 path/domain），落盘必须保留完整属性，不能按名简单覆盖。

### 3.5 失败分支

- 用户在扣子页面未登录就执行脚本 → token beat 返回 `error_code=401 会话过期` → 面板提示「请先完成登录」。
- `x_tt_token` 已失效或已消费 → token beat 返回非 `success` → 回调页返回明确错误，提示重新执行脚本。
- 回调 `state` 不匹配或重放 → 拒绝并记录，不落盘。
- token beat 返回非 2xx → 记录 `errorCode`，不落盘半成品凭据。

**实测的未授权响应**（伪造 token / 无凭据三种组合均一致）：

```text
HTTP 200
{"message":"error","data":{"error_code":401,"description":"会话过期，请重新登录"}}
```

即该端点**始终返回 HTTP 200**，必须按 `message` + `data.error_code` 判定成败，不能只看状态码。

## 9. 关键风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 授权脚本需用户手动执行一步 | 体验不如一键授权 | 面板提供「复制脚本」+ 书签式引导；这是白名单锁死下唯一不读 Cookie 库的路径 |
| `x_tt_token` 生命周期未实测（桌面端 5 分钟是其等待 deep link 的窗口，非 token TTL） | 授权窗口可能更短 | 脚本即时执行；失效由回调页明确报错并提示重试 |
| token beat 始终返回 HTTP 200 | 误判成功 | **必须**按 `message` + `data.error_code` 判定（已实测） |
| 13 条 Set-Cookie 存在同名重复 | Cookie 落盘覆盖丢失 | 保留完整 domain/path 属性，按 (name,domain,path) 三元组存储 |
| claw 增量通道非 SSE | 延迟高 | TASK-003 确认后定轮询节奏 |
| 扣子改版（1.1.x 快） | 协议失效 | 端点集中 `protocol.go`，版本写日志 |
| 无工具调用协议 | 编码体验差 | 先纯对话，`tool_call` 增量已存在，列后续增强 |
