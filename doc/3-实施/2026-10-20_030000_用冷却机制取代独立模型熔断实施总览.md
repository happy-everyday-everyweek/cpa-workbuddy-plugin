# 用冷却机制取代独立模型熔断 实施总览

- 编号：IMP-REPLACE-CIRCUIT-WITH-COOLDOWN-20261020
- 来源：用户 2026-10-20 生产反馈——管理台仍出现大批「请求后才失败」的记录，质疑既然已加冷却与提前判断，为何请求仍被路由过去。
- 状态：代码 + 真实测试 + 变异验证完成；**未提交、未发版、未部署生产**。
- 追加（2026-10-20）：§6 探测窗口零余量修复（`cooldownProbeInterval` 5s → 1s，5 插件）。

## 1. 问题与根因

### 1.1 生产取证

近 60 分钟 `workbuddy-ai-provider` / `deepseek-v4.1-flash` 的失败构成：

| 错误形态 | 次数 | 含义 |
|---|---|---|
| `upstream model circuit open: deepseek-v4.1-flash` | 246 | 本地熔断短路，未打上游 |
| `upstream 400 {"code":11128,...}` | 58 | 真实打到上游后被拦截 |

近 6 小时同模型跨 provider 对比：

| provider | 成功 | 失败 |
|---|---|---|
| workbuddy-provider | 2463 | 1 |
| workbuddy-ai-provider | 0 | 925 |

同一模型在 workbuddy-provider 完全正常、在 workbuddy-ai 100% 被 11128 拦截，
说明拦截点在「上游对该 provider 下该模型」的判定，而非账号故障。

### 1.2 根因

`classifyUpstreamFailure(400, {"code":11128})` 返回 **`failureScopeNone`**——11128 落进
「不记账」分支。实测确认（临时探针断言）：

```
PROBE classifyUpstreamFailure(400,11128) = none
```

即：**11128 从未进入冷却体系**。旧实现另建了一套独立熔断状态机（`model_circuit.go`：
跨 3 个账号命中 → 打开 60 秒闸门），但该闸门只负责「拒绝请求」：

- 不改变路由 → 宿主仍会把请求派给已被拦截的账号×模型；
- 不是冷却 → 不参与 `cooldownProbeLoop` 的到期前探活；
- 状态在内存里 → 容器重启或热重载即归零，需要重新累积 3 个账号才再次熔断。

于是形成「失败 → 熔断 → 60 秒后自动放开 → 再被路由过去 → 再失败」的循环。

## 2. 方案：熔断不再独立存在，11128 直接写冷却

用户裁定：**不需要真正的熔断，复用冷却机制即可。**

改动后：

1. `isModelBlockedError(status, body)` 成为 11128 的唯一判定点（原 `isModelCircuitError` 迁入 `failure_class.go`）；
2. `classifyUpstreamFailure` 把 11128 归入 `failureScopeAuthModel`，与其它模型级失败走同一记账落点 `recordFailureScoped`；
3. 冷却探活 `cooldownProbeTargets` **同时覆盖账号级与账号×模型级冷却**，到期前 5 秒用失败时的模型回放；
4. 探活成功 → `resetAuthModelFailover(authID, model)` 只清该模型；失败 → 按候选来源的维度续期；
5. `model_circuit.go` 收敛为单一函数 `noteModelBlockedHit(authID, model)`，不再持有任何状态。

因此「熔断」变成了冷却的**触发器**，而不再是并列的第二套状态机。请求不再被路由过去，
是因为路由层 `isAuthModelCoolingDown` 本来就会跳过冷却中的账号×模型。

### 2.1 探活维度必须与冷却来源一致

`cooldownProbeCandidate` 新增 `scope` 字段。理由：探活失败拿不到有意义的状态码，
若重新分类会被误判成传输层失败、错误地把模型级冷却升级成账号级；而账号级冷却的
探活失败也必须继续记账号级，否则账号会在冷却期内被重新放上路由。

### 2.2 探活标记按归一化键记录

`markCooldownProbed` 原先按原始 authID 记录。冷却表里同一账号可能同时存在原始键与
归一化别名两条记录，按原始键记录会让另一条查不到标记、对同一账号重复探测。
改为读写都用 `normalizeFailoverKey`。

此问题由 `TestModelBlockedCooldownProbedBeforeExpiry` 的偶发失败暴露（约 1/5 概率）。

## 6. 后续修复：探测窗口零余量（2026-10-20）

### 6.1 问题

冷却探活的触发窗口是 `[cooldownUntil - 5s, cooldownUntil)`，宽度恰好等于
`cooldownProbeInterval`（5s）。窗口内只会落进**一个** tick，而该 tick 一旦被
`cooldownProbeLoop` 的 `running.TryLock()` 跳过（上一轮探活未结束），下一次 tick 时
`now >= cooldownUntil`，`shouldProbeCandidate` 直接返回 false——**该冷却周期永远不会被探测**，
账号会不带验证地重新接流量。

余量分布进一步放大了风险：`cooldownUntil` 取自失败时刻的 `now.Add(...)`，相对 5s 网格任意，
故 `until - tick` 均匀落在 `(0, 5s]`，约 2% 的冷却窗口余量不足 100ms。

### 6.2 修复

`cooldownProbeInterval` 由 5s 改为 1s，窗口内从 1 个 tick 变为 5 个。只改调度粒度，
不动提前量窗口（`cooldownProbeLeadTime` 仍为 5s）、不动阶梯、不动探活请求本身。

涉及 5 个插件：`workbuddy` / `workbuddy-ai` / `traework` / `copilot` / `zcode`。

### 6.3 防回退

新增 `TestCooldownProbeIntervalFitsWindow`（5 插件各一份），断言
`cooldownProbeLeadTime / cooldownProbeInterval >= 3`，即窗口至少容得下 3 个 tick。

变异验证：把 `cooldownProbeInterval` 改回 5s，测试如期失败——

```
--- FAIL: TestCooldownProbeIntervalFitsWindow (0.00s)
    cooldown_probe_test.go:339: 探测窗口只容得下 1 个 tick（窗口 5s / 粒度 5s），窗口余量不足，至少需要 3 个
```

已还原并重跑全绿。

### 6.4 未覆盖

以下三项经排查确认存在但本轮未改，留待后续：

| 项 | 现状 | 影响 |
|---|---|---|
| 单轮串行探测 | `runCooldownProbeTick` 顺序 for 循环，无并发上限 | N 个账号同时进窗口时一轮可达 `N × 20s`，期间其它冷却窗口被连续吞掉 |
| 4h 定时探活不看冷却 | `doActivePing` 不检查账号是否冷却中 | 可能与冷却探活对同一账号并发发两条上游请求 |
| 无首轮相位抖动 | 5s ticker 裸起，无 `schedulerJitterFn` | 批量热重载后 5 个插件的探活网格锁死在同一相位 |

注意：给 `cooldownProbeInterval` 本身加抖动是错误做法——间隔带窗口余量语义，
加抖动会把 tick 推出窗口。若要抖动只能加一次性首轮相位偏移。

## 7. 后续调整：提前量 5s → 20s（2026-10-20）

### 7.1 动机

用户要求「多提前一些」，把探测窗口从到期前 5 秒放宽到 20 秒，让探活有更充裕的时间
在冷却结束前完成，进一步降低「冷却刚到期就被业务请求撞上」的概率。

### 7.2 约束校验

| 约束 | 校验结果 |
|---|---|
| 窗口不得超过最短冷却 | `failoverCooldownBase = 60s`，20s 窗口仅占 1/3，仍留 40s 余量，不越过冷却起点 |
| 窗口须容纳多个 tick | 20s / 1s = 20 个 tick，远大于防回退阈值 3 |
| 探活须在窗口内完成 | 探活超时 20s（copilot 30s）与窗口同量级；超时后仍会沿阶梯续期，不会漏掉验证 |

### 7.3 变更

- `cooldownProbeLeadTime`：5s → 20s（5 插件同步）；
- 同步更新文件头设计要点、常量注释、`cooldownProbeLoop` 注释中的窗口值；
- 修正 `TestShouldProbeCandidateWindow` 的硬编码边界：`10s/6s/5s` → `25s/21s/20s`。

### 7.4 验证

五个插件 `cgo-shim-build.py` 全绿（build / vet / test）。

变异验证：把 `cooldownProbeLeadTime` 改回 5s，测试如期失败——

```
--- FAIL: TestShouldProbeCandidateWindow (0.00s)
    --- FAIL: TestShouldProbeCandidateWindow/距到期正好_20s_进窗口 (0.00s)
```

已还原并重跑全绿。

### 7.5 组合后的最终参数

| 参数 | 值 | 含义 |
|---|---|---|
| `cooldownProbeLeadTime` | 20s | 冷却到期前 20 秒进入探测窗口 |
| `cooldownProbeInterval` | 1s | 每秒一个 tick，窗口内 20 次机会 |
| 最短冷却 | 60s | 窗口占 1/3，不越过冷却起点 |
| 每周期探测次数 | 最多 1 次 | 以 `cooldownUntil` 为周期标识 |
