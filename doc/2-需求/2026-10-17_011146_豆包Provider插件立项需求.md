## 一、背景与目标

### 背景

当前仓库（`cpa-workbuddy-plugin`）已有 9 个 CPA 插件，覆盖腾讯 CodeBuddy、Trae、Qoder、Cursor、ZCode、GitHub Copilot 等服务商。经检索确认：

1. **官方 CLIProxyAPI（`router-for-me/CLIProxyAPI`，55k stars）不内置豆包 provider**——README 支持的 provider 表仅含 Kimi / OpenAI / Anthropic / Antigravity(Gemini) / xAI Grok / Meta Muse / Devin；`internal/` 下 38 个目录无任何豆包相关 provider。
2. **社区存在两个第三方豆包 CPA 插件**，均为 Go + c-shared `.so`，均为 0 star 个人仓库，且**走的是两条不同的上游产品线**：
   - `Lxapk/DouBao-CPA-Plugin`：豆包网页版 **IM 协议**（`/im/send/message`，`aid=497858`），能力为文本 + 深度思考 + 生图 + 生视频；认证方式为**粘贴浏览器 Cookie 快照**。
   - `rex-zsd/doubao-cpa-plugin`：豆包 **Work 端点**（`/alice/office/*`，`aid=1044603`），能力为 agent + 真实 MCP 工具调用；认证方式为 **Passport 扫码**。

3. **两个实现各有硬缺口**，不能直接照搬：
   - Lxapk 版**只发 Cookie、从不读响应 `Set-Cookie`**（全仓仅 3 处 `req.Header.Set("Cookie", …)`，无任何 `resp.Cookies()` 解析），凭据是**一次性快照而非可续期凭据**，`sid_guard` 约 30 天即硬失效；且**无账号级 failover**（`wrapExecutorError` 仅转文案，不切号不冷却）。
   - rex-zsd 版虽实现了 `durableJar`（含 `SetCookies` 持久化 + `deferToNewer` 防覆盖）与 Passport 扫码，但**明示仅支持 Linux amd64、单账号**，且实现体量很大（`gateway.go` 37KB + `toolprobe.go` 28KB + 多轮工具媒体处理）。

因此本需求的目标是**取两者之长**：认证方式经用户裁定为**复用用户浏览器登录态**（插件内不实现登录，避开手机号风控签名与内嵌浏览器两条重路线），会话持久化沿用 rex-zsd 的 `durableJar` 方案解决 Lxapk 版「凭据不可续期」的硬缺口，账号级 failover 复用本仓库既有的账号池 + 阶梯冷却 + 40x 换号模式，并按用户裁定的双线顺序分阶段落地。

### 目标

新增 `doubao-provider` 插件，把豆包账号能力封装为 CPA 的 OpenAI 兼容 Provider，与既有 9 插件同构，分两阶段交付：

- **阶段一（IM 协议）**：登录态导入 → 会话持久化与续期 → 多账号池 → 文本/深度思考/生图/生视频 → 故障转移 → 管理面板 → 发布链路。
- **阶段二（Work 端点）**：评估并落地 agent 能力与客户端工具链（真实 MCP 连接器），复用阶段一的认证与账号池骨架。

## 二、范围

### 范围内

1. **登录态导入**：面板提供「导入登录态」入口，引导用户在自有浏览器登录豆包后，把会话凭据（Cookie）导入插件；插件**不实现登录流程**（不调 `send_code` / `sms_login`，不内嵌浏览器）。因豆包关键会话 Cookie（`sessionid` / `sid_guard` 等）为 HttpOnly、页面 JS 不可读，导入必须由用户从浏览器侧导出，具体形态见 GAP-009。
2. **会话持久化与续期**：实现可写回 Cookie Jar（对齐 `durableJar` 模式），捕获上游 `Set-Cookie` 并持久化，解决 Lxapk 版的「快照 30 天硬失效」问题。
3. **多账号池**：凭据落盘至 `~/.antigravity_cockpit/doubao_accounts/`，支持启停/删除/查看。
4. **故障转移**：429 / 402 / 5xx / 传输错误触发换号重试，复用本仓库既有阶梯冷却模式（30s × 连续失败次数，上限 10 分钟）。
5. **模型发现**：动态拉取账号可用模型清单，响应宿主 `oauth-excluded-models` 配置。
6. **协议实现（阶段一）**：豆包 IM 协议 `/im/*` 端点接入，含 4 个已知协议要点（见「四、约束」）。
7. **能力覆盖（阶段一）**：文本对话、深度思考（`reasoning_content`）、生图、生视频。
8. **流式转发**：SSE 流式与非流式；遇终止帧立即退出并关闭连接。
9. **管理面板**：登录态导入（粘贴/扩展回传）、账号管理、模型展示、状态诊断。
10. **发布链路**：CI workflow、`registry.json`、图标、生产热重载验证。

### 范围外

1. **不修改 CPA 宿主本体**（跨项目只读红线）。
2. **不做豆包开放平台 API key 型接入**（火山方舟 ARK）——本项目定位是网页端账号能力反代，与既有 9 插件路线一致。
3. **阶段一不含 Work agent 工具链**（`/alice/office/*`、真实 MCP 连接器、任务恢复、并发控制）——归阶段二。
4. **不在插件内实现任何登录流程**——不做扫码登录、不做手机号 + 短信验证码登录、不内嵌 headless 浏览器；插件只消费用户浏览器已有的登录态。
5. **不实现豆包侧的自动注册/养号**。

## 三、输入输出

- 输入：用户浏览器导出的豆包会话凭据（Cookie 集合，经面板导入）；CPA 标准 `executor.execute` / `executor.execute_stream` 请求。
- 输出：OpenAI 兼容的 chat completions 响应（流式 SSE 与非流式）；`/v1/models` 模型清单；生图/生视频以 OpenAI 多模态 `image_url` 与 `media` 扩展返回。

## 四、约束

1. **协议约束（阶段一 IM，v1.4 部分实测验证）**：以下 4 点为 Lxapk 版 README 记录的要点，**其中第 1 点已实测确认仍有效，其余 3 点待验证**：
   - `Content-Type` 必须是 `application/json; encoding=utf-8`（参数名是 `encoding` 不是 `charset`）——**v1.4 实测确认**：对 `/im/chain/recent_conv` 用 `charset=utf-8` 或纯 `application/json` 均返回 `712012002 不支持编码类型`；改用 `encoding=utf-8` 后错误推进为 `712012003 不支持CMD类型`，证明编码类型校验通过、该要点仍适用（后续需正确的 `cmd` 参数）；
   - 消息用 `content_block` 数组而非 `content` 字符串（否则"要它画图它只描述图片"）——**待验证**；
   - `option.aggregate_params.mode_id` 必须为 `"1"`——**待验证**；
   - **不需要** `a_bogus` / `msToken` 签名——**v1.4 部分实测确认**：`/alice/basic/launch`、`/alice/im/launch` 省略这两个参数均返回 `code:0`；`/chat/completion` 省略后仍能建立 SSE 流（未触发签名校验）。
2. **参数约束（v1.4 新增，实测确认）**：业务 API（`/alice/*`、`/im/*`）**必须携带完整 query 参数集**才能返回有效数据——实测缺参时 `/alice/basic/launch` 返回 `{"code":0,"data":null}`（HTTP 200 但无数据），补上 `version_code=20800&device_platform=web&doubao_device_platform=web&aid=497858&real_aid=497858&pkg_type=release_version&pc_version=3.41.4&doubao_pc_version=3.41.4&device_id=...&web_id=...&tea_uuid=...&region=CN&sys_region=CN&samantha_web=1&web_platform=browser&use-olympus-account=1` 后返回完整 data（含 `model_list:67`）。**`device_id` / `web_id` / `tea_uuid` 是设备级标识，需与凭据一同持久化**。
3. **端点特异性约束（v1.4 新增，实测确认）**：风控宽松度**非全局一致**——`/alice/basic/launch`、`/alice/im/launch` 宽松（无签名可调），但 `/alice/profile/self` 无签名返回 `710010202 系统错误`。实施时须逐端点验证，不得假设全链路宽松。
4. **认证约束（登录态导入路线）**：豆包会话凭据是 `accounts.doubao.com` / `.doubao.com` 域下的 Cookie 集合，其中 `sessionid` / `sessionid_ss` / `sid_tt` / `sid_guard` / `uid_tt` / `odin_tt` / `d_ticket` / `ttwid` 均为 **HttpOnly**（页面 JS 不可读），仅 `flow_cur_user_sec_id` / `passport_csrf_token` 非 HttpOnly——**因此登录态必须由用户从浏览器侧导出**（DevTools 复制 Cookie header，或浏览器扩展），插件无法从页面 JS 直接读取。**判据见 AC-001**。
5. **会话约束**：会话 Cookie 是全部凭据，无法脱离用户重建；必须有续期机制与失效上报（失效时让 CPA 标记账号待重授权，而非无限重试）。
6. **工程约束**：c-shared 动态库（`import "C"`），Windows 无 CGO 环境，本地验证一律走 `python scripts/cgo-shim-build.py doubao`。
7. **架构约束**：与既有 9 插件同构；凭据直写物理文件（`writeAuthFileDirect` + fsnotify），不走 `host.auth.save` 以免丢字段。
8. **上游能力约束**：豆包网页端是聊天客户端而非补全 API——**不承诺** system prompt 原生优先级、`temperature` / `top_p` 等采样参数、上游返回真实 usage（只能估算）。
9. **本地连接红线**：测试与调试只允许使用 local 配置，禁止连接 test/prod。

## 五、验收条件（AC）

- `AC-001`：面板可完成**登录态导入**（引导用户从自有浏览器导出豆包会话 Cookie → 面板导入 → 插件校验会话有效性 → 落盘至 `~/.antigravity_cockpit/doubao_accounts/doubao-<uid>.json`）。**有效性判据（v1.4 修正）**：调 `GET accounts.doubao.com/passport/account/info/v2/`，以 `message == "success"` 且 `data.sec_user_id` 非空为登录有效——实测有会话返回 `message:"success"` + `sec_user_id`（76 字符）+ `user_id`，无会话返回 `message:"error"` 且无该字段，**区分度已验证**。**不得**使用 `/alice/basic/launch` 的 `code:0` 或 `model_list` 作判据（实测伪造 Cookie 仍返回 `code:0` + 67 条模型，无区分度）。
- `AC-002`：**会话可持续**——实现 Cookie Jar 写回，上游 `Set-Cookie` 被捕获并持久化；会话续期无需人工重新登录；失效时上报明确状态（对比 Lxapk 版的一次性快照）。**v1.4 部分验证**：实测 `accounts.doubao.com/ttwid/check/` 下发 `Set-Cookie: gd_random=...; Max-Age=604800`，证明该域确有滚动下发行为；**但会话主 Cookie（`sessionid`/`sid_guard`）的续期路径尚未验证**，须在实施前补测（若主 Cookie 不滚动下发，则 AC-002 需降级为「长有效期 + 失效重导入」）。
  - **v1.6 补测结论（TASK-003 执行期实测，2026-10-17）**：主 Cookie **不滚动下发**，触发本条降级条款。证据：① `passport/account/info/v2/` 与 `alice/basic/launch` 响应 `Set-Cookie` 数量均为 **0**；② 仅 `accounts.doubao.com/ttwid/check/` 下发 `gd_random`（设备标识 Cookie，HttpOnly，`Max-Age=604800`），与登录态续期无关；③ 会话主 Cookie 全为 HttpOnly 且长期有效，续期由上游按自身策略处理，插件侧无法也不应主动刷新。
  - **降级后口径（TASK-003 实际交付）**：① Cookie Jar 写回能力**保留并实现**（捕获 `gd_random` 等设备级滚动 Cookie 并落盘，减少每次请求的设备指纹漂移）；② **失效检测与状态上报**实现（`auth_state: ok|expired`，依据账号文件中会话主 Cookie 的有效期）；③ 不再承诺「会话续期无需人工重新登录」——会话失效时通过面板状态明确提示用户重新导入，属「长有效期 + 失效重导入」形态。
- `AC-003`：`/v1/models` 返回**稳定语义别名目录**（`doubao/default` 默认助手、`doubao/pro` 深度思考、`doubao/image` 图像生成、`doubao/video` 视频生成），且响应宿主 `oauth-excluded-models` 配置。**v1.5 方案确定**：不解码上游内部名（67 条内部代号与 UI 名的映射未公开），改为自声明别名 + **pass-through 规则**（未知名原样透传给上游，上游忽略未知模型并回落账号默认）。**关键**：`image`/`video` 别名携带 `skill` 参数（`skillImageGen=3` / `skillVideoGen=5`）作为语义声明。**v1.8 修正**：实测该参数不是生成路径的必要条件（上游按提示词意图决定，详见 AC-005），保留注入是为了语义正确与上游策略收紧时的前向兼容。
- `AC-004`：`/v1/chat/completions` 非流式与流式（SSE）均可用；流式遇终止帧立即退出并关闭连接；深度思考以 `reasoning_content` 返回。**v1.5 补充**：请求体须按 GAP-010 解明的契约构造（`content_block` 结构 + `mode_id:"1"` + `need_create_conversation`），且该端点 Content-Type 用纯 `application/json`（**与 `/im/*` 的 `encoding=utf-8` 相反**）。
- `AC-005`：生图与生视频可用，返回 OpenAI 多模态格式（`image_url` + `media` 扩展），无水印直链可换取。**v1.5 补充**：通过 `skill` 参数（`skillImageGen=3` / `skillVideoGen=5`）激活生成路径。**v1.8 修正（TASK-007 实测）**：`skill` **不是**生成的必要条件——上游按提示词意图决定是否绘制，不带 `skill` 的「画一只猫」同样产出 `CREATION` 块，带 `skill=3` 的闲聊提示词仍只回文本（上游回显 `input_skill.skill_id="0"`）。`skill` 注入保留为语义声明（无副作用，且上游策略可能收紧），验收改为「生成提示词能产出可访问媒体 + 多模态格式正确」，不再断言「无 `skill` 必不生成」。
- `AC-006`：**账号级 failover**——多账号可启停/删除；429 / 5xx 触发换号重试并计入阶梯冷却；一次成功即清零回落。
- `AC-007`：`python scripts/cgo-shim-build.py doubao` 的 build/vet/test 全绿。
- `AC-008`：发布链路完整（CI 7 平台产物 + registry 同步 + 远端 raw URL 可达 + 生产热重载 `restart_required=false`）。

## 六、缺口（GAP）

- `GAP-001`：**登录会话能否用于 IM 端点（v1.4 更新：会话有效性已验证，IM 端点在途）**。实测确认：① 会话可用于业务 API——`/alice/basic/launch` 返回 `code:0` / `is_login:true` / `model_list:67`；② `/alice/im/launch` 返回 `code:0` + 3.6KB 配置数据；③ **`/chat/completion` 能建立 SSE 流**（`Content-Type: text/event-stream`，页面真实请求亦为 `text/event-stream`）。**剩余未验证项**：`/chat/completion` 的完整请求体契约（见 GAP-010）与 `/im/chain/single` 的消息拉取（实测返回 `712010202 unknown error`，需正确的 `cmd` 参数）。**证据**：`doc/5-tests/2026-10-17_015144_豆包手机号登录真实链路实测.md` + 本文件 v1.4 修订。
- `GAP-002`：**IM 协议细节时效性（已确认为真）**。实测抓到的真实端点与 Lxapk 版（2026-10-02）**存在实质差异**——业务启动为 `/alice/basic/launch`（Lxapk 用 `/alice/user/launch`）、对话补全为 `/chat/completion`（Lxapk 用 `/im/send/message`）；另有 `/alice/im/launch`、`/im/message/send_rate_limit`、`/creativity/*`、`/alice/commerce/sale/subscription/quota/summary/` 等 Lxapk 未覆盖端点。**处置**：实现前必须以实测清单为准，不得照搬 Lxapk 路径。
- `GAP-003`：**豆包风控边界未知**（是否限速、是否封号、触发人机验证的条件）。**处置**：内置请求限速；生产灰度观察；README 与面板明确风险提示。**状态：未关闭**（单账号低频实测无法暴露边界）。
- `GAP-004`：**多账号并存可行性未验证**。两个第三方实现均为单账号（rex-zsd README 明示「单账号」）或弱多账号，本需求的账号池 + 轮换是否会被上游按设备指纹识别并互踢，尚未验证。**处置**：前置侦察阶段用 2 个账号实测并存与轮换。**v1.4 补充风险**：实测发现请求携带 `device_id` / `web_id` / `tea_uuid` 设备级标识，多账号若共用同一组标识可能被关联——实施时须评估「每账号独立设备标识」策略。
- `GAP-005`：**阶段二 Work 端点工作量评估缺失**。rex-zsd 的 Work 实现含工具链、任务恢复、并发控制、多轮工具媒体处理，体量远超阶段一。**处置**：阶段一交付后单独做阶段二立项评估，不在本需求内承诺工作量。
- `GAP-006`：**认证契约（已解开，路线已改）**。原手机号路线需强风控签名（`a_bogus` / `sign` / `qs`，由浏览器风控 SDK 生成），故被用户裁定弃用。**现行路线为登录态导入**：用户浏览器已完成登录，凭据为 Cookie 集合；登录后业务 API 风控宽松（实测省略 `msToken`/`a_bogus` 仍 `code:0`），导入后调用无需签名。**证据**：同上实测文档。
- `GAP-007`：**插件内登录缺少同类先例（已确认，路线已绕开）**。四个已知豆包逆向实现（`doubao2api` 281★、`doubao-free-api` 222★、Lxapk、rex-zsd）中，**Lxapk 走的正是「用户浏览器登录态导入」路线**（粘贴 Cookie header），证明该路线有可用先例；其余三个各自实现登录（Playwright / 扫码）并承担风控成本。**本需求选择 Lxapk 的路线并修补其硬缺口**（补 `Set-Cookie` 回写续期 + 账号级 failover）。
- `GAP-008`：**登录环节强依赖浏览器环境（已关闭——通过把登录移出插件）**。原问题：手机号登录需浏览器风控签名（`a_bogus` / `sign` / `qs` 由 `webmssdk.es5.js` 动态生成），纯 Go 无法复现。**关闭方式**：用户裁定认证采用「复用用户浏览器登录态」，登录发生在用户自有浏览器中，插件**不再承担登录**，该约束对插件不成立。**另**：纯 HTTP 补测发现扫码路径同样可纯 Go 实现（`get_qrcode` / `check_qrconnect` 裸请求 `error_code=0`，零签名零浏览器），但需用「抖音 APP」扫码，用户已裁定不采用；作为备选记录在实测文档 1.1 / 3 节。**证据**：同上实测文档。
- `GAP-009`：**登录态导入的具体形态待定（不阻断立项）**。豆包关键会话 Cookie 为 HttpOnly，页面 JS 不可读，故导入必须由用户从浏览器侧导出。可选形态：① 面板引导用户在 DevTools 复制 Cookie header 后粘贴（对齐 Lxapk，且本仓库 `traework` 已有 bridge 页粘贴先例）；② 配套浏览器扩展读取 Cookie 后回传。**处置**：实施规划阶段裁定形态；**导入机制本身已确定（用户侧导出），仅 UI 形态未定，属实施细节，不阻断编码**。
- `GAP-010`：**`/chat/completion` 请求体契约未解明（v1.4 新增，v1.5 已解开 → 关闭）**。**解法来源**：Lxapk 最新源码 `completion.go`（2026-10-17 抓取）给出了完整请求体结构，含其自述的两个关键陷阱——① 消息必须用 `content_block`（文本在 `content_block[0].content.text_block.text`），用 `content` 会**静默降级为纯聊天**（不报错，只描述而非生成）；② `option.aggregate_params.mode_id` 必须为 `"1"`，否则不进入生成路径。**本次探测失败的三个具体原因已定位**：Content-Type 误用 `encoding=utf-8`（该端点须纯 `application/json`，与 `/im/*` 相反）、缺 `option.need_create_conversation:true`、`content_block` 结构不符。**请求体骨架**：`{client_meta:{conversation_id,bot_id,last_section_id,last_message_index,local_permissions}, messages:[{local_message_id,content_block:[{block_type,content:{text_block:{text,...}},...}],message_status}], option:{...,aggregate_params:{mode_id:"1",...},model_config,sse_recv_event_options:{support_chunk_delta:true},support_lazy_fetch_stream:true,unique_key,start_seq,need_create_conversation}, user_context:[], ext:{...}}`。**证据**：Lxapk `completion.go` 源码 + 本文件 v1.5 修订。**v1.7 实测修正（TASK-004 执行期）**：`client_meta.local_conversation_id` 是**必填项**，缺失或空串会被上游以 `710020202 common invalid param` 拒绝（HTTP 200 + SSE 错误帧，不报 HTTP 错误）；任意非空值均可（网页端发 `local_<随机串>`）。该项不在 Lxapk 参考实现中，是逐字段消融对照浏览器真实请求定位出来的。同轮实测确认 SSE 正文分散在 `STREAM_MSG_NOTIFY` 首块、`STREAM_CHUNK` 的 `patch_op`、`CHUNK_DELTA` 的 `text` 三类事件中，必须按到达顺序累加；`FULL_MSG_NOTIFY` 携带的是用户提问回显（`message.user_type=1`），计入会把问题拼进回答。正文在首个 `SSE_REPLY_END`（`end_type=1`）前已全部到齐，可立即停止读取。
- `GAP-011`：**模型名编码层未解明（v1.4 新增，v1.5 已解开 → 关闭）**。**解法来源**：Lxapk `model_provider.go` 明确**不解码内部名**，理由是「67 个条目是内部代号（`Aoe`/`ances s2`/`func: ogt（4k）`），与 UI 展示名的映射未公开，与其编造映射不如显式声明目录」。**采用方案**：声明 4 个稳定语义别名（`default` 默认助手 / `pro` 深度思考 / `image` 图像生成 / `video` 视频生成）+ **pass-through 规则**（未知名原样透传，上游忽略未知模型并回落到账号默认）。**关键配套**：`image`/`video` 别名必须带 `skill` 参数（`skillImageGen=3` / `skillVideoGen=5`，来自 `/samantha/skill/recommend`），否则「画一只猫」只会让模型**描述**而非**绘制**。**证据**：Lxapk `model_provider.go` 源码。
